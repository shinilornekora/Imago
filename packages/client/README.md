# `@stand/client` — браузерный клиент стенда

Vite 8 + React 19 + TypeScript (strict). Один и тот же интерфейс и один модуль отрисовки (Canvas 2D)
для трёх адаптеров данных: **H** (`fetch` + `Map`), **Q** (TanStack Query 5), **Z** (`@rocicorp/zero` 1.9.0, zero-cache + synced queries + custom mutators).
Измерения выполняются на production‑сборке (`dist/`), которую отдаёт статический обработчик API/шейпера с корня `/`.

## Запуск

```bash
export PATH=/opt/node24/bin:$PATH
npm install                                  # из корня репозитория (workspaces)
npm run build -w packages/client             # tsc --noEmit (strict) + vite build → packages/client/dist
npm run mock  -w packages/client -- --port 3000 --latency 25 --static ../dist   # мок API (§2.1–2.3) + статика
# либо dev-сервер (не для измерений): npm run dev -w packages/client  → /api проксируется на 127.0.0.1:3000
npm test      -w packages/client             # дымовые проверки Playwright 1.56.0 против мока (см. ниже); z.spec пропускается без STAND_Z_E2E=1
npm run test:z -w packages/client            # адаптер Z против реальных API (:3002, STAND_TEST_HOOKS=1) + zero-cache (:4848) [+ шейпер :8082]
```

Открыть: `http://127.0.0.1:3000/?adapter=H&mode=P&cache=1&doc=doc-alice-1&autologin=alice`.

## Параметры конфигурации (query‑строка)

| Параметр | Значения | По умолчанию | Смысл |
|---|---|---|---|
| `adapter` | `H` \| `Q` \| `Z` | `H` | адаптер данных |
| `mode` | `F` \| `P` | `P` | F — полная загрузка всех страниц при открытии; P — частичная (активная + LRU‑окно) |
| `cache` | `1` \| `3` \| `10` (любое ≥ 0) | `1` | размер LRU‑окна неактивных страниц в режиме P |
| `doc` | id документа | первый документ пользователя (`GET /api/documents`) | открываемый документ |
| `page` | индекс страницы (1‑based, как `data-page-index`) или `pageId` | первая по индексу | **начальная страница**: именно она передаётся адаптеру в `open()` и в режиме F получает приоритет загрузки |
| `autologin` | `alice` \| `bob` | — | автоматический вход тестовой учётной записью (укорачивает измеряемый путь); без него — форма входа |
| `zero` | URL zero-cache | `<origin>/zero` (через шейпер/Caddy) | только Z: адрес WebSocket zero-cache (прямой режим без шейпера: `?zero=http://127.0.0.1:4848`) |
| `zopt` | `1` | выкл | только Z: включить оптимистичную (клиентскую) часть мутатора; в измеряемом пути она **выключена** (см. «Оптимистичная окраска») |

Токен доступа хранится **только в памяти** (`src/auth.ts`, переменная модуля); в `localStorage`/`sessionStorage`/IndexedDB
он не попадает.

**Начальная страница задаётся явно.** `?page=` разбирается в `config.initialPage`, `stand.ts` передаёт его в
`adapter.open(docId, initialPage)` и выбирает ту же страницу для `selectPage` — обе стороны используют один
`resolveInitialPageId()` (`src/adapters/types.ts`). Раньше `open()` вызывался без аргумента, и приоритет активной
страницы в F держался на совпадении «стартовая страница = минимальный `index`»: смена стартовой страницы молча
сломала бы правило §1.6 (критик A, п. 16). Значение по умолчанию — прежнее (первая по индексу), измерительная
оболочка ставит `?page=1` явно.

**Пароль автологина не передаётся в URL.** Измерительная оболочка кладёт `{login, password}` в контекст страницы
(`page.addInitScript` → `window.__standCredentials`) ДО загрузки документа; `passwordFor()` берёт пароль оттуда, и
вход выполняет сама страница обычным `POST /api/auth/login` — измеряемый путь тот же, но секрет не попадает в
журналы доступа, в `Referer`, в счётчики шейпера и в запись прогона (дефект N9). Параметр `?pass=` остаётся
работающим запасным каналом для функциональных проверок (они не измеряют время и идут мимо шейпера); в
production‑сборку пароли по‑прежнему не входят.

## Интерфейс

* Верхняя панель: бейдж адаптера/режима (`[data-testid=adapter-badge][data-adapter][data-mode]`), индикатор состояния
  `[data-testid=state][data-state=idle|loading|ready|error][data-pending=N][data-revision=R]`, статистика удержания, кнопка «Выйти» (`[data-action=logout]`).
* Левая панель: список страниц — кнопки `button[data-page-id][data-page-index]`; панель заливки: `input[type=color][data-testid=fill-color]`,
  «Local fill» (`[data-action=local-fill]`, `setLocalFill` для выделенной фигуры) и «Source fill» (`[data-action=source-fill]`,
  `setSourceFill` для источника выделенного экземпляра либо для выделенного источника).
* Центр: один `<canvas data-testid=stage>` 1280×720 CSS‑px с учётом `devicePixelRatio`; `src/canvas/renderer.ts` рисует **только активную
  страницу** в порядке `z` (rect / ellipse / text фиксированным шрифтом `14px sans-serif`), очищая холст перед каждой отрисовкой.
  Клик — выделение по попаданию (хранится только id фигуры в состоянии интерфейса); колесо — масштаб; Shift/средняя кнопка + перетаскивание — панорама.
  Выделение и камера переживают обновление данных, так как ссылаются на id/координаты, а не на объекты.
* React не участвует в пути данных: адаптер уведомляет подписчика активной страницы, тот кладёт снимок в отрисовщик напрямую;
  в `useSyncExternalStore` (`src/ui-store.ts`) попадают только индикаторы.

### События и их семантика

| Событие | Когда | `detail` |
|---|---|---|
| `open` | метаданные документа получены | `{docId, revision, pages}` |
| `page-select` | вызов `selectPage` (клик или API) | `{pageId, index, seq}` |
| `page-ready` | **один раз на каждый `page-select`**: адаптер отдал **полный** снимок активной страницы с `revision ≥` ревизии последней подтверждённой команды **и** холст отрисован (двойной rAF). Частичный/устаревший снимок готовностью не считается | `{pageId, revision, shapeCount, seq, sinceSelect}` |
| `command-sent` | непосредственно перед POST/мутацией (при повторе после `revision_mismatch` пишется повторно с новым `expectedRevision`) | `{opId, type, targetId, fill, expectedRevision, targetRevision}` |
| `command-server` | **транспорт** подтвердил мутацию: Z — `mutate().server`, H/Q — получен ответ POST. Журнал операций ещё не читался | `{opId, via: 'zero-server'\|'http-post', sinceSent}` |
| `command-synced` | данные команды в клиентском хранилище **активной страницы**: Z — снимок активной страницы достиг `targetRevision` (содержимое сверено, см. ниже), H/Q — перечитывание активной страницы завершено. Холст ещё не перерисован | `{opId, sinceSent}` |
| `command-acked` | сервер вернул **результат операции** (`revision`, `affectedPages`, `affectedShapes`); у Z — после `GET /api/operations/:opId` | `{opId, revision, targetRevision, affectedPages, affectedShapes, sinceSent}` |
| `command-drawn` | активная страница **фактически отрисована** (двойной rAF) со снимком `revision ≥ targetRevision`; **не ждёт `command-acked`** — см. ниже. Если активная страница командой не затронута, её снимок «поднимается» до новой ревизии без сетевого запроса и перерисовывается | `{opId, revision, pageId, drawnRevision, sinceSent, beforeAck}` |
| `command-retry` | шаг политики повтора: `via: 'poll'` (опрос операции), `'repost'` (повторный POST с тем же opId), `'revision_mismatch'` | `{opId, via, attempt?, reason?}` |
| `error` | `scope: 'open' \| 'page' \| 'command' \| 'login' \| 'logout'` | `{scope, message, pageId?, opId?}` |
| `logout` | завершение очистки | `{}` |

«Команда завершена» = `command-acked` **и** `command-drawn` (оба момента пишутся отдельно). Оптимистичная окраска не используется.

#### Почему `command-drawn` не ждёт подтверждения (§1.8)

§1.8 требует: «время отсчитывается до фактического обновления холста, подтверждение сервера регистрируется
отдельно». Поэтому целевая ревизия команды вычисляется **в момент отправки**, а не из ответа сервера:

* `targetRevision = expectedRevision + 1` и это **точно**, а не оценка: сервер принимает команду только при
  `expectedRevision === doc.revision` и поднимает ревизию ровно на единицу в той же транзакции
  (`packages/server/src/domain/executeCommand.ts`, шаги 4 и 6), а документ на стенде меняет единственный
  писатель — сама измерительная оболочка. При `revision_mismatch` контроллер повторяет команду, и
  `targetRevision` уточняется вместе с новым `expectedRevision`.
* `command-drawn` выпускается из `onDrawn` со временем `drawn.at` (второй rAF после `draw()`), как только
  активная страница нарисована с ревизией ≥ `targetRevision`. Условия «команда подтверждена» в предикате нет.
* Следствие: **у Z `command-drawn` регулярно раньше `command-acked`** (`detail.beforeAck = true`) — ровно на
  время чтения журнала операций (`GET /api/operations/:opId`, через шейпер ≈ 60 мс, колонка `t_cmd_opget_ms`).
  Это законный результат, а не ошибка: холст действительно обновлён серверными данными раньше, чем клиент
  узнал номер ревизии. У H/Q результат приходит в теле ответа POST, поэтому там drawn всегда после ack.
  До исправления `command-drawn` выпускался внутри `onAcked`, из-за чего `t_cmd_drawn ≡ t_cmd_ack` у Z и
  метрика §1.2 «команда до актуального холста» была завышена на артефакт оболочки.

### Учёт ревизий (общий для H и Q, `src/adapters/doc-state.ts`)

Клиент знает ревизию документа (максимум из метаданных, ответов чтения и результатов команд) и для каждой подтверждённой
им команды — затронутые страницы. Снимок страницы `P`, прочитанный на ревизии `r`, принимается, если
`r ≥` max ревизии команд, затронувших `P`; иначе ответ («старое чтение», пришедшее после команды) отбрасывается и страница
перечитывается (до 3 раз). Если `r` меньше известной ревизии документа, но все промежуточные ревизии — наши команды, не трогавшие `P`,
снимок эквивалентен снимку на текущей ревизии и хранится с ней («поднятие» без запроса). Если промежуточные ревизии
неизвестны (чужое изменение), страница перечитывается.

## Режимы F и P

**H, F.** `open()` получает метаданные и ставит все страницы (по индексу; первая — активная) в ограничитель параллелизма 4;
`selectPage` поднимает страницу в начало очереди. После команды: активная затронутая страница — прерывание текущего чтения и
немедленное перечитывание (ожидается до разрешения `runCommand`); остальные затронутые — перечитывание в фоне через тот же ограничитель;
незатронутые актуальные — поднятие ревизии.

**H, P.** `selectPage`: отмена незавершённого чтения прежней активной страницы (запись без данных удаляется), затем LRU‑окно:
остаются активная и `cache` последних посещённых, остальные — `Map.delete` (+ удаление их фигур из индекса). Отсутствующая
или `stale` страница читается; `stale` снимок при этом показывается сразу, готовность наступает по свежему. После команды
затронутые неактивные страницы в окне помечаются `stale` и перечитываются при следующем `selectPage`.

**Q, F.** `open()` вызывает `prefetchQuery` для всех страниц; HTTP‑чтения проходят через ограничитель (4) внутри `queryFn`,
`signal` не потребляется (смена страницы не отменяет загрузку). После команды: `invalidateQueries(refetchType:'active')` по
затронутым — активная перечитывается (ожидается), неактивные помечены `stale` и перечитываются в фоне (`prefetchQuery`).

**Q, P.** `selectPage`: `removeQueries` для страниц вне окна (активная + `cache` последних), затем `fetchQuery` активной
(нет данных → чтение; `isInvalidated` → перечитывание; свежие → без запроса; в полёте → дедупликация). Наблюдатель `QueryObserver`
создаётся подпиской интерфейса; отписка при смене страницы отменяет незавершённый запрос. Затронутые командой неактивные страницы
остаются в кеше как `stale` (invalidated) и перечитываются при следующем `fetchQuery`.

**Z.** `open()` — метаданные по HTTP (как H/Q), затем `new Zero({cacheURL: location.origin + '/zero' (или `?zero=<url>`),
userID, auth: токен, schema, mutators, kvStore:'idb'})` и materialized `docMeta` (ревизия документа синхронизацией).
**Страница готова** — `shapesByPage` дал `resultType 'complete'` (результат `'unknown'` готовностью не считается); снимок
несёт синхронизированную ревизию `documents`, **но не выше, чем подтверждает его собственное содержимое** (см. ниже).
**F**: все страницы материализуются при открытии (активная первой, параллелизм 4) и остаются. **P**: активная + LRU‑окно
`cache`; вытесненные view — `destroy()`, строки уходят из хранилища. **Команда** — `zero.mutate(mutators.setSourceFill(...))`:
`command-sent` при вызове; `command-server` — `.server` разрешился успехом; `command-acked` — дополнительно получен результат
операции через `GET /api/operations/:opId` (Zero не отдаёт результат мутатора); `command-drawn` — активная страница
отрисована со снимком ревизии ≥ `expectedRevision + 1`, **независимо от ack** (обычно раньше него).
`getRetained()` — реальные строки хранилища Zero (кеш, обновляемый асинхронно; точно — `getRetainedAsync()`).
`logout()` — `zero.close()` + `dropAllDatabases()`.

*Оптимистичная окраска (клиентская часть мутатора) в измеряемом пути ОТКЛЮЧЕНА.* Клиент регистрирует мутаторы
`setSourceFill`/`setLocalFill` с теми же именами и валидаторами, но с **пустой** клиентской реализацией
(`serverAuthoritativeMutators` в `src/adapters/z.ts`; серверная реализация не затронута — мутация как обычно уходит
на push‑обработчик API). Причина (дефект N1): при оптимистичной окраске содержательный критерий готовности
(`rowsReflect`, ниже) удовлетворялся **записью самого клиента** — `applyOptimistic` красит ровно тот набор строк и в
тот же цвет, который проверяет предикат, — поэтому в штатном пути критерий ничего не связывал, а фактическим
признаком оставалась ревизия строки `documents`; в данных это было видно как `t_cmd_synced ≈ t_cmd_server`. Без
клиентской реализации новая заливка появляется в хранилище ровно из одного источника — синхронизации с сервера, и
`command-synced` / `command-drawn` измеряют приход **серверных** данных.
**Цена для §1.6.** Zero допускает серверную реализацию команды, отличную от локального предварительного действия, и
стенд «не объявляет массовую команду завершённой по предварительной окраске видимых фигур» — то есть ни одна
измеряемая величина смысла не теряет. Но в измеряемом пути пропадает мгновенный локальный отклик, который Zero даёт
в обычном приложении: до прихода поки холст показывает прежние цвета (индикатор `pending` при этом работает).
Поэтому это **граница применимости выводов по Z**: измеряется время до актуального холста по серверным данным, а не
воспринимаемая отзывчивость оптимистичного UI. Вернуть штатное поведение можно параметром `?zopt=1`
(`Z_SETTINGS.optimistic`, пишется в `passport.json → adapters.Z_SETTINGS`); основная серия идёт без него.

*Ревизия снимка Z по содержимому страницы (§1.2).* У строк `shapes` нет ревизии, а ревизия приходит отдельной строкой
`documents`. §1.2 требует для синхронизируемых данных проверять «фактическое содержимое полученной страницы», поэтому
адаптер помнит ожидаемый эффект каждой отправленной им команды (`pendingEffects`: источник и его непереопределённые
экземпляры получают новую заливку — тот же предикат, что у серверного `updateSourceAndInstances`). Пока строки страницы
эффект не отражают, её снимок публикуется с ревизией `targetRevision − 1`, даже если строка `documents` уже принесла
бо́льшую. Страница, которой команда не касается, предикату удовлетворяет тривиально и поднимается до новой ревизии сразу.
Так `page-ready` и `command-drawn` не могут быть зафиксированы на снимке «новая ревизия + старые заливки»; раньше от этого
защищала только недокументированная склейка двух `setSnapshot` в одном кадре rAF. Стоимость — один проход по строкам
страницы, и только пока команда не подтверждена содержимым (в измерительной серии это одна команда на прогон).
Предикат связывает только потому, что оптимистичная окраска отключена (см. выше). Эффект, поверх которого
синхронизированная ревизия уже ушла **дальше** (`syncedRevision > targetRevision`), снимается: иначе две
перекрывающиеся команды по одному источнику в разные цвета навсегда удерживали бы ревизию всех снимков на
`targetRevision − 1` и `page-ready` не наступил бы до `close()` (дефект N7; в измеряемом сценарии команда одна,
поэтому на его числа это не влияет).
Схема/запросы/мутаторы — единый модуль `packages/server/src/zero/schema.ts`. Подробности и измерения — `docs/ZERO_SPIKE.md` §11.

## Разделение bundle по адаптерам

`createAdapter()` (`src/adapters/index.ts`) загружает модуль адаптера динамическим `import()`; Vite выносит `h`, `q`, `z`
в отдельные chunk'и (`dist/assets/{h,q,z}-*.js` ≈ 5 / 36 / 307 КБ) плюс общие мелкие chunk'и (`limiter`, `read-page`),
основной bundle ≈ 245 КБ. Загрузка chunk'а начинается в конструкторе контроллера — параллельно с `login`, а не при открытии
документа. Так H/Q не платят за клиент Zero, Z — за TanStack Query; трафик и первая готовность каждого адаптера включают
только его собственный код (`docs/DEVIATIONS.md` 3.1). Проверяется в `test/smoke.spec.mjs` (какие chunk'и загружены).

## Известные ограничения

* Адаптер Z проверяется отдельно (`test/z.spec.mjs`, `STAND_Z_E2E=1` — нужны API с хуками, zero-cache, при желании шейпер; `npm run test:z`).
* `transfer` — клиентская оценка (Content-Length/длина тел); эталонный объём обмена считается на шейпере.
* `page-ready` пишется один раз на переход; повторная отрисовка той же страницы после команды фиксируется как `command-drawn`, а не как новое `page-ready`.
* `waitFor` по умолчанию смотрит события с момента последнего действия; для ожидания «с начала» передайте `since = 0`.
