# @stand/netshaper — TCP/HTTP‑шейпер и маршрутизатор стенда (SPEC §7.1)

В песочнице нет `tc/netem`, поэтому сетевые условия эмулируются собственным прокси на чистом
Node `net`/`http`. Через него идёт **весь** трафик клиента: статика, HTTP API и WebSocket
zero‑cache. Клиент открывает `http://127.0.0.1:8080`; шейпер направляет запросы по префиксу пути.

## Запуск

```bash
export PATH=/opt/node24/bin:$PATH
node packages/netshaper/bin/netshaper.mjs \
  --listen 8080 \
  --routes '/api=127.0.0.1:3000,/zero=127.0.0.1:4848,/=127.0.0.1:3000' \
  --delay-ms 25 --bandwidth-mbit 20 --stats-port 8081
# или: npx netshaper …   (bin из workspace)
# scripts/start-shaper.sh делает то же; STAND_SHAPER_HANDSHAKE_RTT=0 выключает эмуляцию рукопожатия
```

| Ключ | Значение по умолчанию | Смысл |
|---|---|---|
| `--listen` | 8080 | клиентский порт |
| `--host` | 127.0.0.1 | адрес прослушивания |
| `--routes` | `/api=…:3000,/zero=…:4848,/=…:3000` | маршруты `префикс=host:port`; самый длинный префикс побеждает; суффикс `;strip` убирает префикс из пути (`/zero=127.0.0.1:4848;strip` → `/zero/sync` уходит как `/sync`) |
| `--delay-ms` | 25 | односторонняя задержка (25 → RTT 50; серия RTT 150 → 75) |
| `--bandwidth-mbit` | 20 | полоса в **каждую** сторону; `0` — без ограничения |
| `--bucket-ms` | 20 | ёмкость token bucket в миллисекундах передачи (≈50 КБ при 20 Мбит/с; при 40 мс ≈100 КБ страница из 500 фигур (117 КБ) уходила почти нешейпленной) |
| `--segment-bytes` | 4096 | максимальный сегмент пейсинга |
| `--handshake-rtt` / `--no-handshake-rtt` | **вкл** | задержать первые байты каждого НОВОГО соединения на один RTT (эмуляция TCP‑рукопожатия): прокси завершает рукопожатие локально, поэтому без этой задержки новое соединение обходится клиенту бесплатно. Действует и на HTTP, и на WebSocket; меняется на лету через `POST /config {handshakeRtt}` |
| `--stats-port` | 8081 | служебный порт статистики; `none` — не поднимать |

Программно: `import { startNetshaper } from '@stand/netshaper'` →
`{ listenPort, statsPort, stats(), reset(), configure({delayMs, bandwidthMbit}), close() }`.

## Как устроено

* Слушающий сокет — `net.Server`. Каждое клиентское соединение оборачивается в `ShapedSocket`
  (Duplex): входящие байты проходят через канал **inbound**, исходящие — через **outbound**, и
  только потом попадают к HTTP‑парсеру Node / в raw‑сокет. Обёртка отдаётся `http.Server` через
  `server.emit('connection', duplex)` — документированный способ инъекции потока.
* Канал (`Link`) — один на направление для всех соединений (общая «труба»), два этапа как у
  netem `rate` + `delay`: token bucket (полоса) → очередь FIFO с доставкой через `delay`.
  Порядок сохраняется и при живой смене параметров.
* Дальше — обычный HTTP/1.1 reverse‑proxy: маршрут по префиксу пути, `http.request` к upstream
  через keep‑alive агент, тела — потоками (`Transfer-Encoding: chunked` проходит), hop‑by‑hop
  заголовки вырезаются, добавляется `X-Forwarded-For`. `Upgrade: websocket` — после
  маршрутизации первого запроса соединение переходит в сырое двустороннее пайпирование
  (шейпинг сохраняется, т. к. он в обёртке сокета).
* Байты считаются на клиентском raw‑сокете: `bytesIn` — принято от браузера, `bytesOut` —
  отправлено браузеру (полезная нагрузка TCP, точная). `byRoute` — те же байты, отнесённые к
  маршруту текущего запроса соединения (браузер не пайплайнит запросы; байты следующего
  запроса относятся к нему при его разборе, поэтому для keep‑alive соединений атрибуция точна с
  точностью до порядка запросов).

### Задержка установления соединения (включена по умолчанию)

Прокси принимает TCP‑соединение локально, поэтому «настоящего» рукопожатия через задержанный канал
не происходит: без эмуляции первый запрос нового соединения стоил бы столько же, сколько запрос по
уже открытому. Это односторонняя ошибка в пользу конфигураций, которые открывают больше соединений:
в измерительной серии H/Q в режиме F открывают ≈8 соединений и делают ≈70 запросов на прогон, тогда
как Z обходится одним WebSocket (дефект A6/B22 обзоров прохода 1).

Эмуляция: первые байты клиента становятся видны прокси на один RTT (`2 × --delay-ms`) позже — ровно
та задержка, которую дало бы SYN/SYN‑ACK по тому же каналу. Проверено тестом
(`--delay-ms 25`): первый запрос на новом соединении — медиана **103 мс**, по уже открытому —
**52 мс**; WebSocket: открытие (рукопожатие + upgrade) **105 мс**, кадр по установленному
соединению **52 мс**. Уже открытые соединения при смене флага рукопожатие повторно не проходят.

Отличия от netem, зафиксированные для паспорта: окно перегрузки TCP браузера не «видит» задержку
канала (буферизация в прокси, обратное давление по 1 МиБ на соединение), slow start не
воспроизводится, таймеры ~1 мс — джиттер доставки ≤ 1–2 мс.

## Служебный сервер статистики (только для оболочки)

* `GET /stats` → `{bytesIn, bytesOut, connections, activeConnections, requests, upgrades, errors, byRoute:{'/api':{requests,upgrades,bytesIn,bytesOut},…}, sinceMs, uptimeMs, config, pendingBytes}`; `config` = `{delayMs, bandwidthMbit, bucketMs, segmentBytes, bucketBytes, handshakeRtt, handshakeRttMs}` — текущие параметры канала (их же читает паспорт серии)
* `POST /reset` → обнулить счётчики (маршрут открытых соединений сохраняется)
* `POST /config {delayMs?, bandwidthMbit?, bucketMs?, handshakeRtt?}` → сменить параметры на лету
  (`handshakeRtt` действует на соединения, открытые после вызова); `GET /config`. Измерительная
  оболочка выставляет параметры серии, включая `handshakeRtt`, перед КАЖДЫМ прогоном
* `GET /health`

## Тесты

```bash
cd packages/netshaper && npm test          # node --test, ~10 с
```

Измерения в тестах (Node http‑клиент через шейпер, 25 мс / 20 Мбит/с):
RTT `GET /api/ping` медиана ≈ 52–53 мс (50 + локальные накладные), 5 МБ ≈ 2.1 с → 20.3 Мбит/с,
WebSocket echo RTT ≈ 51 мс, три параллельных загрузки — суммарно ≈ 20.5 Мбит/с, счётчики байт
совпадают с `socket.bytesWritten/bytesRead` клиента с точностью до байта; с эмуляцией рукопожатия —
103 мс на новом соединении против 52 мс на открытом (HTTP) и 105 против 52 мс (WebSocket).
