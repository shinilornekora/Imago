# Колонки `results/<series>/runs.csv` (SPEC §7.3)

Источник истины — `packages/analysis/analysis/schema.py` (`REQUIRED_COLUMNS`). Одна строка = один прогон.
Единицы: время — миллисекунды (`_ms`), память — МБ (`_mb`, JS‑куча, 10⁶ байт) или МиБ (`_mib`, 2²⁰ байт), трафик — байты.
Пустое значение (`''`) = метрика не измерена (например, прогон с `outcome=error`). Булевы — `true`/`false`.

## Обязательные колонки

| Колонка | Тип | Смысл |
|---|---|---|
| `run_id` | str | уникальный идентификатор прогона (UUID или `<series>-<order_index>`) |
| `series` | str | имя серии выполненной программы (одиннадцать серий, 1 014 прогонов): приёмочная `main`; контролируемая ось размера при фиксированной доле посещения — `size-fraction-25x500`, `size-fraction-50x500`, `size-fraction-100x500`; окно кеша с армом F — `route-repeat` (1/3/10) и `cache3`; форма команды — `command-shape`; доля просмотренного документа — `route-full`; канал — `rtt150`; крайние точки неконтролируемой оси размера — `doc5x100`, `doc50x1000`. Серии программы 1 `cache10`, `doc10x200`, `doc100x500` не переснимались (неинформативны или перекрыты) и лежат в `results/archive/programme-1` |
| `adapter` | H|Q|Z | адаптер данных |
| `mode` | F|P | режим загрузки: полный / частичный |
| `cache` | int | окно кеша неактивных страниц (P); в F — как задано в URL (1) |
| `doc` | str | id документа |
| `repetition` | int | номер повторения конфигурации (0..N-1) |
| `order_index` | int | порядковый номер прогона в перемешанной серии |
| `started_at` | ISO‑8601 | время начала прогона |
| `outcome` | ok|error|timeout | исход прогона; ошибки не отбрасываются |
| `error_stage` | str | этап ошибки (`open`, `nav_3`, `command`, `sampling`, `reference`, …) или пусто |
| `t_first_ready_ms` | float | navigation start → готовность страницы 1 |
| `t_nav_1_ms … t_nav_10_ms` | float | клик по странице → готовность; маршрут задаётся серией (`passport.json → seriesConfig.scenario.route`), в приёмочном §7.2 это 2,3,1,4,2,5,1,6,3,50. Колонок ровно десять, поэтому у маршрутов длиннее §7.2 (`route-full` — 49 переходов, `route-repeat` — 18) здесь видны только **первые десять**, а полный список — в `t_nav_ms_list` |
| `t_nav_new_median_ms` | float | медиана переходов на страницы, которые в этом прогоне ещё **не посещались**. Принадлежность «новый/возврат» оболочка определяет ПО ХОДУ маршрута (множество посещённых, `packages/bench/src/scenario/acceptance.mjs`), а не по фиксированным номерам, поэтому набор переходов зависит от маршрута серии. Для приёмочного маршрута §7.2 (`main`, `cache3`, `doc50x1000`, `rtt150`, `command-shape`) новые — переходы **1, 2, 4, 6, 8, 10**; в серии `doc5x100` маршрут `[2,3,1,4,2,5,1,3,2,5]` на документе из 5 страниц, и новых там только **1, 2, 4, 6**; в `route-full` новые — **все 49**, возвратов нет вовсе (медиана возвратов пуста); в `route-repeat` — **12 новых и 6 возвратов**. Сколько значений вошло в каждую медиану, видно в `t_nav_new_count` / `t_nav_return_count`. **Следствие: `t_nav_new/return` сравнимы только ВНУТРИ серии** — между сериями с разными маршрутами это медианы по разным наборам переходов |
| `t_nav_return_median_ms` | float | медиана возвратов на уже посещённую страницу. Для маршрута §7.2 — переходы 3, 5, 7, 9; в `doc5x100` — 3, 5, 7, 8, 9, 10 (см. предыдущую строку) |
| `t_cmd_ack_ms` | float | отправка команды → подтверждение сервера с результатом операции (`command-acked`). Как и все `t_cmd_*`, считается по журналу событий страницы (см. врезку «Откуда берутся `t_cmd_*`» ниже) |
| `t_cmd_drawn_ms` | float | отправка команды → **фактическое** обновление холста (`command-drawn`). Фиксируется по отрисовке страницы с ревизией ≥ `expectedRevision+1` и **не ждёт подтверждения**: у Z это значение регулярно МЕНЬШЕ `t_cmd_ack_ms` (ack требует отдельного `GET /api/operations/:opId`). §1.8: «время отсчитывается до фактического обновления холста, подтверждение сервера регистрируется отдельно». Значение — из журнала событий (диспетчеризация `command-drawn`), точный момент отрисовки — `scenario.command_timings[].drawnAt`; разница +0.5 мс медиана, +3.2 мс максимум (врезка ниже) |
| `t_scenario_ms` | float | время сценария с объявленными паузами, **без** накладных расходов оболочки: `t_scenario_wall_ms − probe_overrun_ms`. По нему считается `success` — но **против бюджета серии**, а не против общего порога: бюджет берётся из паспорта (`scenario.budgets.scenarioMs`) и равен 30 000 мс для маршрута §7.2, **40 000** у `route-repeat` и **70 000** у `route-full` (объявленные паузы длинных маршрутов сами по себе дают 18 и 49 с). Границы: от navigationStart до готовности ПОСЛЕДНЕГО действия маршрута; завершающей паузы после него нет — сценарий кончается действием, а не паузой, поэтому объявленных пауз ровно столько же, сколько действий (11 в маршруте §7.2: по одной перед каждым из 10 переходов и одна перед командой) |
| `bytes_in` | int | байт к клиенту по шейперу |
| `bytes_out` | int | байт от клиента по шейперу |
| `cdp_bytes_in` | int | байт к клиенту по CDP `Network.*` (перекрёстная проверка) |
| `js_heap_peak_mb` | float | пик `Runtime.getHeapUsage().usedSize`, МБ. Опрос по таймеру `js_heap_sample_interval_ms` (250 мс, как частная память) плюс по одной пробе на границе каждого шага, снимаемой ДО обращения к странице и ДО сборки мусора. Опрос приостановлен только на время двух точных сканов хранилища и выгрузки снимков — три окна, одни и те же у всех адаптеров (суммарно `js_heap_suspended_ms`), — поэтому копия строк, созданная инструментом, в пик не попадает. Число фактических сэмплов — `js_heap_samples`; расписание принудительных сборок одинаково у всех конфигураций, что подтверждается `js_heap_gc_count` |
| `js_heap_end_mb` | float | `usedJSHeapSize` в момент остановки часов сценария (до выгрузки снимков и заключительного скана хранилища), МБ |
| `chromium_private_peak_mib` | float | пик суммы Private_Clean+Private_Dirty всех процессов Chromium, МиБ. Пусто, если сэмплер не нашёл процессов экземпляра: такой прогон помечен `sampling_incomplete` и учтён как `outcome=error` (память клиента — существенная величина), нуля здесь не бывает |
| `chromium_private_end_mib` | float | та же сумма в конце сценария, МиБ |
| `client_storage_bytes` | int | оценка IndexedDB/localStorage приложения в конце |
| `retained_pages_end` | int | удерживаемые страницы в конце: **точный** подсчёт `getRetainedAsync()` (у Z — скан клиентского хранилища), выполняется после остановки часов сценария. Численно равен `retained_pages_end_exact` — это один и тот же скан в одной и той же точке; сравнивать адаптеры между собой следует по нему |
| `retained_shapes_end` | int | то же для фигур (равен `retained_shapes_end_exact`) |
| `retained_pages_max` | int | максимум по шагам + после команды + конечный. С 2026-09-13 расписание проб одинаково у всех адаптеров (`retained_probe_mode = cached-steps+exact-after-cmd-and-end`): **ни один шаг** точного скана не делает, шаг берёт собственное (кешированное) значение адаптера, а точные сканы остаются ровно в двух точках — после команды и в конце. Поэтому максимум отвечает на вопрос «что адаптер сам считает удержанным» (у H/Q это точный размер `Map`/`queryCache`, у Z — кеш, обновляемый асинхронно после complete/вытеснения); вывод об окне кеша делается по `retained_*_end_exact` |
| `retained_shapes_max` | int | то же для фигур |
| `loaded_pages_end` | int | `getLoadedPages().length` в конце |
| `server_api_cpu_ms` | float | CPU‑время процесса API за прогон, мс |
| `server_api_mem_peak_mib` | float | пик **частной** памяти API (`Private_Clean+Private_Dirty` из `smaps_rollup`; при недоступности `smaps_rollup` — RSS, тогда в записи прогона `mem_fallback_rss`), МиБ. Полный RSS — в служебной `server_api_rss_peak_mib` |
| `server_api_mem_integral_mib_s` | float | ∫ частной памяти API dt, МиБ·с |
| `server_pg_cpu_ms` | float | CPU‑время процессов PostgreSQL, мс |
| `server_pg_mem_peak_mib` | float | пик суммарной частной памяти процессов PostgreSQL, МиБ (RSS — в `server_pg_rss_peak_mib`) |
| `server_pg_mem_integral_mib_s` | float | ∫ частной памяти PostgreSQL dt, МиБ·с |
| `server_zero_cpu_ms` | float | CPU‑время zero‑cache, мс. С 2026-09-13 группа сэмплируется в **каждом** прогоне (§1.2, дефект A8), поэтому в прогонах H/Q здесь **не ноль**, а измеренный фон компонента, который работает на стенде постоянно и нужен только профилю Z. Принадлежность бюджету конфигурации — в `server_zero_applicable`: `true` (прогон Z) — часть серверного бюджета, `false` (H/Q) — фон, к их бюджету не прибавляется. **Пусто** — сэмплер работал и не нашёл ни одного процесса, то есть измерения не было (`sampling_incomplete`; в прогоне Z такой прогон ещё и `outcome=error`). Нуля «по построению» больше нет |
| `server_zero_mem_peak_mib` | float | пик частной памяти zero‑cache, МиБ (RSS — в `server_zero_rss_peak_mib`). В H/Q это измеренный фон, см. `server_zero_applicable`; пусто — не измерено. Величина почти не зависит от адаптера: в `results/main` медианы 603.2–603.4 МиБ у H/Q и 604.4–604.9 у Z (RSS ≈ 929 и ≈ 930), то есть zero‑cache резидентен и в прогонах H/Q — DEVIATIONS 4.2 |
| `server_zero_mem_integral_mib_s` | float | ∫ частной памяти zero‑cache dt, МиБ·с (в H/Q — фон; пусто — не измерено) |
| `zero_replica_bytes` | int | размер каталога реплики zero‑cache на диске. Замеряется в **каждом** прогоне (в программе 2 — 89.9–90.1 МБ во всех 1 014, независимо от адаптера); прежнего «0 для H/Q» больше нет. Реплика содержит базу всего кластера (девять документов), а не измеряемого документа |
| `within_budget_first` | bool | t_first_ready_ms ≤ 2000 |
| `within_budget_nav` | bool | все t_nav_i_ms ≤ 1000 |
| `within_budget_cmd` | bool | t_cmd_drawn_ms ≤ 2000 |
| `within_budget_scenario` | bool | t_scenario_ms ≤ бюджета сценария СЕРИИ (по инструмент‑free значению): 30 000 мс для маршрута §7.2, 40 000 у `route-repeat`, 70 000 у `route-full` — порог объявлен в паспорте (`scenario.budgets.scenarioMs`) и повторён анализом в производной колонке `scenario_budget_ms` |
| `reference_ok` | bool | все проверки эталона (БД + снимки) прошли |

## Необязательные колонки

| Колонка | Смысл |
|---|---|
| `doc_pages` | число страниц документа — для проверки «удержано ≤ окно» в F и абсолютных долей |
| `doc_shapes_per_page` | фигур на страницу — для проверки `retained_shapes_max ≤ (cache+1)·shapes_per_page` |
| `rtt_ms`, `bandwidth_mbps` | параметры шейпера прогона |
| `seed`, `finished_at`, `error_message`, `commit`, `notes` | служебные |
| `t_cmd_server_ms` | отправка → подтверждение мутации **транспортом**: Z — `mutate().server`, H/Q — ответ POST. Без чтения журнала операций |
| `t_cmd_opget_ms` | `t_cmd_ack_ms − t_cmd_server_ms` — цена протокола подтверждения. У H/Q ≈ 0 (результат в теле ответа), у Z — HTTP‑круг `GET /api/operations/:opId` (через шейпер ≈ 60 мс). Именно эта величина раньше молча входила в `t_cmd_drawn_ms` у Z |
| `t_cmd_synced_ms` | отправка → данные команды в клиентском хранилище активной страницы (Z — синхронизация со сверкой содержимого, H/Q — завершённое перечитывание). Отрисовка ещё не выполнена: `t_cmd_drawn_ms − t_cmd_synced_ms` — цена кадра |
| `cmd_drawn_before_ack` | bool: холст обновился раньше подтверждения сервера (норма для Z) |
| `t_scenario_wall_ms` | сырое время сценария: navigationStart → последняя готовность, включая накладные расходы оболочки |
| `probe_overrun_ms` | суммарное превышение объявленных пауз измерительной пробой. Пауза 1 с отсчитывается от готовности предыдущего действия, следующее действие выполняется ровно в `t_ready + 1000` мс (ожидание идёт в часах страницы); если проба не уложилась, разница попадает сюда и вычитается из `t_scenario_ms` |
| `t_scenario_model_ms` | **независимая** реконструкция `t_scenario_ms` по журналу событий страницы (`bench` → `scenarioModelFromJournal`): `t` первого `page-ready` + Σ (`page-ready` − `page-select`) по переходам + (число пауз)·`pauseMs` + (max(`command-acked`, `command-drawn`) − `command-sent`). Слагаемые берутся из событий страницы, а не из бухгалтерии оболочки, поэтому это настоящая сверка: прежняя «модель» складывалась из тех же `t_nav`, из которых вычиталась, и её остаток был нулевым **по построению** (дефект N5) |
| `t_scenario_model_residual_ms` | `t_scenario_ms − t_scenario_model_ms`. В остаток входит время от клика до `page-select` (диспетчеризация) и любое расхождение в сопоставлении событий. Норма — единицы миллисекунд (по данным программы: **3.9–15.1 мс**, медиана 5.2, 95‑й процентиль 6.6; по сериям медианы 5.0–5.3); десятки и больше означают пропущенный шаг, лишний `page-select`, не ту страницу или не ту команду — повод смотреть `events[]` прогона |
| `probe_total_ms` | суммарная длительность измерительных проб (диагностика; в паузах, не в часах сценария) |
| `retained_probe_mode` | политика проб удержания. С 2026-09-13 она ОДИНАКОВА для всех адаптеров, режимов и документов и равна `cached-steps+exact-after-cmd-and-end`: на каждом шаге — только дешёвая проба `getRetained()` (собственное значение адаптера), точный скан `getRetainedAsync()` — ровно в двух фиксированных точках (сразу после команды и в конце, после остановки часов сценария). Прежние значения `exact` / `exact-until-step` (скан на каждом шаге, пока он дешевле порога 150 мс) встречаются только в сериях до этой даты: при них расписание проб и, как следствие, давление сборщика мусора зависели от адаптера (дефекты N2/N4) |
| `retained_pages_end_exact`, `retained_shapes_end_exact` | результат точного скана хранилища в конце прогона — тот же скан и та же точка у всех адаптеров, то есть **сравнимая** между ними величина; по ней и делается вывод об окне кеша. Численно совпадает с `retained_*_end`, но названа отдельно, чтобы сравнение не опиралось на колонку, смысл которой у адаптеров мог бы разойтись |
| `js_heap_samples`, `js_heap_sample_interval_ms` | сколько сэмплов кучи и с каким шагом дали `js_heap_peak_mb` |
| `js_heap_gc_count` | число принудительных `HeapProfiler.collectGarbage` за прогон. Точки вызова фиксированы и не зависят ни от адаптера, ни от режима, ни от вида пробы (после каждой шаговой пробы — 11, после снимка каждого посещения — 11, после пробы вслед за командой, в момент остановки часов, после выгрузки снимков и после заключительного скана) — **26 вызовов** при штатном маршруте. Величина обязана совпадать у всех конфигураций: расхождение означает, что `js_heap_peak_mb` и `chromium_private_peak_mib` измерены при разном давлении сборщика и между адаптерами несравнимы (дефект N2; программа 2 — **26 во всех 564 прогонах** маршрута §7.2, 16 / 28 / 52 на оси `size-fraction-*`, 42 в `route-repeat`, 104 в `route-full`; было ≈13 у H/Q против 2–3 у Z/F) |
| `js_heap_post_gc_mb` | куча сразу после принудительной сборки в фиксированной точке «остановка часов сценария», МБ. В отличие от `js_heap_peak_mb` / `js_heap_end_mb` не зависит от того, когда сборщик решил сработать сам; в пик не входит (опрос на это время приостановлен) |
| `js_heap_suspended_ms` | сколько всего опрос кучи был приостановлен: два точных скана хранилища + выгрузка снимков. Окна одни и те же у всех адаптеров; у Z/F величина больше просто потому, что дороже сам скан (≈25 000 строк) |
| `sampling_incomplete` | перечень сэмплеров (разделены вертикальной чертой), не нашедших ни одного процесса в этом прогоне: `chromium`, `api`, `pg`, `zero`. Пусто = все нужные прогону сэмплеры измеряли реальные процессы. Соответствующие `server_*` / `chromium_*` колонки в такой строке ПУСТЫ, а не нули; если не измерена существенная величина (память Chromium, API или PostgreSQL в любом прогоне, zero‑cache в прогоне Z), прогон записан как `outcome=error` с `error_stage=sampling` и результатом не считается |
| `sampling_ticks` | полнота выборки по каждому сэмплеру: `имя=совпало/ожидалось`, записи разделены вертикальной чертой (например `chromium=54/54` `api=54/54` `pg=54/54` `zero=54/54`). Полнота перестала быть двоичной (дефект N6): группа, найденная лишь в части опросов, публикует заниженные `cpu_ms` и `mem_integral_mib_s`, поэтому при покрытии < 90 % она помечается `<имя>:partial` в `sampling_incomplete`, а если существенна для прогона — прогон записан как ошибочный, а не как «результат» |
| `server_zero_applicable` | входит ли zero‑cache в серверный бюджет адаптера этого прогона. `true` — прогон Z (§1.2: «дополнительный сервер нельзя исключать из бюджета»); `false` — прогон H/Q: группа **сэмплирована**, её расход измерен, но это фон компонента, нужного только профилю Z, и к бюджету H/Q он не прибавляется. Это не «не применимо» и не «не измерено»: неизмеренная величина — пустая ячейка `server_zero_*`. Анализ учитывает колонку в суммах `server_*_total` (вклад zero — только при `true`) и публикует фон отдельно (`server_zero_background_*`) |
| `server_disk_used_bytes` | занято на диске серверной частью на конец прогона: каталог данных PostgreSQL + каталог реплики zero‑cache, байты. §1.7: бюджет 40 ГиБ, порог остановки 32 ГиБ; разложение по каталогам — в записи прогона (`server_disk.dirs`) |
| `route_len`, `route_distinct_pages` | длина маршрута серии (число переходов) и число РАЗНЫХ страниц, которых он касается, включая страницу открытия. Вместе они задают долю документа, которую сценарий вообще просматривает: `main` — 10 переходов и 7 из 50 страниц, `route-repeat` — 18 и 13, `route-full` — 49 и все 50. Без этой пары строка CSV не говорит, что именно измерено, и серии с разными маршрутами нельзя сравнивать осознанно |
| `t_nav_count`, `t_nav_new_count`, `t_nav_return_count` | сколько переходов измерено всего и сколько из них классифицированы как новые / возвраты (по факту посещения, см. `t_nav_new_median_ms`). У маршрута §7.2 — 10/6/4, у `route-full` — 49/49/**0**, у `route-repeat` — 18/12/6. Это знаменатели медиан `t_nav_new/return`: при `t_nav_return_count = 0` медиана возвратов пуста не по ошибке, а потому, что возвратов в маршруте нет |
| `t_nav_median_ms`, `t_nav_ms_list` | медиана ВСЕХ переходов прогона и полный их список через `|`, в порядке маршрута. Нужны длинным маршрутам: колонок `t_nav_1…10` хватает только маршруту §7.2, поэтому у `route-full` (49 переходов) и `route-repeat` (18) суждение о переходах делается по `t_nav_median_ms`, а поэлементная проверка — по `t_nav_ms_list` (там же видно, какой именно переход не уложился в 1 с) |
| `nav_cache_hits`, `nav_cache_misses` | переходы, при которых страница **ещё удерживалась** клиентом перед кликом (`getLoadedPages()` из пробы предыдущего шага), и переходы, при которых её пришлось загружать. Считаются ОДИНАКОВО у H, Q и Z, поэтому промах окна — единственная величина повторной материализации, сравнимая между всеми тремя адаптерами (у Z HTTP‑чтений страниц нет). Промах определяется кешем, а не маршрутом: возврат на вытесненную страницу — одновременно `is_return` и промах (`packages/bench/README.md` §3) |
| `page_loads_observed` | `nav_cache_misses + 1` — загрузок страниц за прогон вместе с открытием документа. В F равно 1: все страницы приходят при открытии, промахов нет по устройству режима |
| `api_page_reads`, `api_page_reads_distinct`, `api_page_read_bytes` | HTTP‑чтения `GET /api/documents/*/pages/*` по CDP: сколько всего, сколько разных страниц и сколько байт в ответах. **У Z это 0 — измерение, а не пропуск**: страницы приходят синхронизацией, и сравнивать его повторные чтения с H/Q можно только через `nav_cache_misses`. У H/Q величина восстанавливает модель перечитывания: `api_page_reads = 1 (открытие) + nav_cache_misses + возвраты на удерживаемую страницу, которую команда пометила устаревшей` — последнее слагаемое и есть цена перечитывания после изменения |
| `cmd_variant`, `cmd_target_id` | вариант команды серии (`variants`, `packages/bench/README.md` §4.2) и фактический `targetId` `setSourceFill`. Пусто в сериях без вариантов. В `command-shape` это `baseline` (81 изменённая фигура на 10 страницах), `concentrated` (81 на 2), `spread` (51 на 50), `large-share` (2001 на 50); анализ включает колонку в ключ конфигурации, поэтому варианты не усредняются друг с другом |
| `wall_ms`, `browser_launch_ms`, `cdp_bytes_out`, `cdp_ws_bytes_in`, `cdp_ws_bytes_out`, `shaper_requests`, `shaper_connections`, `cmd_revision`, `cmd_affected_pages`, `cmd_affected_shapes`, `server_*_rss_peak_mib`, `chromium_processes_peak` | служебные колонки оболочки (`packages/bench/README.md` §5); принимаются валидатором, в отчёт не выносятся |
| `client_transfer_bytes_in`, `client_transfer_bytes_out` | сумма РАСПАКОВАННЫХ тел запросов/ответов в байтах UTF‑8, посчитанная самим клиентом (`window.__stand.transfer`). Не трафик: без заголовков, без WebSocket и без транспортного сжатия — с `bytes_*` (шейпер) и `cdp_bytes_*` не сопоставима |
| `bytes_in_api`, `bytes_in_zero`, `bytes_in_static` | **разложение входящего обмена по назначению** (счётчики шейпера по маршрутам `/api`, `/zero`, `/`): данные API, кадры синхронизации Zero и статика сборки. Статика — поадаптерная КОНСТАНТА (в выполненной программе 260 432 Б у H, 291 444 у Q, 572 562 у Z), одинаковая в F и в P, поэтому в отношении P/F она тянет результат к единице тем сильнее, чем меньше в прогоне данных; `docs/DEVIATIONS.md` §3.1 требует её вычитать. Если колонок нет, анализ восстанавливает их из `shaper.stats.byRoute` в per‑run JSON (`traffic_split_from_runs`) и помечает источник в `traffic_split_source` |
| `bytes_out_api`, `bytes_out_zero`, `bytes_out_static` | то же для исходящего направления |
| `chromium_private_peak_excl_probe_mib` | пик частной памяти Chromium **с исключением окон измерительной пробы** (точный скан хранилища). Сэмплер кучи на время скана приостанавливается, сэмплер `procfs` — исторически нет, а скан после команды у Z/F стоит ≈ 955 мс против 38.7 у H/F и материализует ≈ 25 000 объектов, то есть сырой `chromium_private_peak_mib` у Z содержит инструмент, а не адаптер. Сравнимая между адаптерами величина — эта; сырой пик остаётся рядом. Принимается также синоним `chromium_private_peak_noprobe_mib`, а для конца прогона — `chromium_private_end_excl_probe_mib` (та же политика, но для последней выборки, а не для максимума) |
| `bytes_in_other`, `bytes_out_other` | остаток разложения обмена по маршрутам шейпера: всё, что не попало ни в `/api`, ни в `/zero`, ни в статику сборки (служебные запросы вроде `favicon.ico`, редиректы, ответы вне известных префиксов). В головную величину «данные» **не входит**: `bytes_in_data = bytes_in_api + bytes_in_zero`. В выполненной программе равен 0 во всех 1 014 прогонах, поэтому «данные + статика» исчерпывают весь обмен; ненулевое значение означало бы, что часть обмена осталась неклассифицированной и отношения P/F считаются по неполному разложению |
| `bytes_in_route_residual`, `bytes_out_route_residual` | **контрольная величина**: (`*_api + *_zero + *_static + *_other`) − итог (`bytes_in` / `bytes_out`). Обязана быть нулём в КАЖДОМ прогоне — это доказательство полноты разложения, а не оценка. До 2026‑09‑13 кадры уже открытого WebSocket не относились ни к какому маршруту, и остаток был отрицательным; в выполненной программе он равен 0 везде (проверка — раздел «Обмен данными против полного объёма» в отчёте серии). Ненулевой остаток обесценивает любое число «только данные» |
| `chromium_private_peak_raw_mib` | тот же пик частной памяти Chromium, но по ВСЕМ выборкам `procfs`, включая попавшие в окна измерительных проб. Историческая колонка `chromium_private_peak_mib` оставлена равной ей ради совместимости схемы (проверяется тождеством при чтении), поэтому две эти колонки — одно и то же число под двумя именами, а сравнимая между адаптерами величина — `chromium_private_peak_excl_probe_mib` |
| `chromium_probe_ticks`, `chromium_samples` | сколько выборок сэмплера `procfs` пришлось на окна измерительных проб и сколько выборок было всего за прогон. Отношение `ticks / samples` — доля наблюдений, которые исключены из `chromium_private_peak_excl_probe_mib`: по нему видно, насколько «пик без пробы» опирается на меньшую выборку, чем сырой (у Z доля выше, потому что точный скан хранилища там длиннее) |
| `server_api_mem_peak_excl_probe_mib`, `server_pg_mem_peak_excl_probe_mib`, `server_zero_mem_peak_excl_probe_mib` | пики памяти серверных групп (`api`, `postgres`, `zero-cache`) с исключением тех же окон проб — политика у всех сэмплеров одна. Нужны, чтобы бюджет «сервер ≤ 8 ГиБ» проверялся по величине, не содержащей инструмент; в выполненной программе серверные пики от окон проб практически не зависят (скан идёт в браузере), и совпадение с сырыми пиками — самостоятельная проверка того, что исключение окон не удаляет полезный сигнал |
| `probe_window_count`, `probe_window_ms` | сколько окон измерительных проб было в прогоне и сколько миллисекунд они заняли суммарно. **`probe_window_count` — проверка паритета политики проб**: он обязан совпадать у всех конфигураций серии (в `main` это 14 у всех шести), иначе адаптеры измерены разным инструментом. `probe_window_ms` при этом у адаптеров разная — это измеренное свойство адаптера (точный скан хранилища у Z/F дороже), а не нарушение паритета |
| `js_heap_sampler_coverage` | `js_heap_samples × js_heap_sample_interval_ms / t_scenario_wall_ms` — доля времени прогона, покрытая опросом JS‑кучи. Сэмплер кучи ПРИОСТАНАВЛИВАЕТСЯ на время точного скана и выгрузки снимков, а длительность этих пауз у адаптеров разная, поэтому `js_heap_peak_mb` снят по разному окну наблюдения и читается только вместе с этой колонкой: покрытие 0.79 означает, что пятая часть прогона в пик кучи не попала вовсе |
| `harness_id` | первые 16 символов `passport.harness.harnessId` — идентичность измерительной оболочки (sha256 по `packages/bench/src/**`, `packages/netshaper/src/**`, конфигурации серии и набору колонок), продублированная в каждую строку CSV. **Различается у разных серий по построению**, потому что включает конфигурацию серии; сопоставимость абсолютных величин задаёт не он, а `passport.harness.comparableBy` (`benchId`, `benchSrcSha256`, `netshaperSrcSha256`, `columnsSha256`, `referenceSha256`) — у всех одиннадцати серий выполненной программы они совпадают |

### Откуда берутся `t_cmd_*` (и чем они отличаются от `command_timings[]`)

Все колонки `t_cmd_ack_ms`, `t_cmd_drawn_ms`, `t_cmd_server_ms`, `t_cmd_synced_ms` считаются оболочкой
**по журналу событий страницы**: `t` события (`command-acked` / `command-drawn` / `command-server` /
`command-synced`) минус `t` события `command-sent`, где `t = performance.now()` в момент
**диспетчеризации** события (`packages/bench/src/scenario/acceptance.mjs`, `emit` в
`packages/client/src/stand.ts`). Это НЕ `drawnInfo.at` и не поля `timing.*`: сам клиент фиксирует
момент отрисовки во втором `requestAnimationFrame` после `draw()` и кладёт его в
`scenario.command_timings[]` (`sentAt`, `serverAt`, `syncedAt`, `ackedAt`, `drawnAt`, `opGetMs`) —
**это и есть точный источник**, если нужны моменты без накладных расходов диспетчеризации.

Расхождение между CSV и `command_timings[]` измерено по прогонам выполненной программы
(4 величины на прогон): смещение **равномерное и положительное, медиана +0.5 мс,
максимум +3.2 мс** (минимум +0.2). По адаптерам оно одинаково — медианы 0.40–0.50 мс у H, Q и Z
(`t_cmd_drawn`: 0.50 / 0.50 / 0.50; максимум +3.2 мс — один прогон Z), поэтому на сравнение
адаптеров не влияет и на бюджет команды (2 000 мс) не влияет тем более. Если нужна точность лучше
миллисекунды — брать `command_timings[]` из записи прогона, а не колонки CSV.

**Чего в CSV сознательно нет.** `RetainedStats.bytesEstimate` (= `shapes × 200 Б`) — СИНТЕТИЧЕСКАЯ константа,
одинаковая для всех адаптеров и не зависящая от фактического представления строк (`Map`, `queryCache`,
b‑tree Zero). В записи прогона она доступна как `steps[].retained_bytes_synthetic`, но метрикой памяти
не является и в отчёт как память не выносится; память клиента — только `chromium_private_*`, `js_heap_*`
и `client_storage_bytes`.

## Производные (считает анализ, в CSV не пишутся)

`scenario_budget_ms` — бюджет сценария СЕРИИ, прочитанный из паспорта (`scenario.budgets.scenarioMs`)
и по умолчанию равный 30 000 мс (§7.4). По нему считаются `success` и бюджет «сценарий в пределах порога»,
поэтому у `route-repeat` (40 000) и `route-full` (70 000) отчёт проверяет их собственный порог и называет его
в заголовке таблицы. Проверять длинный маршрут порогом 30 с нельзя: объявленные паузы §1.2 дают там 18 и 49 с
сами по себе.

`server_cpu_ms_total`, `server_mem_peak_mib_total`, `server_mem_integral_mib_s_total` — серверные суммы
**бюджета конфигурации**: слагаемое zero‑cache входит в них только там, где `server_zero_applicable=true`
(прогоны Z). В прогонах H/Q измеренный расход zero‑cache — фон, он публикуется отдельными производными
`server_zero_background_cpu_ms` и `server_zero_background_mem_peak_mib`. Если колонки `server_zero_applicable`
в серии нет (до 2026-09-13, когда `server_zero_*` были нулями по построению), суммы считаются по‑старому.
Также `bytes_total` и `success` = `outcome=='ok' ∧ t_scenario_ms ≤ scenario_budget_ms ∧ reference_ok`.

`bytes_in_data` / `bytes_out_data` — **обмен данными**: `*_api + *_zero`, то есть весь обмен, кроме статики
сборки. Это ГОЛОВНАЯ величина обмена во всех таблицах и во всех отношениях P/F; полный `bytes_in`
печатается рядом как проверочный, а размер статики — отдельной строкой, чтобы разницу можно было
восстановить. Если оболочка пишет только `bytes_in_static`, данные считаются вычитанием;
`traffic_split_source` говорит, откуда взято разложение (`columns` — колонки оболочки, `runs-json` —
восстановлено из счётчиков шейпера в записях прогонов, пусто — разложения нет и таблицы «только данные»
не строятся).

## Per‑run JSON (необязательно, для графика удержания по шагам)

`results/<series>/runs/<run_id>.json`:
```json
{"run_id": "...", "adapter": "H", "mode": "P", "cache": 1,
 "steps": [{"step": 0, "action": "open", "page_id": "p1", "t_ms": 812, "retained_pages": 1, "retained_shapes": 500, "loaded_pages": 1},
           {"step": 1, "action": "nav", "page_id": "p2", "t_ms": 410, "retained_pages": 2, "retained_shapes": 1000, "loaded_pages": 2}]}
```
Также принимается `retained: {pages, shapes}` вместо плоских полей.

Дополнительно в `scenario`: `command_timings[]` — моменты каждой команды в часах страницы
(`sentAt`, `clientAt`, `serverAt`, `syncedAt`, `ackedAt`, `drawnAt`, `opGetMs`, `targetRevision`),
то есть метрики команды восстановимы по сырым данным без пересчёта (**это точный источник**, см.
врезку «Откуда берутся `t_cmd_*`»); `heap_sampler`
(`peak_mib`, `samples`, `interval_ms`, `suspended_ms`); `retained_probe`; а в `steps[]` —
`probe_ms`, `probe_overrun_ms`, `retained_source`, `retained_bytes_synthetic`.

В корне записи прогона — `sampling` (по каждому сэмплеру: `matched`, `essential`, причина отсутствия
совпадений) и `server_disk` (`dirs`, `total_bytes`, `budget_bytes`): по ним видно, какие колонки пусты
потому, что величина не измерялась.
