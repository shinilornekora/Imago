# packages/analysis — анализ результатов измерений

Python‑пакет для SPEC §7.5: читает `results/<series>/runs.csv` (+ необязательные
per‑run JSON и `passport.json`), считает медианы, p95, бутстреп‑интервалы, долю
успеха с интервалом Уилсона, изменение метрик **внутри адаптера** (P−F, P/F) и
сопоставление этого изменения **между адаптерами**, проверяет бюджеты §7.4 и
соответствие удерживаемых записей объявленному окну кеша; выпускает Markdown‑отчёт
и PNG‑графики.

## Установка и тесты

```bash
cd packages/analysis
pip install -r requirements.txt     # numpy 2.4.4, pandas 3.0.2, matplotlib 3.10.9, pytest 9.1.1
python -m pytest                    # тесты на синтетической серии с известными распределениями
```

scipy не требуется: бутстреп и интервал Уилсона реализованы на numpy.

## Вход: схема `runs.csv`

Список колонок зафиксирован в `analysis/schema.py` (`REQUIRED_COLUMNS`) и
продублирован в [`COLUMNS.md`](COLUMNS.md) (генерируется из схемы:
`python -c "from analysis.schema import columns_markdown; print(columns_markdown())"`).
Измерительная оболочка (`packages/bench`) должна писать ровно эти имена; проверка:

```bash
python -m analysis.report --series results/main --validate-only
# OK — rows=180            либо
# INVALID — rows=180; MISSING required columns: t_cmd_drawn_ms, reference_ok; outcome: unexpected values ['crashed'] ...
```

Необязательные колонки (`doc_pages`, `doc_shapes_per_page`, `rtt_ms`, …) используются, если есть;
неизвестные — игнорируются с предупреждением. Пустая ячейка = метрика не измерена
(например, прогон с `outcome=error`). Ошибки и таймауты не отбрасываются: они входят
в таблицу исходов и в долю успеха, но исключаются из сводок времени/памяти.

Per‑run JSON (`results/<series>/runs/<run_id>.json` с полем `steps`) даёт график
удерживаемых фигур по шагам сценария; формат — в `COLUMNS.md`.

## CLI

```bash
python -m analysis.report --series results/main --out docs/results/RESULTS_main.md --figs docs/results/figs/main
python -m analysis.report --series results/main --out docs/results/RESULTS_main.md --figs docs/results/figs/main \
       --compare results/cache3,results/route-repeat,results/rtt150      # прочие серии программы 2
python -m analysis.report --series results/main --validate-only        # только схема (136 колонок)
python -m analysis.report --series results/command-shape --out docs/results/RESULTS_command-shape.md --figs docs/results/figs/command-shape
python -m analysis.report --series results/archive/main-preliminary-56runs --out /tmp/old.md --lenient   # архивная серия (79 колонок вместо нынешних): --lenient строит отчёт, даже если обязательной колонки нет
python -m analysis.synth  --out results/synthetic --runs 30            # синтетическая серия для «сухого» прогона

# сквозная проверка СЫРЫХ данных перед публикацией: CSV против записей прогонов, параметры
# шейпера против паспорта, полнота разложения обмена, шейпер против CDP (HTTP+WS), удержание
# против независимой модели LRU, паритет окон проб, идентичность оболочки. Код возврата 1 при
# любом расхождении, расхождения названы поимённо.
python -m analysis.verify --series ../../results/main,../../results/route-repeat  [--quiet]

# перекрёстное сравнение серий по осям главы 1 (окно кеша — в том числе на маршруте, где оно
# связывает; размер документа; доля просмотренного документа; форма команды; RTT)
SERIES=main=../../results/main,size-fraction-25x500=../../results/size-fraction-25x500,\
size-fraction-50x500=../../results/size-fraction-50x500,size-fraction-100x500=../../results/size-fraction-100x500,\
route-repeat=../../results/route-repeat,command-shape=../../results/command-shape,route-full=../../results/route-full,\
rtt150=../../results/rtt150,doc50x1000=../../results/doc50x1000,doc5x100=../../results/doc5x100,cache3=../../results/cache3

python -m analysis.cross --series "$SERIES" \
       --out ../../docs/results/RESULTS_cross.md --figs ../../docs/results/figs/cross

# числовая опора итогового отчёта: все ОДИННАДЦАТЬ серий (1 014 прогонов) в одной таблице на показатель
python -m analysis.summary --series "$SERIES" --out ../../docs/results/SUMMARY.md
```

Параметры: `--seed` (по умолчанию 42), `--n-boot` (2000), `--lenient` (строить отчёт даже при
отсутствии обязательных колонок — результат проверки схемы попадает в шапку отчёта). Коды возврата:
0 — отчёт построен; 1 — `--validate-only` нашёл проблемы; 2 — файл не найден / схема невалидна.

**Контролируемая ось «размер документа при фиксированной доле посещения».** Простая ось размера
(`doc5x100` → `main` → `doc50x1000`) меняет размер и долю посещения ВМЕСТЕ, поэтому раздельного
эффекта размера в ней нет — `analysis.cross` печатает обе величины рядом (§3.4) и говорит об этом
прямо. Контролируемый ответ даёт §3.5: раздел и графики `sizefrac_*.png` строятся **автоматически**
по сериям, чьи имена начинаются на `size-fraction` (в программе 2 это `size-fraction-25x500`,
`-50x500`, `-100x500`: 12 500 / 25 000 / 50 000 фигур при доле посещения 12 % и размере страницы
500 фигур). Порядок на оси — по числу фигур документа; доля посещения берётся из маршрута в паспорте
каждой серии и **проверяется на совпадение**: если доли разошлись, раздел печатает предупреждение,
что ось снова смешивает размер с маршрутом, и читать её как эффект размера нельзя.

**Сопоставимость серий.** Оболочка объявляет собственный критерий — список полей
`passport.harness.comparableBy` (`benchId`, `benchSrcSha256`, `netshaperSrcSha256`, `columnsSha256`,
`referenceSha256`). `analysis.cross` и `analysis.summary` сверяют именно его
(`schema.harness_comparable_signature`) и печатают результат явным абзацем: совпал — «абсолютные
величины между сериями сопоставимы», разошёлся — какие серии в какой группе. **`harnessId` для этого
не годится**: он дополнительно включает конфигурацию серии и потому у разных серий различается
закономерно; в таблице состава он печатается отдельным столбцом рядом с `benchId`. Если паспорт
`comparableBy` не несёт (серии из `results/archive/**`), проверка откатывается на
`schema.harness_identity` и печатает, что сравнимость **не проверена**.

## Что в отчёте (Markdown, русские заголовки)

1. Паспорт серии (`passport.json`) — как есть, поэтому недостающие ключи (`adapters`, `client.buildId`,
   `commit`, …; полный список — `docs/PASSPORT.md` §2.1) видны сразу.
2. Состав серии и доля успеха по конфигурациям с интервалом Уилсона 95 %
   (успех = `outcome=ok` ∧ `t_scenario ≤ бюджета СЕРИИ` ∧ `reference_ok`), отдельной колонкой —
   прогоны `outcome=ok`, у которых эталон не сошёлся (§1.8 требует допуска по эталону до сравнения).
   Бюджет сценария читается из паспорта (`scenario.budgets.scenarioMs`, функция
   `schema.scenario_budget_ms`) и по умолчанию равен 30 000 мс: у `route-repeat` он 40 000, у
   `route-full` — 70 000, потому что объявленные паузы §1.2 дают там 18 и 49 с сами по себе.
   Фактический порог печатается в заголовке таблицы бюджетов и в колонке `scenario_budget_ms`.
3. Сводные показатели: для каждой метрики — n, медиана **и** p95, **каждый со своим 95 %
   бутстреп‑интервалом**, min, max (время; трафик; память клиента; удерживаемые записи; сервер).
   **Обмен считается по данным.** Головная величина — `bytes_in_data` (API + кадры синхронизации
   Zero) без статики сборки: статика — поадаптерная константа, одинаковая в F и в P, и в отношении
   P/F она тянет результат к единице (`docs/DEVIATIONS.md` §3.1). Полный `bytes_in` печатается
   рядом как проверочный, размер статики — отдельной строкой, а подраздел «Обмен данными против
   полного объёма» показывает оба отношения и столбец «изменилось» — то есть прямо называет, какие
   головные числа двигает вычитание статики. Разложение берётся из колонок оболочки
   (`bytes_in_api` / `bytes_in_zero` / `bytes_in_static`), а если их нет — восстанавливается из
   `shaper.stats.byRoute` в per‑run JSON; источник печатается в отчёте (`traffic_split_source`).
   Пик частной памяти Chromium: если оболочка пишет `chromium_private_peak_excl_probe_mib` (пик без
   окон измерительной пробы), головной становится эта колонка, а сырой пик остаётся рядом.
   **Полнота разложения проверяется поПРОГОННО** (`stats.traffic_decomposition_check`): сумма
   `api + zero + static + other` сверяется с итогом `bytes_in`/`bytes_out` с точностью до байта, и
   рядом печатается собственный контрольный остаток оболочки `bytes_*_route_residual` — головное
   число «только данные» осмысленно ровно настолько, насколько разложение полное.
   **Окна измерительных проб** (`stats.probe_parity_check`): число окон (`probe_window_count`)
   обязано совпадать у всех конфигураций серии, иначе адаптеры измерены разным инструментом; рядом —
   насколько сырой пик выше пика без проб, доля выборок, попавших в окна, и покрытие сэмплера
   JS‑кучи (`js_heap_sampler_coverage`), без которого пик кучи между адаптерами не читается.
4. **Моменты команды** (§1.2, §1.8): `t_cmd_ack` и `t_cmd_drawn` по отдельности, их разность внутри
   прогона (настоящая пара) с интервалом, доля прогонов с `drawn < ack` и доля вырождения `drawn = ack`
   (±0.5 мс — признак того, что одно событие выпускается из обработчика другого, а не результат).
   При наличии колонок — разложение времени команды у Z: `t_cmd_server_ms`, `t_cmd_synced_ms`,
   `t_cmd_opget_ms`.
5. Бюджеты §1.2 — матрица «конфигурация × бюджет» и итог: first‑ready ≤ 2 с, переход ≤ 1 с,
   команда до **актуального холста** ≤ 2 с (медианы), сценарий в пределах бюджета серии в ≥ 95 % **начатых** прогонов
   (с интервалом Уилсона), Chromium ≤ 768 МиБ (медиана и максимум пика), сервер ≤ 4 vCPU
   (медиана CPU‑мс/мс сценария), ≤ 8 ГиБ, диск ≤ 40 ГиБ, эталон совпал во всех проверенных прогонах.
   **Вердикт трёхзначный и всегда назван явно**: `✓`/`✗` — точечная оценка, а рядом знак по
   интервалу — пусто (интервал целиком по нужную сторону порога), `≈` (интервал порог накрывает,
   данные вопрос не решают) или `!` (интервал порог исключает). **Нарушение бюджета объявляется
   только при `!`**; итоговая таблица разделяет «точечно вне бюджета», «нарушение подтверждено
   интервалом» и «не решено». Медиана перехода считается по `t_nav_ms_list` (все переходы
   маршрута), а не по первым десяти колонкам; отдельной справочной строкой печатается худший
   одиночный переход и число прогонов с `within_budget_nav=false` — §1.2 задаёт бюджет перехода
   медианой, но умолчать о таких прогонах нельзя.
6. Изменение внутри адаптера, P − F и P / F, с объёмом выборки при каждом числе (`†` — n < 8,
   интервал ненадёжен; `‡` — n < 30, меньше, чем требует §1.8) и со **знаковым критерием** рядом с
   бутстрепом (точный двусторонний критерий знаков по поблочным разностям: при 6 парах одного знака
   p = 0.031 — устойчивая проверка там, где интервал по шести точкам сам по себе ненадёжен).
   В двух видах:
   * **6.1 парный (блочный)** — основной: разность берётся внутри блока повторения, точечная оценка —
     медиана поблочных разностей и отношений, интервал — бутстреп по блокам;
   * **6.2 непарный** — разность и отношение медиан при независимом ресемплинге.
   Если парность невозможна (нет `repetition`, мало общих блоков), раздел 6.1 печатает причину.
7. Сопоставление между адаптерами (§1.8) — так же в двух видах: 7.1 на общих блоках, 7.2 непарно.
8. Удерживаемые записи против объявленного окна: в P — `retained_pages_max ≤ cache + 1`
   (и `retained_shapes_max ≤ (cache+1)·shapes_per_page`, если известно), в F — все страницы документа.
9. Ошибки, прерывания и **выбросы**: прогоны за границей `Q3 + 3·IQR` внутри своей конфигурации
   называются поимённо вместе с медианой и p95 «с ними и без них». Ни один такой прогон не
   отбрасывается (§1.7); таблица показывает вклад одного прогона, а не исправляет данные.
10. **Полнота данных**: какие необязательные метрики серия уже пишет, каких нет и какие колонки схемой
    вообще не описаны. Нужно, чтобы смена семантики оболочки была видна, а не тихо проигнорирована.
11. Графики (PNG): по одному на метрику — первая готовность, переход новая/возврат, команда до холста,
    трафик, пик частной памяти Chromium, JS‑куча, удерживаемые фигуры, CPU и память сервера —
    сгруппированные столбцы по адаптерам, F и P рядом, планки = бутстреп‑интервал медианы, пунктир = бюджет;
    плюс точечный график удерживаемых фигур по шагам (если есть per‑run JSON).
12. Сравнение серий (при `--compare`): таблицы медиан по конфигурациям и графики.
13. Выводы: какие конфигурации укладываются во все бюджеты, подтверждённые интервалами изменения P/F,
    нарушения окна кеша, результат перекрёстной проверки обмена, вырождение моментов команды,
    замечание об объёме серии (нижняя граница Уилсона достигает 95 % без единого отказа только при
    n ≥ 73), условия применимости частичной загрузки.

## Определения статистик

Чтобы число нельзя было прочитать двояко, определения зафиксированы в коде (`analysis/stats.py`) и
повторены в шапке каждого отчёта:

* **p95** — перцентиль по линейной интерполяции порядковых статистик (`numpy.percentile`, тип 7).
  При n = 30 это интерполяция между 29‑м и 30‑м значением ряда, поэтому p95 не превышает максимум
  выборки и при малых n смещён вниз относительно истинного 95‑го перцентиля. Определение «ближайший
  ранг» дало бы при n = 30 ровно максимум — это другое число, и смешивать их нельзя.
* **Интервалы медианы и p95** — перцентильный бутстреп (2000 ресемплов) по **одной** матрице ресемплов,
  поэтому они согласованы между собой. При n = 1 интервал не строится (`—`), при n < 8 помечается †
  как ненадёжный: выдавать `[x; x]` за 95 % интервал — вводить читателя в заблуждение.
* **Доли** — интервал Уилсона 95 % без поправки на непрерывность, по **всем начатым** прогонам
  конфигурации: ошибка и таймаут считаются неуспехом.
* **Ключ конфигурации** — `(adapter, mode, cache, doc, cmd_variant)`. `cmd_variant` входит в ключ
  только в сериях с вариантами команды (`packages/bench/README.md` §4.2); подпись конфигурации
  получает хвост `[вариант]` (`Z/F [large-share]`), и варианты никогда не усредняются друг с другом
  — ни в сводках, ни в бюджетах, ни в парных P−F.
* **Сводки времени и ресурсов** — только по прогонам `outcome=ok`. Прогоны `error`/`timeout` не
  отбрасываются молча: они входят в доли, в раздел ошибок и в бюджет «сценарий в пределах бюджета серии».
* **Детерминированность** — seed каждой группы выводится из `--seed` и ключа группы, поэтому результат
  не зависит от порядка обработки и воспроизводится повторным запуском.

## Парный анализ: почему по повторениям

Раннер выполняет каждое повторение как **блок**: в одном повторении ровно по одному прогону каждой
конфигурации серии, порядок внутри блока перемешан seeded‑PRNG, перед каждым прогоном — сброс документа
и новый процесс Chromium (`packages/bench/src/series/plan.mjs`, `docs/PASSPORT.md` §6). Поэтому
`repetition` — законный блокирующий фактор: прогоны одного блока выполнены в одном «окне» состояния
машины, и разность P − F внутри блока снимает медленный дрейф между блоками (прогрев, фоновая нагрузка,
рост реплики).

Чего парность не даёт и что отчёт говорит прямо: прогоны блока разнесены во времени на минуты и идут в
разном порядке — это блок, а не одновременное измерение, и эффект позиции внутри блока не снимается.
Пара, в которой хотя бы один прогон не `ok`, отбрасывается целиком (число отброшенных публикуется),
поэтому при несимметричных отказах парная и непарная оценки считаются по разным подмножествам.
Обе печатаются рядом: расхождение между ними и есть мера чувствительности вывода к дрейфу и к выпавшим
прогонам.

## Чего анализ ждёт от оболочки

Необязательные колонки: отсутствующие пропускаются, присутствующие попадают в отчёт, а раздел «Полнота
данных» перечисляет и те и другие. Список известных анализу необязательных метрик — `stats.OPTIONAL_METRICS`.

| Колонка | Зачем нужна |
|---|---|
| `cdp_ws_bytes_in` / `cdp_ws_bytes_out` | перекрёстная проверка обмена у Z: шейпер сравнивается с **суммой** HTTP и WebSocket; без них проверка даёт ложный провал |
| `t_cmd_server_ms`, `t_cmd_synced_ms`, `t_cmd_opget_ms` | разложить время команды у Z на «сервер выполнил», «клиент увидел синхронизированную ревизию» и «стоимость чтения журнала операций»; без них вклад лишнего HTTP‑круга по сырым данным не восстанавливается |
| `t_scenario_wall_ms`, `t_scenario_model_ms`, `probe_overrun_ms`, `probe_total_ms` | отделить время сценария от накладных расходов измерительной пробы |
| `js_heap_samples`, `js_heap_sample_interval_ms` | понять, пик это или максимум редкой выборки |
| `server_disk_used_bytes` | проверить бюджет §1.2 «40 ГиБ» по всей серверной конфигурации, а не по одной реплике zero‑cache |
| `repetition` | блок для парного анализа (§1.8) |
| `route_len`, `route_distinct_pages`, `t_nav_count`/`t_nav_new_count`/`t_nav_return_count` | понять, какую долю документа трогает маршрут и по скольким значениям посчитаны медианы новых/возвратов |
| `t_nav_median_ms`, `t_nav_ms_list` | суждение о переходах на маршрутах длиннее десяти (колонок `t_nav_1…10` не хватает) |
| `nav_cache_hits`, `nav_cache_misses`, `page_loads_observed` | сравнимая между H, Q и Z мера повторной материализации страниц |
| `api_page_reads`, `api_page_reads_distinct`, `api_page_read_bytes` | восстановить модель перечитывания и байтов у H/Q; у Z это измеренный ноль |
| `cmd_variant`, `cmd_target_id` | разделить серию по вариантам команды, чтобы 81 изменённая фигура не усреднялась с 2 001 |
| **`bytes_in_api`, `bytes_in_zero`, `bytes_in_static`** (и `_out`) | считать обмен **по данным**: статика сборки — поадаптерная константа (260 432 / 291 444 / 572 562 Б), одинаковая в F и в P, и `DEVIATIONS` §3.1 требует её вычитать. Пока колонок нет, анализ восстанавливает разложение из `shaper.stats.byRoute` в per‑run JSON (читается только голова файла), но это резервный путь: колонки надёжнее и не зависят от сохранности журналов |
| **`chromium_private_peak_excl_probe_mib`** (синоним `chromium_private_peak_noprobe_mib`) | пик частной памяти **без окон измерительной пробы**: сэмплер `procfs` не приостанавливается на время точного скана, а скан у Z/F стоит ≈ 955 мс, поэтому сырой пик у Z содержит инструмент. При наличии колонки она становится головной, сырой пик печатается рядом |
| **`bytes_in_other`, `bytes_out_other`, `bytes_in_route_residual`, `bytes_out_route_residual`** | проверить, что разложение обмена ПОЛНОЕ: «прочее» — маршруты вне `/api`, `/zero` и статики, а остаток обязан быть нулём в каждом прогоне. Без них «только данные» — величина, недосчитанная на неизвестный остаток |
| **`chromium_private_peak_raw_mib`, `chromium_probe_ticks`, `chromium_samples`** | сырой пик под собственным именем (историческая `chromium_private_peak_mib` равна ему) и доля выборок, исключённых из пика без проб: по ней видно, на насколько меньшей выборке стоит головная величина |
| **`probe_window_count`, `probe_window_ms`** | паритет политики проб: число окон обязано совпадать у всех конфигураций серии, иначе пики памяти между адаптерами несравнимы. Длительность окон различается законно — это свойство адаптера |
| **`js_heap_sampler_coverage`** | доля времени прогона, покрытая опросом JS‑кучи. Сэмплер кучи приостанавливается на время точного скана, и у Z/F покрытие падает до 0.57–0.79 — пик кучи там снят по меньшему окну и занижен |
| **`server_*_mem_peak_excl_probe_mib`** | серверные пики памяти с той же политикой исключения окон проб: бюджет «≤ 8 ГиБ» должен проверяться по величине без инструмента |
| **`harness_id`** (строка) | идентичность оболочки в каждой строке CSV; сверяется с `passport.harness.harnessIdShort` |
| **`harness` в паспорте** (или `code.benchId`) | хеш измерительной оболочки (`packages/bench/src/**`, конфигурация серии, скрипты эталона). Без него межсерийная сопоставимость абсолютных величин **не проверяется**, и отчёты печатают об этом предупреждение: `packages/bench` между половинами выполненной программы менялся |

Если оболочка переименует или перестанет писать **обязательную** колонку, `--validate-only` сообщит об
этом, а `--lenient` позволит всё равно собрать отчёт, чтобы было видно, что именно изменилось.

## Допущения

* Сводки времени/ресурсов считаются только по прогонам `outcome=ok`; доли — по всем прогонам.
* Бюджет «сервер ≤ 4 vCPU» трактуется как медиана средней загрузки за прогон:
  `(server_api_cpu_ms + server_pg_cpu_ms + server_zero_cpu_ms) / t_scenario_ms ≤ 4`.
  На машине с 2 vCPU (`docs/DEVIATIONS.md` 1.3) это фактически «не более 2 доступных ядер».
* Бюджет «диск ≤ 40 ГиБ» §1.2 относится ко всей серверной конфигурации. Оболочка пишет
  `server_disk_used_bytes` (в прогонах основной серии он заполнен — `server_disk.total_bytes`), а по
  прогонам Z дополнительно `zero_replica_bytes`. Полная занятость до и после серии контролируется
  скриптом `scripts/replication-check.sh`, раздел `[3]` (`docs/PASSPORT.md` §8.1–8.2).
* Перекрёстная проверка обмена: вердикт ставится по **входящему** направлению (шейпер против суммы
  `cdp_bytes_in + cdp_ws_bytes_in`, допуск 10 %). Исходящее — справочно с допуском 50 %: `cdp_bytes_out`
  не измеряется, а оценивается по `Network.requestWillBeSent` и систематически занижен на заголовки,
  добавляемые сетевым стеком браузера, и на рукопожатие WebSocket (наблюдаемое расхождение 20–40 %).
* Бюджет Chromium проверяется по медиане пика (итоговая отметка) и дополнительно показывается максимум.
* Ключ конфигурации — `(adapter, mode, cache, doc)`; в F значение `cache` не влияет на подпись.
* `t_nav_new_median_ms` / `t_nav_return_median_ms` считает измерительная оболочка по факту
  посещения, поэтому набор переходов зависит от маршрута серии (в §7.2 это 1,2,4,6,8,10 и 3,5,7,9;
  в `route-full` новых 49 и возвратов 0). Бюджет перехода проверяется по объединённой медиане всех
  `t_nav_i_ms` и отдельно по новым/возвратам; у маршрутов длиннее десяти переходов колонок
  `t_nav_1…10` не хватает, и полная медиана берётся из `t_nav_median_ms`.
* Маршрут и повторные чтения (`route_len`, `nav_cache_hits/misses`, `page_loads_observed`,
  `api_page_reads*`) выводятся в отдельный раздел отчёта 3.4.1 и в ось «доля документа»
  перекрёстного отчёта. У Z `api_page_reads = 0` — это измерение (страниц по HTTP он не читает), а
  не пропуск.
