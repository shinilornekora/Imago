## 1. Подготовка стенда

```bash
export PATH=/opt/node24/bin:$PATH PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers
# PostgreSQL, API (STAND_TEST_HOOKS=1), zero-cache — см. scripts/
node packages/netshaper/bin/netshaper.mjs --listen 8080 \
  --routes '/api=127.0.0.1:3000,/zero=127.0.0.1:4848,/=127.0.0.1:3000' \
  --delay-ms 25 --bandwidth-mbit 20 --stats-port 8081     # --handshake-rtt включён по умолчанию
```

Шейпер (`packages/netshaper/README.md`): весь трафик клиента идёт через `http://127.0.0.1:8080`,
счётчики байт и параметры канала — `http://127.0.0.1:8081/{stats,reset,config}`.

**Задержка установления соединения включена.** Каждое новое клиентское соединение платит один RTT
до первых байтов запроса (HTTP и WebSocket одинаково). Без неё соединение бесплатно, и конфигурации,
открывающие их больше (H/Q в F — ≈8 соединений и ≈70 запросов на прогон против одного WebSocket у Z),
получают незаслуженное преимущество (дефект A6/B22). Раннер выставляет флаг перед **каждым** прогоном
(`series.shaper.handshakeRtt`, по умолчанию `true`) вместе с delay и полосой, а `passport.json →
shaper.effective.handshakeRtt` фиксирует фактическое значение серии.

## 2. Сэмплеры

```js
import { startProcSampler } from './src/sampling/procs.mjs';
const s = startProcSampler({ intervalMs: 250, groups: [
  { name: 'api',  patterns: ['node .*packages/server'], exclude: ['netshaper'] },
  { name: 'pg',   patterns: ['postgres'] },                    // backend'ы — потомки postmaster'а, находятся по ppid
  { name: 'zero', patterns: ['zero-cache'], dir: '/tmp/zero-replica' },
]});
… const summary = s.stop();   // {api: {cpu_ms, cpu_user_ms, cpu_sys_ms, mem_peak_mib, mem_end_mib, mem_integral_mib_s, rss_peak_mib, disk_*_bytes, pids, samples[], …}, …}
```

* CPU — `utime+stime` из `/proc/<pid>/stat` (jiffies → мс через `CLK_TCK`), Σ по всем процессам
  группы, когда‑либо виденным за прогон (короткоживущие backend'ы не теряются).
* Память — `Private_Clean+Private_Dirty` из `/proc/<pid>/smaps_rollup` (fallback RSS из `stat`,
  флаг `mem_fallback_rss`); интеграл — Σ private·Δt по фактическим интервалам (МиБ·с).
* Группы взаимоисключающие в порядке объявления. Дерево процессов самой оболочки (её
  shell‑предки и потомки, т. е. Chromium) исключается всегда, если у группы не задано
  `allowSelfTree: true` (нужно только тестам, где фейковый сервер — дочерний процесс).
  `--dry-run` серии печатает, какие процессы сейчас попадают в каждую группу — проверяйте
  паттерны перед серией (в песочнице могут работать посторонние `zero-cache`/`node` процессы).
* Chromium: `startChromiumSampler(browser)` — главный pid (через внутренний объект Playwright,
  fallback — поиск потомка с маркером `--stand-run=<id>` в `/proc`) + все потомки; `attachCdp(page)`
  — `Runtime.getHeapUsage` (fallback `performance.memory`) и счётчики `Network.*`.

## 3. Приёмочный сценарий (§7.2)

```bash
node src/scenario/cli.mjs --base http://127.0.0.1:8080 --adapter H --mode P --cache 1 \
     --doc <docId> --source <sourceId> --fill '#ff8800' --out run.json
```

Открыть `/?adapter&mode&cache&doc&page=1&autologin=alice`; ждать `page-ready` страницы 1
(`t_first_ready` = `t` события, часы страницы отсчитываются от navigationStart); далее
10 переходов `2,3,1,4,2,5,1,6,3,50`: клик по `[data-page-index=k]`, ожидание `page-ready` этой
страницы → `t_nav[i]`; после 5‑го перехода — `window.__stand.runCommand({type:'setSourceFill',
targetId, fill})`, ожидание `command-drawn` и `command-acked` → `t_cmd_drawn`, `t_cmd_ack`
(плюс необязательные `command-server` и `command-synced` → `t_cmd_server`, `t_cmd_synced`,
`t_cmd_opget = t_cmd_ack − t_cmd_server`). В конце — снимки `getPageSnapshot()` всех посещённых
страниц (в P вытесненные дают `null`), `navigator.storage.estimate()`, `getCommandTimings()`,
журнал `events`, ошибки консоли. Все моменты — из журнала страницы, не из часов оболочки.

**Маршрут — параметр произвольной длины.** `scenario.route` задаёт любую последовательность
1-based индексов страниц: приёмочный маршрут §7.2 (10 переходов), `route-full` (49 переходов 2→50),
`route-repeat` (18 переходов с возвратами). Всё, что зависит от длины, считается от `route.length`:
число объявленных пауз, число снимков посещений, расписание принудительных сборок мусора
(`js_heap_gc_count` = 2·(route+1)+4 — 26 для маршрута §7.2, 104 для `route-full`) и номер шага
команды (`cmdAfterStep` отсчитывается от начала маршрута). Колонок `t_nav_1…10` хватает только
маршруту §7.2; у более длинных маршрутов все переходы видны в `t_nav_ms_list`, `t_nav_median_ms`,
`t_nav_new_count`/`t_nav_return_count` и полностью — в `runs/<run_id>.json` (`scenario.t_nav`, `steps[]`).

**Каждый переход классифицируется дважды.** `is_return` — свойство МАРШРУТА (страница уже
посещалась); `was_loaded` — свойство КЕША (страница ещё удерживалась клиентом перед кликом, по
списку `getLoadedPages()` из пробы предыдущего шага). Их расхождение и есть повторное чтение:
`nav_cache_hits` / `nav_cache_misses` считаются одинаково у H, Q и Z. У H и Q то же самое видно
прямым счётчиком HTTP-чтений страниц (`api_page_reads`, CDP `Network.*` по URL
`/api/documents/*/pages/*`, плюс `page_reads_delta` на каждом шаге), у Z таких запросов нет вовсе —
страницы приходят синхронизацией, и промах окна остаётся единственной наблюдаемой мерой повторной
материализации. Страница, помеченной командой как устаревшая, даёт `was_loaded=true` и при этом
чтение — поэтому у H/Q `api_page_reads` может превышать `nav_cache_misses + 1` ровно на число таких
перечитываний.

**Начальная страница — явный параметр.** Оболочка ставит `?page=1` (`opts.initialPage`), клиент передаёт
его в `adapter.open()`, поэтому приоритет активной страницы в F не зависит от того, совпала ли стартовая
страница с минимальным индексом (критик A, п. 16).

**Пароль тестовой учётки не попадает в URL.** Оболочка кладёт `{login, password}` в контекст страницы
(`page.addInitScript` → `window.__standCredentials`) до загрузки документа; вход выполняет сама страница
тем же `POST /api/auth/login`, что и форма входа, поэтому измеряемый путь не меняется, а секрет не
оказывается ни в строке запроса, ни в журналах доступа, ни в `Referer`, ни в счётчиках шейпера, ни в
`runs/<run_id>.json` (дефект N9). Способ передачи виден в записи прогона (`credentialsVia`); значение
`query` означало бы откат к `?pass=` (только если страница не поддерживает `addInitScript` — фейки тестов).

**Порядок `command-drawn` и `command-acked` не навязывается.** `command-drawn` фиксируется по
ФАКТИЧЕСКОЙ отрисовке холста (§1.8) и не ждёт подтверждения, поэтому у Z он регулярно наступает
раньше ack — ровно на время чтения журнала операций (`t_cmd_opget_ms`, через шейпер ≈ 60 мс);
в записи прогона это видно как `command.drawnBeforeAck = true`. Сценарий ждёт оба момента,
а «действие завершено» (точка отсчёта следующей паузы) = `max(t_acked, t_drawn)`.

### 3.1 Паузы, часы сценария и стоимость измерительных проб

§1.2: «между действиями выдерживается одна секунда» — пауза отсчитывается **от готовности
предыдущего действия**, а не от конца измерительной пробы. Ожидание выполняется в контексте
страницы (`performance.now()` — те же часы, что и у событий), поэтому следующий клик происходит
ровно в `t_ready + pauseMs` независимо от того, сколько заняли проба и задержки CDP. Если проба
всё же не уложилась в паузу, превышение пишется в `steps[].probe_overrun_ms` и суммируется в
`probe_overrun_ms` прогона.

| Величина | Определение |
|---|---|
| `t_scenario_wall_ms` | сырое: navigationStart → последняя готовность (включает накладные расходы оболочки) |
| `t_scenario_ms` | `t_scenario_wall_ms − probe_overrun_ms` — время пользовательского пути с объявленными паузами, свободное от инструмента; по нему считается бюджет сценария **своей серии** (30 000 мс по умолчанию, у `route-repeat` 40 000, у `route-full` 70 000 — §4.3) и `success` |
| `t_scenario_model_ms` | **независимая** реконструкция по журналу событий страницы: `t` первого `page-ready` + Σ (`page-ready` − `page-select`) по переходам + (число пауз)·`pauseMs` + (max(`command-acked`, `command-drawn`) − `command-sent`) |
| `t_scenario_model_residual_ms` | `t_scenario_ms − t_scenario_model_ms` |
| `probe_total_ms` | суммарная длительность проб (диагностика; они идут внутри пауз) |

Про модель (дефект N5). Прежняя «сверка» складывалась из тех же `t_nav`, из которых вычиталась, и её
остаток был нулевым **по построению** — поймать она ничего не могла. Теперь слагаемые берутся из
журнала страницы (`scenarioModelFromJournal`), а не из бухгалтерии оболочки, поэтому остаток —
настоящая величина: в него входит время от клика до `page-select` (диспетчеризация, единицы мс) и любое
расхождение в сопоставлении событий — пропущенный шаг, лишний `page-select`, не та страница, не та
команда — то есть десятки-сотни мс. Ожидаемый порядок остатка — единицы мс; больше — повод смотреть
`events[]` прогона, а не ошибка сама по себе.

Число объявленных пауз в приёмочном сценарии — 11 (по одной перед каждым из 10 переходов и одна
перед командой), `pauses_declared`/`pauses_declared_ms` пишутся в запись прогона. Сценарий
заканчивается ДЕЙСТВИЕМ, а не паузой: часы останавливаются на готовности последнего перехода
(страница 50), завершающей паузы в `t_scenario_ms` нет.

### 3.2 Что и когда сэмплируется

Политика проб ОДИНАКОВА для всех адаптеров, режимов и документов. Это требование сравнимости, а не
удобства: пока расписание проб зависело от стоимости скана, H/Q получали ≈13 принудительных сборок
мусора за прогон, а Z/F — 2–3, и `js_heap_peak_mb` у них измерялся при разном давлении сборщика
(дефекты N2/N4).

* **retained.** На **каждом** шаге — только дешёвая проба: `getRetained()` (собственное значение
  адаптера: H — `Map`, Q — `queryCache`, Z — кеш реальных строк). Точный скан `getRetainedAsync()`
  (ожидание ≤ 3 с; у Z/F он материализует все ≈25 000 строк хранилища, 0.3–0.5 с) выполняется
  **ровно в двух фиксированных точках**: сразу после команды и в конце, уже после остановки часов
  сценария. Ни один шаг точного скана не делает — ни у H/Q, ни у Z. `retained_probe_mode` =
  `cached-steps+exact-after-cmd-and-end` во всех 1 014 прогонах программы 2.
  **Что с чем сравнимо:** `retained_pages_end_exact` / `retained_shapes_end_exact` (и равные им
  `retained_*_end`) — результат одного и того же скана в одной и той же точке, это и есть сравнимая
  между адаптерами величина. `retained_pages_max` / `retained_shapes_max` — максимум по дешёвым
  шаговым значениям: они сняты по одинаковому расписанию, но отвечают на вопрос «что адаптер сам
  считает удержанным» (у H/Q это точный размер `Map`/`queryCache`, у Z — кеш, обновляемый
  асинхронно после `complete`/вытеснения). Сравнивать их между адаптерами можно только с этой
  оговоркой; вывод об окне кеша делается по `*_end_exact`.
* **JS‑куча.** Опрос по таймеру `js_heap_sample_interval_ms` (250 мс — как частная память) плюс по
  одной пробе на границе каждого шага, снимаемой **до** любого обращения к странице и **до** сборки
  мусора, — поэтому `js_heap_peak_mb` остаётся настоящим пиком выборки. Опрос приостанавливается
  только на время двух точных сканов и выгрузки снимков (три окна, одни и те же у всех адаптеров;
  их суммарная длительность — `js_heap_suspended_ms`, у Z/F она больше просто потому, что дороже
  сам скан). Число сэмплов — `js_heap_samples`; `js_heap_end_mb` снимается в момент остановки часов
  сценария, до выгрузки снимков.
  **Доля прогона, на которой сэмплер кучи действительно работал, выведена колонкой
  `js_heap_sampler_coverage`** — и это не формальность: медиана по программе 2 — 1.000, но у Z/F она
  падает до **0.565** (`doc50x1000`), 0.759 (`command-shape`), 0.787 (`main`,
  `size-fraction-100x500`), тогда как у H и Q равна 1.000 везде. Значит, пик JS‑кучи у Z/F снят по
  меньшему окну наблюдения и **систематически занижен**; величина занижения не измерена
  (`docs/DEVIATIONS.md` §4.14).
* **Окна измерительных проб исключаются из сэмплеров памяти.** Сэмплер `/proc` и сэмплер Chromium
  не останавливаются на время точного скана (иначе потерялись бы сами пики), но выборки, попавшие
  в окно пробы, помечаются и не входят в `chromium_private_peak_excl_probe_mib` и
  `server_*_mem_peak_excl_probe_mib`; сырой пик остаётся рядом как `chromium_private_peak_raw_mib`.
  Число и суммарная длительность окон — `probe_window_count` / `probe_window_ms`; `probe_window_count`
  обязан быть **константой внутри серии** у всех конфигураций (в программе 2: 9 / 14 / 15 / 22 / 27 /
  53 в зависимости от длины маршрута). Без этого пик Z/F завышался бы на цену собственной пробы:
  261.7 против 236.2 МиБ в `main` (`docs/DEVIATIONS.md` §0).
* **Принудительная сборка мусора.** `HeapProfiler.collectGarbage` вызывается в фиксированных точках,
  не зависящих ни от адаптера, ни от режима, ни от вида пробы: после каждой шаговой пробы (11),
  после снимка каждого посещения (11), после пробы вслед за командой (1), в момент остановки часов
  сценария (1), после заключительной выгрузки снимков (1) и после заключительного скана (1) —
  **26 вызовов на прогон** при штатном маршруте; в общем виде `2·(длина маршрута + 1) + 4`.
  Фактическое число пишется в `js_heap_gc_count` и обязано совпадать у всех конфигураций СЕРИИ;
  расхождение означает, что паритет сломан и пики памяти несравнимы. Проверено на всей программе 2
  (1 014 прогонов одиннадцати серий): `js_heap_gc_count = 26` во всех 564 прогонах маршрута §7.2
  (`main`, `command-shape`, `rtt150`, `doc50x1000`, `doc5x100`, `cache3`), `16` / `28` / `52` в
  `size-fraction-25x500` / `-50x500` / `-100x500` (5, 11 и 23 перехода), `42` в `route-repeat`
  (18 переходов) и `104` в `route-full` (49 переходов) — и одинаково у H, Q и Z внутри каждой серии
  (было: ≈13 у H/Q против 2–3 у Z/F). Сразу после сборки в фиксированной точке «остановка
  часов» снимается `js_heap_post_gc_mb` — величина, не зависящая от того, когда сборщик решил
  сработать сам; в пик она не входит.
* **Синтетика.** `retained_bytes_synthetic` в `steps[]` — это `shapes × 200 Б`, одинаковая
  константа для всех адаптеров; памятью не является и в `runs.csv` не выгружается.

Ожидания от клиента сверх SPEC §4.2: кнопки страниц `[data-page-index="k"]`, желательно с
`data-page-id`; `detail` событий `page-*` содержит `pageId` и/или `pageIndex` (иначе страница
определяется по `activePageId` сразу после готовности). `waitFor` необязателен — есть опрос
журнала (25 мс).

### 3.3 Снимки посещений и журнал `visits` (дефект A11)

На **каждое** посещение страницы, дошедшее до `page-ready`, сценарий снимает её снимок сразу после
готовности — пока страница ещё удерживается клиентом — и ведёт журнал посещений. Без этого в режиме
P эталон сверял бы только последнюю страницу маршрута: к концу прогона все прочие вытеснены из окна
кеша, то есть предметная правильность промежуточных «поздних переходов» не проверялась бы вовсе.

* `scenario.visits[]` — `{seq, step, pageIndex, pageId, afterCommands, revision, shapeCount, error}`
  (лёгкий, остаётся в `runs/<run_id>.json`); `steps[].visit_seq` связывает шаг с посещением;
* сами снимки (`{pageId, visitSeq, afterCommands, revision, shapes[]}`) оболочка пишет файлами
  `reference/<run_id>/snapshots/v<seq:3>-<pageId>.json`, а журнал — `reference/<run_id>/visits.json`
  (путь уходит эталону как `STAND_RUN_VISITS`). В запись прогона снимки посещений НЕ кладутся:
  11 × 500 фигур удвоили бы её размер без пользы для анализа;
* `afterCommands` — сколько команд прогона завершилось к моменту снимка: посещения до команды
  сверяются с состоянием до неё, после — после. Посещение без снимка — не «пропуск», а провал
  прогона (`error_stage=reference_inputs`, `reference_ok=false`);
* формат задан в шапке `scripts/reference-check.sh`; `compare-snapshots --require-visits` требует,
  чтобы у каждого посещения был свой снимок. Проверено на всей программе 2: `reference_ok = true` во
  всех **1 014** прогонах; число посещений равно длине маршрута + 1 и покрыто целиком
  (`visits = visitsCovered` в каждом прогоне): **11** на маршруте §7.2 (13–18 снимков, 6 500–9 000
  сверенных фигур), **6 / 12 / 24** на оси `size-fraction-*`, **19** в `route-repeat`, **50** во всех
  60 прогонах `route-full` (52–100 снимков, до 50 000 сверенных фигур на прогон); при
  `visitSnapshotMissing = visitPageMismatch = visitMomentMismatch = badVisit = snapshotError = 0` и
  `mismatchTotal = 0` во всех 1 014 прогонах, и 0 расхождений `compare-db` по всему документу.

Бюджеты (§7.4) пишутся булевыми полями, не навязываются. Тайм‑аут/исключение → `outcome`
`timeout`/`error` со стадией (`open`, `first_ready`, `nav_<n>`, `nav_<n>_click`, `cmd_send`,
`cmd_ack`, `cmd_drawn`, `cmd_result`, `snapshots`); сценарий никогда не бросает.

### 4.1 zero-cache сэмплируется в КАЖДОМ прогоне (§1.2)

zero-cache работает на стенде постоянно — в том числе во время прогонов H и Q, где он реплицирует
изменения от команды прогона. §1.2 требует, чтобы серверный бюджет был виден целиком, поэтому группа
`zero` сэмплируется во всех прогонах, а не только в прогонах Z (дефект A8; раньше `server_zero_*` были
нулями «по построению», и оценка фона ничем не проверялась).

Как читать колонки:

| Случай | `server_zero_cpu_ms` и др. | `server_zero_applicable` | Смысл |
|---|---|---|---|
| прогон Z | измерено | `true` | часть серверного бюджета конфигурации Z (§1.2: «дополнительный сервер нельзя исключать из бюджета») |
| прогон H/Q, zero-cache работает | измерено | `false` | **фон простоя** компонента, который нужен только профилю Z: его нельзя прибавлять к бюджету H/Q, но и скрывать нельзя — это измеренная цена того, что стенд держит zero-cache постоянно |
| zero-cache не запущен | **пусто** | `false`/`true` | измерения не было. В прогоне Z это ошибка прогона (`sampling`), в H/Q — отметка `zero:absent` в `sampling_incomplete`. Ноль не пишется никогда |

Полнота выборки перестала быть двоичной (дефект N6): группа, найденная лишь в части опросов
(процесс перезапустился или появился поздно), публикует заниженные `cpu_ms` и `mem_integral_mib_s`.
Поэтому сводка группы содержит `matched_ticks`/`expected_ticks`/`coverage`, в CSV они сведены в
`sampling_ticks` (`api=48/48|pg=48/48|zero=48/48|chromium=48/48`), а при покрытии < 90 % группа
помечается `partial`: она попадает в `sampling_incomplete` как `<имя>:partial`, и если группа
существенна для этого прогона — прогон становится ошибочным, а не «результатом».

`referenceCommand` (по умолчанию `scripts/reference-check.sh`) запускается из корня репозитория после
каждого прогона **до** сброса документа перед следующим. Оболочка пишет для него
`results/<series>/reference/<run_id>/commands.json` (команда прогона с фактическим `opId` и
`expectedRevision` последней отправки) и `snapshots/<pageIndex>.json` (снимки посещённых страниц;
вытесненные из окна страницы не пишутся) и передаёт `STAND_RUN_COMMANDS`, `STAND_RUN_SNAPSHOTS_DIR`,
`STAND_REQUIRE_PAGES` (F — все посещённые страницы, P — последняя страница маршрута), `STAND_RUN_VISITS`
(журнал посещений, §3.3), `STAND_DOC_JSON`, `STAND_REF_DIR`, `STAND_RUN_JSON`, `STAND_API_URL`. Скрипт выполняет `compare-snapshots` и
`compare-db --check-operations`, отчёты — `report-snapshots.json`, `report-db.json`, `reference.log`
в том же каталоге; хвост лога попадает в `runs/<run_id>.json` (`reference.log`).

Для каждого прогона: (1) `POST /api/auth/login` (alice) → `POST /api/test/reset {docId}` с токеном;
`resetCommand` (если задан; получает `STAND_RUN_ID/DOC/ADAPTER/MODE/CACHE`); `POST <shaper>/config`
параметров серии и `POST <shaper>/reset`; (2) **новый процесс Chromium** (`chromium.launch`,
`--disable-extensions`, канал `chromium`, headless) + новый контекст — холодный клиент (пустые
кеши, IDB, localStorage); (3) сэмплеры /proc и Chromium, CDP; (4) сценарий; (5) остановка
сэмплеров до закрытия браузера, статистика шейпера, закрытие; (6) `results/<series>/runs/<run_id>.json`
и строка в `results/<series>/runs.csv`; `referenceCommand` (если задан; получает `STAND_RUN_JSON`,
код 0 → `reference_ok=true`, иначе `false`).

Порядок конфигураций перемешивается в каждом повторении seeded‑PRNG (mulberry32 от `(seed, rep)`,
Fisher–Yates); `order_index` и `run_id` (`<series>-<order>-<adapter><mode><cache>`) не зависят от
`--only` и от уже выполненных прогонов, поэтому серия возобновляется тем же вызовом (resume
пропускает `run_id`, уже присутствующие в `runs.csv`/`runs/`). После `maxConsecutiveErrors`
(5) подряд неуспешных прогонов серия прерывается (стенд, вероятно, упал).

Цена «новый процесс Chromium на прогон»: медиана `browser_launch_ms` — **187 мс** (150–253 по
180 прогонам `main`) и ≈170–280 МиБ частной памяти в `chromium_private_*`; при 180 прогонах серии
`main` это ~0.6 мин.
Взамен память/кеши процесса не наследуются между прогонами и конфигурациями.

`results/<series>/passport.json`: хост (ОС, ядро, CPU, память), версии Node/npm/PostgreSQL/Chromium/
Python, версии пакетов из `package-lock.json` (прямые зависимости всех workspace; вложенная в workspace версия
приоритетнее поднятой в корень, расхождения — `packagesHoistedDifferent`), параметры шейпера (запрошенные +
`effective` из `GET :8081/config`: `delayMs, bandwidthMbit, bucketMs, bucketBytes, segmentBytes, handshakeRtt`,
и `beforeSeries`; после серии с иными параметрами (rtt150) шейпер восстанавливается), конфигурация серии, seed, план,
время начала/конца, число прогонов.

### 4.2 Варианты команды (`variants`)

Серия может измерять одни и те же конфигурации с РАЗНЫМИ командами — так проверяются «доля
изменённых объектов и их размещение» (введение, §1.4). В конфигурации серии:

```jsonc
"variants": [
  { "name": "baseline",     "sourceId": "doc-cmd-50x500-src-1"  },   // 81 фигура на 10 страницах
  { "name": "concentrated", "sourceId": "doc-cmd-50x500-src-21" },   // 81 фигура на 2 страницах
  { "name": "spread",       "sourceId": "doc-cmd-50x500-src-22" },   // 51 фигура на 50 страницах
  { "name": "large-share",  "sourceId": "doc-cmd-50x500-src-23" }    // 2001 фигура на 50 страницах
]
```

Раннер разворачивает `configs × variants` ДО построения плана, поэтому перемешивание повторения
идёт по всему списку и варианты не идут подряд. Вариант входит в `run_id`
(`command-shape-0008-ZP1-largesha`), в ключ конфигурации (`Z:P:1:large-share`, годится для `--only`)
и в колонки `cmd_variant` / `cmd_target_id`. Без `variants` план, run_id и ключи не меняются.
Эталон получает фактическую команду прогона (`commands.json` с реальным `targetId`), поэтому сверка
вариантов ничем не отличается от обычной.

### 4.3 Ось размера при ПОСТОЯННОЙ доле посещённого (`size-fraction-*`)

Прежняя ось размера (`doc5x100 → doc10x200 → main → doc50x1000 → doc100x500`) спутана: маршрут
подстраивался под документ, поэтому доля посещённых страниц шла **100 / 70 / 14 / 7 / 14 %**, и
отношение обмена оказывалось функцией ДОЛИ, а не размера (у `main` и `doc50x1000` доля одинакова —
и отношение совпадает до третьего знака). Три серии `size-fraction-*` закрепляют долю и меняют
только размер:

| Серия | Документ | Страниц × фигур | Посещается | Маршрут | Переходов |
|---|---|---|---|---|---|
| `size-fraction-25x500` | `doc-frac-25x500` | 25 × 500 = 12 500 | 3 из 25 = 12 % | 2,3,1,2,3 | 5 |
| `size-fraction-50x500` | `doc-acc-50x500` | 50 × 500 = 25 000 | 6 из 50 = 12 % | 2…6,1…6 | 11 |
| `size-fraction-100x500` | `doc-frac-100x500` | 100 × 500 = 50 000 | 12 из 100 = 12 % | 2…12,1…12 | 23 |

Правило маршрута одно на все три размера: первый проход по страницам 2…D (новые), затем возврат
1…D — каждая посещаемая страница читается **ровно дважды**, то есть прочитанная доля документа тоже
постоянна. Команда — после ПЕРВОГО перехода (активная страница 2 входит в S1 во всех трёх
документах), её область одинакова: 81 фигура на 10 страницах. Документы 25×500 и 100×500 порождены
пресетами `frac-25x500` / `frac-100x500` с той же структурой источников, что у приёмочного
(20 источников × 25 экземпляров, `overrideShare` 0.2, S1 = 100 экземпляров на 10 страницах), поэтому
вдоль оси меняется ТОЛЬКО число страниц. Воспроизведение и проверка:
`npm run gen -w packages/generator -- preset frac-25x500 --load` и `… -- verify <abs>/data/frac-25x500.json`.

Что это даёт отчёту: если отношение обмена «только данные» (`bytes_in_api + bytes_in_zero`)
постоянно вдоль оси — порог задаётся долей посещённого, а не размером документа, и формулировать
условие применимости надо в долях; если оно меняется — это собственный эффект размера, и тогда
порог по числу фигур измерен, а не выведен.

Серия `doc5x100` остаётся в программе как ПРЕДЕЛЬНЫЙ случай другой природы: её маршрут отличается от
§7.2 вынужденно (в документе 5 страниц, переходы на 6 и 50 невозможны; шаги 8–10 заменены на 3,2,5 —
длина маршрута, число возвратов и шаг команды сохранены), поэтому посещаются ВСЕ 5 страниц:
доля 100 %. Это отличие записано в `notes` самой конфигурации серии и, значит, в паспорте.

### 4.4 Три серии, закрывающие оси введения (часть программы 2)

В программе 1 `route-full`, `route-repeat` и `command-shape` были «необязательной группой» и
требовали `--with-optional`. В программе 2 они входят в `SERIES_ORDER` и запускаются без флагов;
`--with-optional` теперь добавляет **снятые** серии `cache10`, `doc10x200`, `doc100x500` (§4).

| Серия | Документ | Маршрут | Конфигурации | Повт. | Что закрывает |
|---|---|---|---|---|---|
| `route-full` | `doc-acc-50x500` | 2,3,…,50 (49 переходов, все 50 страниц) | H/Q/Z × F,P/1 | 10 | «последовательное обращение ко всему содержимому» (введение): исчезает ли выигрыш P, когда документ всё равно прочитан целиком |
| `route-repeat` | `doc-acc-50x500` | 2,3,4,2,5,6,7,5,2,8,9,10,8,11,12,50,4,6 (18 переходов, 13 разных страниц) | H/Q/Z × P/1,3,10 **+ H/Q/Z × F** (12 конфигураций) | 10 | «при частых повторных переходах существенной станет политика сохранения страниц»: маршрут, на котором окно 10 действительно вытесняет. **Арм F обязателен**: без него изменение метрики ВНУТРИ адаптера (P−F) на оси окна невычислимо в самой серии, и порядок §1.8 не выполняется. Ячейка `cache = 10` здесь заменяет снятую серию `cache10`, где маршрут §7.2 посещал 7 страниц и окно 11 не срабатывало ни разу |
| `command-shape` | `doc-cmd-50x500` | §7.2 | H/Q/Z × F,P/1 × 4 варианта команды | 6 | «доля изменённых объектов и их размещение»: 81/10 страниц, 81/2, 51/50, 2001/50 при одном и том же маршруте и документе |

Бюджет сценария §1.2 (30 с) относится к маршруту §7.2 из 11 действий. У длинных маршрутов
объявленные паузы сами по себе дают 11–49 с, поэтому `scenario.budgets.scenarioMs` задан явно:
30 200 мс у `size-fraction-50x500`, 40 000 у `route-repeat`, 56 600 у `size-fraction-100x500`,
70 000 у `route-full` (30 с + по секунде на каждое действие сверх §7.2).

**Бюджет читается ПО СЕРИИ, а не по общему порогу** (прежняя редакция этого абзаца утверждала
обратное и была неверна). Обе стороны согласованы:

* оболочка пишет `within_budget_scenario` по бюджету своей серии — `DEFAULT_BUDGETS` из
  `src/scenario/acceptance.mjs` (30 000 мс) сливаются с `scenario.budgets` конфигурации серии, и
  фактически применённые пороги уходят в паспорт (`passport.scenario.budgets`);
* анализ берёт тот же порог из паспорта — `schema.scenario_budget_ms()` ищет
  `scenario.budgets.scenarioMs` сперва в корне паспорта, затем в `seriesConfig.scenario.budgets`;
  при отсутствии — 30 000 мс по умолчанию. По нему считаются и признак `success`, и строка
  «сценарий в бюджете серии ≥ 95 %», а сам порог печатается в заголовке таблицы бюджетов и в
  производной колонке `scenario_budget_ms`.

Поэтому длинный маршрут не объявляется нарушением бюджета по построению. Фактически в программе 2:
`within_budget_scenario = true` во **всех 1 014** прогонах при `t_scenario_ms` от 6.9 с
(`size-fraction-25x500`, бюджет 30 с) до 62.8 с (`route-full`, бюджет 70 с); промежуточные —
`route-repeat` 20.2–24.3 с (40 с), `size-fraction-100x500` 25.8–31.6 с (56.6 с),
`size-fraction-50x500` 13.3–15.7 с (30.2 с), `command-shape` 12.1–15.8 с (30 с).

Отдельная оговорка: **доля «сценарий в бюджете ≥ 95 %» по этим объёмам выборки формально
недостижима.** При нуле отказов нижняя граница интервала Уилсона равна 88.7 % при n = 30 и 72.2 %
при n = 10, поэтому бюджет помечается «не решено», хотя фактическая доля — 100 %; для подтверждения
нужен n ≥ 73 без единого отказа (`docs/DEVIATIONS.md` §4.15).

Документ `doc-cmd-50x500` генерируется пресетом `cmd-50x500` (`packages/generator`): те же
50×500 = 25 000 фигур и тот же seed 50500, что у приёмочного, поэтому источники 1…20 и ВСЕ их
экземпляры совпадают с `data/acceptance.json` побайтно (различается только добивка обычными
фигурами); сверх них — три источника с заданным размещением экземпляров (`shapedSources`).
Воспроизведение: `npm run gen -w packages/generator -- preset cmd-50x500 --load`, проверка —
`… -- verify <abs>/data/cmd-50x500.json` (инварианты включают фактическое размещение экземпляров
и предсказанные `affectedShapes`/`affectedPages` каждого фигурного источника).

## 5. Схема `results/<series>/runs.csv`

Одна строка = один прогон. Имена обязательных колонок совпадают с `packages/analysis/COLUMNS.md`
(проверяется тестом). Пустое значение — метрика не измерена (например, при ошибке до этой стадии).
Время — мс, память — МБ (`_mb`, 10⁶) или МиБ (`_mib`, 2²⁰), трафик — байты, булевы — `true/false`.

| Колонка | Смысл |
|---|---|
| `run_id` | `<series>-<order_index:4>-<adapter><mode><cache>[-<вариант>]`, например `main-0007-HP1`, `command-shape-0008-ZP1-largesha` |
| `series` | имя серии из конфигурации |
| `adapter` | `H` / `Q` / `Z` |
| `mode` | `F` / `P` |
| `cache` | окно кеша неактивных страниц (P); в F — как передано в URL |
| `doc` | id документа |
| `repetition` | номер повторения, 0..N−1 |
| `order_index` | сквозной номер прогона в перемешанной серии, 0.. |
| `started_at` | ISO‑8601 начала прогона |
| `outcome` | `ok` / `error` / `timeout` (тайм‑аут ожидания события) |
| `error_stage` | стадия ошибки: `preflight`, `browser`, `open`, `first_ready`, `nav_<n>`, `nav_<n>_click`, `cmd_send`, `cmd_ack`, `cmd_drawn`, `cmd_result`, `cmd_missing`, `snapshots`, `samplers`, `shaper-stats`, `reference_inputs`, `reference`; пусто при `ok` |
| `t_first_ready_ms` | navigationStart → `page-ready` страницы 1 (часы страницы) |
| `t_nav_1_ms` … `t_nav_10_ms` | клик → `page-ready` для переходов 2,3,1,4,2,5,1,6,3,50 (первые десять переходов ЛЮБОГО маршрута) |
| `route_len`, `route_distinct_pages` | длина маршрута серии и число разных страниц в нём (со страницей открытия) |
| `t_nav_count`, `t_nav_new_count`, `t_nav_return_count` | сколько переходов измерено всего, из них новых и возвратов (у маршрута §7.2 — 10/6/4) |
| `t_nav_median_ms`, `t_nav_ms_list` | медиана всех переходов прогона и полный их список через `\|` (длинные маршруты не помещаются в `t_nav_1…10`) |
| `nav_cache_hits`, `nav_cache_misses` | переходы, при которых страница уже удерживалась клиентом / потребовала загрузки; считаются одинаково у H, Q и Z (§3) |
| `page_loads_observed` | `nav_cache_misses + 1` — загрузок страниц за прогон, включая открытие документа |
| `api_page_reads`, `api_page_reads_distinct`, `api_page_read_bytes` | HTTP-чтения `GET /api/documents/*/pages/*` по CDP: сколько всего, сколько разных страниц, сколько байт. У Z — 0 (страницы приходят синхронизацией), и это измерение, а не пропуск |
| `cmd_variant`, `cmd_target_id` | вариант команды серии (`variants`, §4.2) и фактический источник `setSourceFill`; пусто, если вариантов нет |
| `t_nav_new_median_ms` | медиана переходов на страницы, которые в этом прогоне ещё не посещались (классификация по факту посещения, а не по номеру шага: у маршрута §7.2 это 1,2,4,6,8,10‑й переходы, у `route-full` — все 49, у `doc5x100` — 4 из 10) |
| `t_nav_return_median_ms` | медиана возвратов на уже посещённые страницы (у маршрута §7.2 — 3,5,7,9‑й; число значений см. в `t_nav_new_count`/`t_nav_return_count`) |
| `t_cmd_ack_ms` | `runCommand` → `command-acked` (результат операции известен) |
| `t_cmd_drawn_ms` | `runCommand` → `command-drawn` (ФАКТИЧЕСКОЕ обновление холста; не ждёт ack, у Z обычно меньше `t_cmd_ack_ms`) |
| `t_cmd_server_ms` | `runCommand` → `command-server` (Z — `.server`, H/Q — ответ POST) |
| `t_cmd_synced_ms` | `runCommand` → `command-synced` (данные команды в хранилище активной страницы) |
| `t_cmd_opget_ms` | `t_cmd_ack_ms − t_cmd_server_ms` — цена протокола подтверждения (у H/Q ≈ 0, у Z — `GET /api/operations/:opId`) |
| `cmd_drawn_before_ack` | холст обновился раньше подтверждения сервера |
| `t_scenario_ms` | сценарий с объявленными паузами, без накладных расходов оболочки (см. §3.1) |
| `t_scenario_wall_ms` | то же сырое: navigationStart → последняя готовность |
| `probe_overrun_ms` | суммарное превышение объявленных пауз измерительной пробой (вычитается из `t_scenario_ms`) |
| `t_scenario_model_ms` | независимая модель `t_scenario_ms` по журналу событий (§3.1) |
| `t_scenario_model_residual_ms` | `t_scenario_ms − t_scenario_model_ms`; единицы мс — норма, десятки и больше — расхождение в сопоставлении событий |
| `probe_total_ms`, `retained_probe_mode` | суммарная длительность проб; политика проб retained (§3.2) |
| `retained_pages_end_exact`, `retained_shapes_end_exact` | точный скан хранилища в общей для всех адаптеров точке — **сравнимая** величина (§3.2) |
| `js_heap_samples`, `js_heap_sample_interval_ms` | сколько сэмплов кучи и с каким шагом дали `js_heap_peak_mb` |
| `js_heap_gc_count` | число принудительных `HeapProfiler.collectGarbage` за прогон; одинаково у всех конфигураций (§3.2) — доказательство паритета давления сборщика |
| `js_heap_post_gc_mb` | куча сразу после принудительной сборки в фиксированной точке «остановка часов сценария» |
| `js_heap_suspended_ms` | сколько всего опрос кучи был приостановлен (два точных скана + выгрузка снимков) |
| `sampling_ticks` | полнота выборки по сэмплерам: `имя=совпало/ожидалось` (§4.1) |
| `server_zero_applicable` | входит ли zero-cache в бюджет адаптера этого прогона: `true` — бюджет Z, `false` — измеренный фон в прогоне H/Q (§4.1) |
| `bytes_in` | байт **к клиенту** по шейперу (= `bytesOut` шейпера; ориентация клиента, как в COLUMNS.md) |
| `bytes_out` | байт **от клиента** по шейперу (= `bytesIn` шейпера) |
| `cdp_bytes_in` | Σ `encodedDataLength` завершённых HTTP‑ответов по CDP `Network.loadingFinished` (перекрёстная проверка; WebSocket‑кадры — отдельно в `cdp_ws_bytes_in`) |
| `js_heap_peak_mb` | пик `Runtime.getHeapUsage().usedSize` по выборке с шагом 250 мс + пробы на границах шагов, МБ; окна собственных сканов оболочки исключены (§3.2) |
| `js_heap_end_mb` | то же в момент остановки часов сценария (до выгрузки снимков и заключительного скана) |
| `chromium_private_peak_mib` | пик Σ Private_Clean+Private_Dirty всех процессов экземпляра Chromium (опрос 250 мс), МиБ |
| `chromium_private_end_mib` | та же сумма в последнем опросе (до закрытия браузера) |
| `client_storage_bytes` | `navigator.storage.estimate().usage` + 2·(символы localStorage+sessionStorage) в конце |
| `retained_pages_end` / `retained_shapes_end` | retained в конце — всегда точный скан `getRetainedAsync()` (после остановки часов сценария) |
| `retained_pages_max` / `retained_shapes_max` | максимум retained по шагам + после команды + конечный сэмпл (§3.2: какие шаги точные, какие — по кешу адаптера) |
| `loaded_pages_end` | `getLoadedPages().length` в конце |
| `server_api_cpu_ms`, `server_api_mem_peak_mib`, `server_api_mem_integral_mib_s` | группа `api`: CPU (utime+stime) за прогон; пик Private; ∫Private·dt |
| `server_pg_cpu_ms`, `server_pg_mem_peak_mib`, `server_pg_mem_integral_mib_s` | группа `pg` (postmaster + backend'ы) |
| `server_zero_cpu_ms`, `server_zero_mem_peak_mib`, `server_zero_mem_integral_mib_s` | группа `zero`: измеряется в **каждом** прогоне; в H/Q это фон простоя, не их бюджет (§4.1). Пусто = не измерено (никогда не 0) |
| `zero_replica_bytes` | размер каталога реплики zero‑cache (`procGroups[zero].dir`) в конце прогона; пусто, если группа не измерялась |
| `within_budget_first` | `t_first_ready_ms ≤ 2000` |
| `within_budget_nav` | все `t_nav_i_ms ≤ 1000` |
| `within_budget_cmd` | `t_cmd_drawn_ms ≤ 2000` |
| `within_budget_scenario` | `t_scenario_ms ≤ scenario.budgets.scenarioMs` серии (умолчание 30000; `route-repeat` 40000, `route-full` 70000 — §4.3). Фактический порог серии виден в `passport.scenario.budgets` |
| `reference_ok` | результат `referenceCommand` (0 → true); пусто, если команда не задана. Если обязательных снимков нет (в F — посещённые страницы, в P — последняя страница маршрута), сверка **не запускается**: прогон получает `outcome=error`, `error_stage=reference_inputs` и `reference_ok=false` (у прогона, упавшего раньше, — пусто). Вакуозное «эталон совпал» на нуле снимков исключено |
| `doc_pages`, `doc_shapes_per_page` | из конфигурации серии |
| `rtt_ms`, `bandwidth_mbps` | параметры шейпера прогона (2·delayMs; Мбит/с) |
| `seed` | seed серии |
| `finished_at` | ISO‑8601 конца прогона |
| `error_message` | текст ошибки (≤1000 символов) |
| `notes` | заметка из конфигурации |
| `wall_ms` | полное время прогона по часам оболочки (preflight + запуск браузера + сценарий + закрытие) |
| `browser_launch_ms` | время `chromium.launch()` |
| `cdp_bytes_out` | оценка байт запросов по CDP (строка запроса + заголовки + тело) |
| `cdp_ws_bytes_in`, `cdp_ws_bytes_out` | Σ полезной нагрузки WebSocket‑кадров по CDP (+ оценка заголовка кадра) |
| `shaper_requests`, `shaper_connections` | число HTTP‑запросов (вкл. upgrade) и TCP‑соединений за прогон |
| `cmd_revision`, `cmd_affected_pages`, `cmd_affected_shapes` | из `CommandResult` |
| `server_api_rss_peak_mib`, `server_pg_rss_peak_mib`, `server_zero_rss_peak_mib` | пик RSS групп (для сравнения с Private) |
| `chromium_processes_peak` | максимум числа процессов экземпляра Chromium |
| `client_transfer_bytes_in`, `client_transfer_bytes_out` | `window.__stand.transfer`, если клиент его ведёт |

`rows=60` (`route-full`, `rtt150`, `doc50x1000`, `doc5x100`, `cache3`) — **итого 1 014**. Замечание
«unknown columns (ignored): route_len, …» в старых строках `results/logs/run-all-series.log`
относится к состоянию схемы на момент программы 1 и снято вместе с объявлением колонок.

### 5.2 Запись прогона `runs/<run_id>.json`

`runs/<run_id>.json` содержит всё вышеперечисленное в структурированном виде плюс `steps[]`
(`step, action, page_index, page_id, is_return, t_click, t_select, t_ready, t_ms, budget_ok, retained,
retained_pages, retained_shapes, retained_bytes_synthetic, loaded_pages, js_heap_mb, probe_ms,
probe_overrun_ms, retained_source, visit_seq, drawn`, а также `page_reads_delta` / `page_reads_total`
— HTTP‑чтения страниц, накопленные **к этому шагу**; именно по ним видно, что в режиме F полная
загрузка продолжается после первой готовности, `docs/DEVIATIONS.md` §4.9), `visits[]` (журнал посещений, §3.3),
`gc` (`forced/failed/points`), `retained_end_exact`, `credentialsVia`, `initialPage`,
`t_scenario_model_detail`, `snapshots{pageIndex:{pageId, snapshot}}` для эталона,
`events[]` (журнал страницы), `consoleErrors[]`, `server.<group>.samples[]`, `chromium.samples[]`,
`cdp`, `shaper.stats`, `preflight`, `command`, а также `scenario.command_timings[]`
(`sentAt/clientAt/serverAt/syncedAt/ackedAt/drawnAt/opGetMs/targetRevision` — метрики команды
восстановимы по сырым данным), `scenario.heap_sampler` и `scenario.retained_probe`.
