# Функциональные проверки (SPEC §6, таблица 1 + безопасность)

Playwright 1.56.0 + предустановленный Chromium против **реального стека** (API Fastify + PostgreSQL,
для Z — ещё zero‑cache) по контракту `window.__stand` (SPEC §4.2). Каждая проверка — отдельный тест с
названием строки таблицы 1, выполняется для каждой конфигурации адаптер × режим (× cache) в **новом
контексте браузера** (холодный клиент) после **сброса документа** тестовым хуком (`POST /api/test/reset`,
`clear-operations`, `DELETE /api/test/delay`).
**Документ — параметр (`--doc`), а не константа.** §1.7 требует допуска той конфигурации, числа которой потом
используются, поэтому допуск выполняется и на малом документе (быстрая полная матрица), и на ТОМ документе,
который измеряет серия (масштабозависимое поведение: полнота набора на 500 фигурах, окно LRU при 50 страницах,
материализация 50 view у Z/F). Документ bob (`doc-bob-5x50`, только чтение) используется проверками безопасности.
Эталон — `packages/reference` (`compare-db --check-operations`, `compare-snapshots`); БД читается через `psql`.

## Запуск

```bash
export PATH=/opt/node24/bin:$PATH
# полная матрица всех 12 конфигураций (H,Q,Z × F, P/1, P/3, P/10) на малом документе, один summary.md
scripts/run-functional.sh --adapters H,Q,Z --port 3005 --zero-url http://127.0.0.1:4848 \
  -- --caches 1,3,10 --doc data/small-10x200.json --zero-query-api http://127.0.0.1:3000
# приёмочный документ 50×500: строки таблицы 1 + инварианты (сокращённый набор — «частичный допуск»)
scripts/run-functional.sh --adapters H,Q,Z --port 3005 --zero-url http://127.0.0.1:4848 \
  -- --caches 1 --doc data/acceptance.json --timeout 600000 \
     --only 1-open,2-local-fill,3-source-fill,4-late-nav,5-stale-read,6-retry,I1-full-load,I2-window \
     --zero-query-api http://127.0.0.1:3000
scripts/run-functional.sh -- --only 6-retry --configs H:P:1   # пробросить аргументы run.mjs
node packages/bench/src/functional/run.mjs --help             # все опции раннера
```

`scripts/run-functional.sh` без `--base` поднимает собственный экземпляр API на `--port` (по умолчанию 3005;
`STAND_TEST_HOOKS=1`, `packages/client/dist`, pidfile `results/logs/api-functional-<порт>.pid`, лог `api-functional-<порт>.log` —
имена зависят от порта, поэтому параллельные прогоны на разных портах не останавливают чужой API),
при необходимости собирает клиент/сервер, и по завершении останавливает свой API (`--keep-api` — оставить).
С `--base` API не запускается (готовый стенд: шейпер `/api → :3000`, `/zero → :4848`).

Опции `run.mjs`: `--adapters H,Q[,Z]`, `--modes F,P`, `--caches 1,3,10` (окна кеша режима P — ими покрываются
серии `cache3`/`cache10`), `--configs H:P:1,Q:F:1`, `--only <id,…>`, `--doc data/<файл>.json`,
`--bob-doc doc-bob-5x50`, `--out results/functional`, `--label <метка>`, `--stamp <каталог>`, `--timeout`,
`--zero-query-api <url>`, `--headed`. Адрес zero‑cache для Z передаётся клиенту через `--zero-url`
(query‑параметр `?zero=`). `--zero-query-api` — адрес API, который zero‑cache вызывает как `ZERO_QUERY_URL`
(обычно общий стенд `:3000`): туда проверка 5 ставит задержку трансформации synced query.
Перед запуском раннер проверяет: API с хуками, документ в БД, **БД после сброса == экспорт генератора**
(compare‑db без команд); для Z — preflight открытия документа (адаптер недоступен → вся конфигурация `skip` с причиной).

## Результат и вердикт допуска

`results/functional/<timestamp>/`:

* `summary.json` — `{base, label, docId, docProfile, checkSet, partialCheckSet, totals:{pass,fail,skip,na,admitted[],admittedPartial[],admittedWithCaveat[],notAdmitted[]}, verdicts:[…], configs:[…], rows:[…]}` — одна строка на (конфигурация, проверка);
* `summary.md` — таблица «конфигурация × проверка» (✅/❌/⏭/`n/a`), раздел «Оговорки и неприменимые проверки» и все строки с сообщениями;
* `<config>.json` (`HP1.json`, `QF1.json`, …) — подробности каждой проверки (`details`, при провале — `stack` и `partial`);
* `artifacts/<config>/<check>-*.json` — команды для эталона, отчёты `compare-db`/`compare-snapshots`, `*-partial.json`
  (что успела зафиксировать проверка) — расхождение воспроизводится вручную командой из сообщения.

**Вердикт конфигурации** (§1.7 — «прохождение ВСЕХ предметных проверок», а не «ни одна не провалилась»):

| Вердикт | Когда |
|---|---|
| `допуск` | выполнен ПОЛНЫЙ набор проверок, все применимые — `pass` |
| `допуск (частичный набор)` | провалов нет, но набор сокращён `--only`: подтверждена часть строк таблицы 1, полный допуск даёт другой прогон |
| `допуск с оговоркой` | провалов нет, но есть `skip` — они перечислены с причиной; «чистого» допуска такой прогон НЕ даёт |
| `не допущено` | есть `fail`, либо конфигурация пропущена целиком (preflight Z), либо не выполнено ни одной проверки |

Неприменимые проверки (`applies` = false: И1 в режиме P, И2 в F, Б3 у H/Q) выводятся строкой `n/a` **с
обоснованием**, а не опускаются молча. Код возврата: `0` — все конфигурации получили `допуск`; `1` — есть провал
или непройденная конфигурация; `3` — провалов нет, но есть `skip`/частичный набор; `2` — фатальная ошибка.
**Проверки не пропускаются при обнаружении дефекта** — они падают с точным сообщением; ошибки
`pageerror`/`console.error` страницы также = провал (кроме сессий, где ошибка — ожидаемый исход проверки).

## Ворота допуска (покрытие конфигураций сериями)

`node packages/bench/src/functional/admission-gate.mjs --series <a.json,b.json> --summaries <r1/summary.json,…>
[--out results/functional/gate.md] [--allow-caveat]` сопоставляет конфигурации, которые СОБИРАЮТСЯ измерять
серии, с фактическими вердиктами и отказывает (код 1), если у конфигурации нет допуска на её документе или нет
допуска по полному набору проверок. `scripts/run-all-series.sh` вызывает его после стадий допуска и не запускает
серии без зелёных ворот; отчёт пишется в `results/functional/<stamp>-gate.md`.

## Проверки и что утверждается

| id | Проверка (таблица 1) | Что утверждается |
|---|---|---|
| `1-open` | 1. Открытие страницы | после `page-ready` p1: `detail.shapeCount == N`, `detail.revision == ревизии документа`; `getPageSnapshot(p1)` содержит **ровно** ожидаемые id (из JSON), исходные `fill`/`fillOverridden`; `drawn.pageId == p1`, `drawn.shapeCount == N`, на холсте > 1 цвета, `[data-state=ready]`. Зонд (`addInitScript`, опрос `getPageSnapshot` каждые ~4 мс с загрузки скрипта) не видел ни одного снимка с числом фигур ≠ N; до `page-ready` снимок либо `null`, либо полный. Вторая страница: в P чтение задержано хуком на 700 мс — сразу после `selectPage` снимок `null` и `state=loading`, готовность ≥ 650 мс, правило хука израсходовано; в F страница уже загружена. Z/P — хук ставится не на чтение (оно идёт по WebSocket), а на РЕГИСТРАЦИЮ synced query (`POST /api/zero/query`, 700 мс): те же утверждения (`null`/`loading` во время загрузки, готовность ≥ 650 мс, правило сработало) |
| `2-local-fill` | 2. Локальная заливка | `setLocalFill` экземпляра S на странице X: `revision +1`, `affectedPages=[X]`, `affectedShapes=1`, `command-drawn` на X, снимок и БД: `fill=LOCAL`, `fillOverridden=true`, сосед не тронут. Переход через `cache+1` других страниц (P и `cache+1 <` числа страниц: `retained.pages ≤ cache+1`, X **вытеснена** — нет в `getLoadedPages()`, снимок `null`, при возврате **повторное чтение** `/api/…/pages/X` по журналу запросов; F, а также P с окном шире документа — например P/cache=10 на 10 страницах: вытеснения нет по построению, проверяется обратное — страница осталась и не перечитывалась) → заливка и переопределение сохранены. `setSourceFill(S, LOCAL)` (тот же цвет) и `setSourceFill(S, OTHER)`: переопределённый экземпляр остаётся `LOCAL`/`true` (снимок и БД), сосед получает цвет источника; `affectedPages`/`affectedShapes` как ожидается; эталон `compare-db --check-operations` |
| `3-source-fill` | 3. Общая заливка источника | источник с непереопределёнными экземплярами на ≥ 3 страницах (S1, 100 экземпляров на 9 страницах); активная X, в P ≥ 2 затронутых страниц не загружены. После `setSourceFill`: `compare-db --check-operations` = ok; `affectedPages`, `affectedShapes`, `revision` результата и `command-acked` совпадают с `expectedResults` эталона и с расчётом по JSON; `documents.revision` в БД; снимок X = эталон (`compare-snapshots`), переопределённые не изменены, непереопределённые перекрашены |
| `4-late-nav` | 4. Поздний переход | после команды открывается затронутая страница Y, которую клиент не показывал: `page-ready.revision ≥ ревизии команды`, `drawn` для Y с полным числом фигур, снимок Y = эталон, экземпляры перекрашены/переопределённые сохранены; в P — ровно одно чтение Y. В F (данные Y загружены **до** команды): все страницы достигают ревизии ≥ команды, снимки **всех** 10 страниц = эталон, каждая затронутая страница **перечитана** (журнал запросов), незатронутые — без запросов (информационно); Z — обновление приходит синхронизацией |
| `5-stale-read` | 5. Ответ старого чтения | Общая постановка: данные страницы X **запрошены до** команды, **доставлены после** неё, итог — послекомандный, отката нет. **H/Q**: `POST /api/test/delay` (задержка в `onSend` — ответ вычислен на старой ревизии) на чтение X 1500 мс; P — `selectPage(X)` (чтение в полёте) → через 120 мс `setSourceFill`, затрагивающая X; F — задержка ставится до открытия, команда сразу после готовности p1. Утверждается: исход старого чтения (ответ 200 или отмена клиентом) наступил **после** POST команды; правило хука израсходовано; X перечитана (≥ 2 чтений); `page-ready(X).revision ≥ rev`, `command-drawn.drawnRevision ≥ rev`, итоговый снимок/холст на ревизии ≥ rev с новой заливкой у ВСЕХ непереопределённых экземпляров и сохранёнными переопределениями; зонд снимков (~2 мс) после первого актуального кадра не видел ни ревизии < rev, ни старого цвета; событий `error` нет. **Z**: путь чтения — WebSocket, HTTP-хук неприменим; поздняя доставка создаётся задержкой РЕГИСТРАЦИИ synced query — `POST /api/zero/query` (`ZERO_QUERY_URL`, `--zero-query-api`) задерживается на 1800 мс. Команду подаёт ВТОРОЙ участник (оболочка по HTTP от имени alice), потому что у Z данные, подтверждения мутаций и обновления запросов идут по ОДНОМУ упорядоченному соединению и задержка чтения задерживает и собственную команду клиента (измерено: ack 2076 мс против доставки 1950 мс) — см. `docs/FUNCTIONAL_FINDINGS.md` §3. P — `selectPage(X)` регистрирует новый запрос, затем команда; F — правило ставится ДО открытия (все запросы страниц регистрируются в `open()`), команда подаётся, пока ни одна страница не доставлена. Утверждается то же плюс «запрошено до команды» и «доставлено позже завершения команды» с временными метками в `details.timings`. Если поздней доставки не получилось — `skip` с причиной (**не** `pass`) |
| `6-retry` | 6. Повтор команды | **А** (ответ потерян после обработки): `page.route` → `route.fetch()` + `route.abort('connectionreset')` → `command-retry via 'poll'`, один POST, `command-acked`/`command-drawn` по одному разу, в `operations` ровно одна строка с opId и тем же результатом, `documents.revision +1`. **Б** (запрос потерян до сервера): `route.abort()` без fetch → poll 404 → `command-retry via 'repost'`, по журналу `route` два POST с **одинаковым телом** (тот же opId), одна строка, ревизия +1. Далее прямой повтор opId по HTTP → 200, тот же результат, `x-stand-replayed: 1`, ревизия не меняется; тот же opId с иными параметрами → 409 `op_conflict`; `compare-db --check-operations`. **Z** (мутатор по WebSocket): А — `context.setOffline(true)` до отправки, через 700 мс сеть возвращается → `.server` подтверждён после восстановления (`commandTimings`), одна строка; Б — офлайн сразу после `command-sent` на 700 мс → одна строка, ревизия +1 (повторная доставка идемпотентна) |
| `S1-access` | Б1. Чужой документ (HTTP и клиент) | bob по HTTP: документ alice 403 (`forbidden`), страница 403, команда над источником alice 403 (ревизия/журнал/заливка не изменились), команда в своём документе над чужим источником 403/404, в списке документов bob нет документа alice; alice → документ bob 403; без токена 401, подделанный токен 401. Клиент `?doc=<alice>&autologin=bob`: `state=error`, `error{scope:'open'}`, `getLoadedPages()=[]`, `getRetained()={0,0}`, снимок `null`, `[data-state=error]`, ни одного ответа 200 на чужой документ (≥ 1 × 403), `page-ready` не было. Контроль: bob на своём документе — `ready`, первая страница полностью (id = JSON) |
| `S2-logout` | Б2. Выход (logout) | после переходов и команды `__stand.logout()`: `getRetained()={0,0,0}`, `getLoadedPages()=[]`, снимки `null`, `state=idle`, `pendingCommands=0`, `localStorage`/`sessionStorage` пусты, `indexedDB.databases()=[]` (Z: kvStore удалён), событие `logout` один раз, форма входа, cookie нет; токен исчез: `runCommand` отклоняется, после выхода ни одного запроса с `Authorization`, `fetch('/api/documents')` из страницы → 401 |
| `S3-zero-query` | Б3. Zero — чужие данные не приходят (только Z) | (1) endpoint synced queries `POST /api/zero/query` (его вызывает zero-cache): bob → `shapesByPage`/`docMeta` документа alice = `{error:'app', details.code:'forbidden'}`, своя страница → AST, без токена 401, alice → AST; (2) клиент bob на документе alice → `error`, в хранилище Zero 0 фигур; (3) **принудительная регистрация чужого запроса**: alice сначала открывает свой документ (запрос `shapesByPage({alice,p1})` уже зарегистрирован в zero-cache — проверяется и кеш трансформаций по (name,args)), затем клиент bob запускается с ПОДДЕЛАННЫМ ответом `GET /api/documents/<alice>` (`route.fulfill`), поэтому `ZAdapter` создаёт Zero и материализует чужие запросы НАСТОЯЩИМ токеном bob. За 6 с: `retained.shapes==0`, реальных строк хранилища Zero 0, `getLoadedPages()==[]`, снимок `null`, `page-ready` не было, ни одного 200 на чужие страницы; попытка регистрации доказана (ошибка `zero query error: … forbidden`), иначе проверка **падает**; (4) дополнительно — прямой `zero.run(query,{type:'complete'})`, если клиент опубликует handle и реестр запросов |
| `I1-full-load` | И1. Инвариант F | после открытия `getLoadedPages().length == 10`, `getRetained()` = 10 страниц / 2000 фигур, каждый снимок = ожидаемые id; H/Q: каждая страница прочитана ровно один раз, параллелизм чтений 2…4 (по журналу запросов) |
| `I2-window` | И2. Инвариант P | маршрут 2→3→1→4→2→5→1→6→3→10: после каждого перехода `retained.pages ≤ cache+1`, `getLoadedPages()` ⊆ окна (активная + `cache` последних посещённых), `retained.shapes` = Σ фигур удерживаемых страниц, снимки вытесненных `null`; H/Q: число чтений каждой страницы **равно** предсказанию LRU‑модели (вытесненные перечитываются, удержанные — нет) |

Общие приёмы (как в `packages/client/test/smoke.spec.mjs`): ожидание событий через `__stand.waitFor` внутри
страницы; `runCommand` = промис + `command-acked` + `command-drawn`; журнал запросов `page.on('request'/'response'/
'requestfinished'/'requestfailed')` для подсчёта чтений страниц, параллелизма и заголовка `Authorization`.

Особенности Z: `getRetained()` у Z — кеш, пересчитываемый асинхронно (P: сразу и через 150/450 мс после
вытеснения; F: debounce 300 мс), поэтому проверки ждут «устаканивания» до 2,5 с (`retainedSettled`); HTTP‑чтений
страниц у Z нет — утверждения о числе чтений заменены наблюдением через `getLoadedPages()`/`snapshot=null`.

## Структура

```
run.mjs                 раннер: предусловия, матрица конфигураций, preflight Z, summary
admission-gate.mjs      ворота: покрытие измеряемых конфигураций фактическими вердиктами допуска
lib/config.mjs          аргументы CLI / переменные среды, матрица конфигураций (--modes/--caches/--doc)
lib/doc.mjs             факты о документе из data/<doc>.json (страницы, источники, экземпляры, выбор целей)
lib/api.mjs             HTTP: login, чтение, команды, тестовые хуки (delay/reset/clear-operations)
lib/db.mjs              psql → JSON: ревизия, operations, фигуры, распределение экземпляров
lib/oracle.mjs          обёртка python3 -m reference.compare (expected / compare-db / compare-snapshots)
lib/stand.mjs           Playwright-помощники над window.__stand, зонд снимков, журнал запросов
lib/runner.mjs          исполнение проверок, вердикты допуска, summary.{json,md}
checks/01…08-*.mjs      проверки (id, заголовок строки таблицы 1, applies, run)
```
