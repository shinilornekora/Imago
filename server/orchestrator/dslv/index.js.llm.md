# `server/orchestrator/dslv/index.js` — заметка для LLM

> Сайдкар: карта файла для отладки. Источник истины — код и SPEC.md. Меняешь файл — обнови заметку в том же коммите (конституция, принцип VII; проверка — `node tools/sidecars.mjs`).

## Назначение
DSLV (SPEC §10.1, стрелки 10/11): пул `worker_threads`, в котором идёт прогон brain (патч → операции на копии стейта → раскладка → validate → починка). Шапка файла подробно описывает поведение пула по кругам 27/29/31 — читать её при любом сбое воркеров.

## Главное
- `createDslv(o)` (≈85) → `{run(payload, hooks), close, stats, size, alive, load}`; в `hooks` — `onLlm`, стадии, `onQueued`, signal.
- Пул: min(2, CPU) воркеров, лениво; воркер ведёт до `WORKER_JOBS_MAX` заданий, пока они ждут модель; новое — только когда ни одно его задание не считает. Места нет — очередь `POOL_QUEUE_MAX` / `POOL_QUEUE_WAIT_MS` (`queued {scope:'workers'}`).
- `resourceLimits` (`WORKER_MAX_OLD_MB`) и таймаут СЧЁТНОГО времени (`WORKER_TIMEOUT_MS`; часы стоят, пока воркер ждёт модель).
- Вызовы модели воркер шлёт сообщением сюда, их исполняет `onLlm` вызывающего в главном потоке.
- `workerEnv(src)` — воркеру только безопасные переменные (`WORKER_ENV_KEYS`), ключей нет.
- `BAD_SHAPE` / `BAD_TRANSFER` — ответ модели не той формы / не передался → `llm_bad_response`.

## Инварианты
- Упал/вышел за память/время — задание получает `worker_failed`/`timeout`, воркер заменяется, процесс живёт.
- Соседи упавшего, ждавшие модель, не виноваты: встают в начало очереди и идут заново на свежем воркере (`RESTARTS_MAX` = 1), ответы модели берутся из сохранённых по слепку запроса — модель повторно не зовётся.
