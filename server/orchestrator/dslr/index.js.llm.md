# `server/orchestrator/dslr/index.js` — заметка для LLM

> Сайдкар: карта файла для отладки. Источник истины — код и SPEC.md. Меняешь файл — обнови заметку в том же коммите (конституция, принцип VII; проверка — `node tools/sidecars.mjs`).

## Назначение
DSLR-клиент агента (SPEC §10.1, стрелки 4a/5a): стейт проекта и номер головы у Document service, с кешем и проверкой целостности журнала.

## Главное
- `createDslrClient({...})` (≈208) → `{read(project, {signal, lease, onQueued}), list, stats, gate, forget, usage, peek}`; `read` → стейт `{seq, doc, chain, epoch, …}`.
- Кеш на проект `{seq, doc, chain, epoch}`; первый раз — `GET /api/projects/:id` (+ дочитывание по `more`), дальше — `…/ops?since=&tip=&epoch=`.
- `createReadGate({max, bytes, queue})` (≈58) — семафор полных чтений по числу и байтам (круг 39): байты прочитанного документа держатся, пока он нужен команде (`lease`); ждущим — `queued {scope:'read'}`.
- `chainNext`, `estimateBytes`, внутренний `Reset` — сигнал «журнал переписан, читаем заново».

## Инварианты
- Каждая запись проверяется: seq подряд, `chain = sha256(prev + tx_id + seq)` от нашего якоря, строгий `applyOps` на кешированный документ (§8.3).
- 410, другая эпоха, чужой chain, голова позади кеша, отказ applyOps — откат базы: кеш выбрасывается, стейт читается целиком. Иначе патч строился бы по несуществующему документу.
- Чтения одного проекта — по одному (цепочка промисов): DUIL и команда не затирают кеш старым стейтом.
