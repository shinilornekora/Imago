# Orchestrator

Процесс «агент» из SPEC §8.1: ведёт команду человека по шагам 3–13 с доски. Контракт —
SPEC §10 (нормативен и для клиента `src/agent.js`; дополнения по кругам — §10.5–§10.8). Node 22, `node:http`, без фреймворков и
без новых зависимостей. **К базе не прикасается**: стейт читает у Document service
(`GET /api/projects/:id`, дальше `…/ops?since=`), пишет транзакцией (`POST …/tx`) с
`author_kind:'agent'`. Движок, промпты и компилятор патча — те же `src/core.js` и
`src/brain.js`, что работают в браузере.

```
server/orchestrator/
  index.js        вход: окружение, сборка модулей, SIGTERM/SIGINT; export start(opts)
  http.js         маршруты §10.2, SSE §10.3, лимит тела 1 МБ, единое тело ошибки
  pipeline.js     шаги intent → read → library → llm/validate → write → result; очередь на проект; стоп; варианты + apply
  dslr/           чтение стейта: кеш {seq, doc, chain, epoch}, хвост ops?since=&tip=&epoch= по `more`, сброс при откате базы
  duil/           срез библиотек: проекты kind=library → внешний словарь в прогон brain (library)
  dslv/           пул worker_threads: прогон brain (план → патч → операции → раскладка → validate → починка)
  llm/            провайдер модели: OpenAI-совместимый или Anthropic; URL-сборка, redact ключей
  dslts/          запись транзакции: пределы до сети (413), повтор с тем же tx_id, 503 + Retry-After, 426
  docclient.js    fetch до Document service с дедлайном; сеть/5xx → document_down
  traces.js       трассы §10.4 → POST /api/internal/traces (X-Internal-Token)
  errors.js       OrchError {status, code, message, retryable, detail?}
  limits.js       пределы и умолчания
```

## Запуск

```sh
# Document service рядом (см. server/document/README.md)
npm run server                                    # :8080

# агент с локальной моделью (LM Studio, Ollama, vLLM — любой OpenAI-совместимый)
LLM_BASE_URL=http://127.0.0.1:1234/v1 npm run orchestrator          # :8090

# агент с Anthropic
LLM_KIND=anthropic LLM_API_KEY=... LLM_MODEL=claude-sonnet-4-5 npm run orchestrator

curl -s localhost:8090/agent/health
curl -N -X POST localhost:8090/agent/command -H 'content-type: application/json' \
  -d '{"command_id":"c1","project":"<id>","text":"собери экран тарифов"}'
```

| переменная | по умолчанию | что |
|---|---|---|
| `PORT` / `HOST` | `8090` / `0.0.0.0` | адрес HTTP |
| `DOCUMENT_URL` | `http://127.0.0.1:8080` | Document service |
| `INTERNAL_TOKEN` | — | заголовок `X-Internal-Token` для трасс; не задан — трассы только в памяти |
| `LLM_KIND` | `openai` | `openai` или `anthropic` |
| `LLM_BASE_URL` | — | адрес API модели; не задан — `llm:'unconfigured'`, команды для модели → `503 llm_down` |
| `LLM_MODEL` | первая из `/models` | имя модели; id из `/models` — строкой без управляющих знаков, до 200 символов, иначе не берётся (круг 33) |
| `LLM_API_KEY` | — | ключ; наружу не выводится нигде |
| `LLM_TIMEOUT_MS` | `120000` | дедлайн одного запроса к модели |
| `WORKERS` | `min(2, CPU)` | размер пула DSLV |
| `WORKER_MAX_MB` | `512` | потолок кучи воркера (`resourceLimits`) |
| `WORKER_TIMEOUT_MS` | `60000` | счётное время прогона (ожидание модели не считается) |
| `QUEUE_MAX` | `4` | ждущих команд на проект; больше — `429 busy` |
| `WORKER_JOBS` | `4` | заданий на воркер одновременно, пока они ждут модель (круг 27) |
| `POOL_QUEUE_MAX` | `32` | заданий, ждущих свободный воркер; больше — `error busy` (429, `retry_after: 5`) |
| `POOL_QUEUE_WAIT_MS` | `30000` | сколько задание ждёт воркер; дольше — `error busy` (`retry_after: 10`) |
| `DSLR_FULL_CONCURRENCY` | `4` | полных чтений стейта у Document service одновременно (круг 39) |
| `DSLR_FULL_BYTES` | `67108864` | байтов JSON документов, прочитанных целиком и ещё нужных командам (круг 39) |

Приём запроса (круг 33; `limits.js`, окружением не настраивается): тело не пришло за 30 с —
`408 timeout` (`detail.limit: 'body_timeout'`), соединение закрывается; заголовки node ждёт
20 с, запрос целиком — 35 с (`headersTimeout`/`requestTimeout`; раньше — умолчание node,
300 с). Ответ (поток SSE команды) под эти сроки не попадает.

Адрес модели собирается через `URL`: суффикс (`chat/completions`, `models`, `v1/messages`)
дописывается к пути, query базы идёт после него (`…/v1/chat/completions?api-version=…`).
Учётные данные в адресе (`http://user:pass@host/v1`) вынимаются в `Authorization`
(`Basic`, или `Bearer <user>` без пароля); `LLM_API_KEY` важнее. Всё, что уходит в ответы,
события, трассы и лог, проходит `redact` (ключ, пароль, значения query, любые userinfo).

## Как устроено

* **Порядок команды.** `intent` (без сети) → проверка перед стартом (Document service жив;
  модель жива, если нужна — иначе HTTP `503` с `Retry-After` до открытия потока) → очередь
  проекта (`queued {position, scope:'project'}`) → `read` (круг 39: ждёт семафора полных чтений —
  `queued {position, scope:'read'}`) → `library` → `llm`/`validate`/`repair` (стадии brain
  из воркера) → `write` → `result` → `done`.
* **Без JEV** (круг 38). Классификатора «оболочка или модель» в архитектуре больше нет:
  команды оболочки — открытая таблица в клиенте (`src/shell.js`, `SHELL_COMMANDS`), клиент
  исполняет их сам и агенту не шлёт. Orchestrator команд оболочки не исполняет и события
  `shell` не шлёт. Стадия `intent` («Разбираю запрос», `detail` — вид работы по
  `classifyUtterance`: «правка», «создание», «иллюстрация»…, или «варианты») — часть конвейера
  агента (`intentOf` в `pipeline.js`): выбор пути и промпта, а не привратник. Варианты
  (`mode:'variants'` или «покажи три варианта» — `recognizeVariants`; по имени слоя — после
  `read`) и местные ответы brain без модели (пустая реплика, двусмысленная отмена, «сделай
  компонент») — как раньше. Если реплика всё же явная команда редактора (старый клиент, внешний
  вызов API: «отмени», «впиши всё», «/zoom 100» — `recognizeAction` brain, слэш-форма,
  `isShellCommandText` таблицы оболочки), ответ — `stage intent` (`detail: 'команда редактора'`)
  → `result {tx_id: null, seq: null, applied: 0, summary: 'Это команда редактора — выполните её
  в строке команд', editorCommand: true}` → `done`: модель не зовётся, документ не читается,
  очередь не занимается, трасса `kind:'editor'`.
* **Воркеры.** `runCommand` монолитен (раскладка и проверка между вызовами модели), поэтому
  в воркере идёт весь прогон brain. Модель воркер **не зовёт сам**: его провайдер — посредник,
  вызов уходит сообщением в главный поток, где ключ, сеть, кеш здоровья и общий AbortSignal
  команды. Так ключ не покидает главный поток, упавший воркер не оставляет висящих
  соединений, а таймаут меряет только счёт (часы стоят, пока ждём модель). Воркер упал или
  вышел за память → `error worker_failed`, вышел за время → `error timeout`; воркер
  заменяется, процесс живёт. Круг 27: воркер ведёт до `WORKER_JOBS` заданий — пока одно ждёт
  модель, он берёт следующее (новое — только когда ни одно из его заданий не считает), и
  шесть команд в шесть проектов при двух воркерах идут разом, а не парами. Места нет —
  очередь пула (предел по числу и сроку); ждущему дольше 0,4 с — `queued {position, scope:'workers'}`.
  Круг 29: ожидание, пока свежий воркер стартует (загрузка модулей и первый прогон, не дольше
  3 с), очередью не считается — часы извещения ждут прогрева воркера; и порог извещения — не
  меньше последнего измеренного старта воркера (под нагрузкой медленнее всё). Воркер упал за память
  или снят (таймаут счёта соседа, застрявший «стоп») — `worker_failed`/`timeout` получает
  только тот, кто считал; задания, ждавшие в этот миг модель, один раз идут заново на свежем
  воркере, а ответы модели (и ещё не пришедшие) берут прежние — модель второй раз не зовётся.
  Не помог и повтор — `worker_failed` «расчёт пришлось перезапустить… повторите».
* **Ошибки brain** (круг 29, J5): «ни одна правка не приложилась к документу» — `not_applied`
  (422, текст — сама причина, без «правлю …»), а не `llm_failed`. Отказ модели 4xx — человеку
  нейтральное «Модель не приняла запрос…», статус и тело отказа — строкой в лог.
* **Чья команда** (круг 33). `POST /agent/stop {command_id, client?}` и
  `POST /agent/apply {command_id, variant, client?}` сверяют `client` с тем, что пришёл с
  командой (поля нет — `null`, и сверяется с `null`). Чужая команда неотличима от
  неизвестной: стоп — `{stopped: false}`, apply — `404 not_found`.
* **Стоп.** `POST /agent/stop` → AbortSignal: ждущая команда снимается из очереди, вызов
  модели прерывается сразу (гонка с сигналом в воркере), счёт — через `abort` воркеру (не
  ответил за 2 с — воркер снимается; если на нём есть чужие задания — снимается, только если
  не отпустит это задание за остаток счётного времени). Если запись уже ушла, она доводится.
* **Чьё выделение** (круг 27, I6): `/agent/command` принимает `selection_by: 'human'|'agent'`
  (иначе — `400`); `'agent'` — выделение поставила оболочка после правки агента. brain не
  считает его границей работы человека, и «собери экран …» идёт новой доской, а не внутрь
  только что созданного экрана.
* **Разрыв SSE** команду не отменяет: поток просто перестаёт писать, транзакция приходит
  клиенту по сокету Hub.
* **Варианты.** `runVariants` → `variants {base_seq, items}` (превью — сами операции: клиент
  накладывает их своим движком); набор живёт в памяти 15 минут по `command_id`;
  `POST /agent/apply {command_id, variant}` пишет выбранный через ту же очередь проекта.
  Повтор того же выбора — та же запись; другой вариант после выбора — `400`.
* **Чтение (SPEC §10.6).** Кеш стейта хранит chain своей головы и эпоху; хвост —
  `ops?since=&tip=&epoch=` страницами до `more:false`. 410, другая эпоха, чужой chain у
  пришедшей записи, голова позади кеша — кеш проекта выбрасывается, стейт читается целиком:
  после отката базы агент строит патч по новому журналу, а не по закешированному.
* **Запись.** `tx_id = core.uid('tx')`, `base_seq` = голова прочитанного стейта,
  `author:'Агент'`, `author_kind:'agent'`, `client` — вкладка, приславшая команду (её
  `sync.js` пометит транзакцию как «свою»), `title` — что сделано, словами по операциям
  (brain `changeSummary`: «Стиль текста «Заголовок»: «заголовок» → «крупный»»; у варианта —
  «Вариант «…»: …»; то же уходит в `result.title`), `engine`. Больше 5000
  операций или 4 МБ — `too_large` до сети, без частичной записи. 5xx или дедлайн → повтор с
  тем же `tx_id` (до 3 раз; у 503 — по `Retry-After`, не дольше 5 с за раз); отказ соединения
  (502/504 прокси) — повторы с паузой 0,3→2 с до бюджета 15 с: перезапуск сервиса документов
  (~3 с) не губит работу модели, стадия `write` говорит «Жду сервис документов…»; 413 — `too_large`,
  426 — `engine`, без повтора. «Менять нечего» (`nothingChanged`) не пишется.
* **Библиотеки.** DUIL отдаёт в прогон brain выжимки проектов `kind:'library'`
  (`runCommand({library})`): имена документа главнее, использованный мастер переносится в
  библиотеку документа той же транзакцией (`result.libraryAdded`).
* **Трассы.** После каждой команды: шаги и длительности, число вызовов и токены модели,
  `tx_id/seq`, код ошибки — без промптов, ответов модели и ключей. Нет эндпойнта (`404`) или
  сети — одна строка в лог, команда не замечает. Последние 100 — в памяти (`svc.traces.recent()`).
* **Останов** (`SIGTERM`/`SIGINT`, круг 25): новые соединения не принимаются, новые команды —
  `503 shutting_down`, ждущие в очереди снимаются сразу с `error shutting_down` (повторяемо,
  `retry_after: 5`; круг 27 — не `cancelled`: прервал не человек); выполняемой — дедлайн 5 с
  (`SHUTDOWN_GRACE_MS`), потом отмена (`error shutting_down`) и до 1,5 с на то, чтобы свернуться; потоки закрываются,
  воркеры снимаются, трассы дописываются не дольше 1 с. Весь останов — меньше 8 с
  (`SHUTDOWN_HARD_MS`; Docker шлёт SIGKILL через 10), иначе выход с кодом 1 по таймеру.
* **Секреты** (круг 25): `redact` закрывает ключ целиком, любые его куски от 8 знаков и куски
  его base64/base64url (во всех выравниваниях — Basic-заголовок в эхе сервера модели).
  Воркеры DSLV получают окружение по белому списку (`PATH`, `HOME`, `LANG`, `LC_*`, `TZ`,
  `NODE_ENV`, `TMPDIR`): ни `LLM_API_KEY`, ни `INTERNAL_TOKEN`, ни `LLM_BASE_URL`.
* **Кеш DSLR** (круг 25) ограничен и числом проектов (64), и байтами (`DSLR_CACHE_BYTES`, 96 МиБ
  оценки JSON документов): давние вытесняются, только что прочитанный остаётся. Хвост
  страницы ложится одним черновиком (`core.applyBatches`).
* **DUIL** (круг 25): список библиотек (`GET /api/projects?kind=library&limit=9` — круг 26: сервис
  отдаёт страницами) — не чаще раза в 30 с,
  одно чтение на параллельные команды, при сбое — прежний (до 10 мин); словарь и выжимка
  библиотеки пересчитываются только при новом `head_seq`.
* **Круг 26.** `/agent/health` несёт `instance` (id процесса) и `started_at` — оболочка узнаёт
  перезапуск по смене `instance`. Тело ошибки и событие `error` несут `retry_after` (с), когда
  срок повтора известен. Текст `llm_down` — для человека («Модель сейчас недоступна…»); совет
  администратору (адрес модели, причина сбоя, «задайте LLM_BASE_URL») — в лог, не чаще раза в
  минуту на причину.
* **Круг 29 (J1).** `document` в `/agent/health` — `'up'` только при `200 {ok:true}` от
  `GET /api/health`; `503` (хранилище Document service лежит: `detail.storage:'down'`), сеть и
  дедлайн — `'down'`.
* **Круг 31.** `/agent/health` при `document:'down'` несёт `document_reason`: `'storage'` —
  сервис отвечает, но его база лежит (`503 detail.storage:'down'`), `'unreachable'` — сервис не
  ответил или ответил не тем; так же — `detail.document_reason` у `503 document_down` до потока.
  Ошибки команды: исключение кода агента (не модели) — `internal` (500, `retryable:false`, стек —
  в лог); пустой патч модели — `result` с `nothingChanged:true` без записи («Агент не нашёл, что
  поменять»); ответ модели больше потолка (`LLM_MAX_BODY_BYTES`, 8 МБ; тело читается потоком),
  глубже 100 уровней или не JSON — `llm_bad_response` (502, повторяемо), без глобального
  `llm_down`. Ответ модели, который не передаётся воркеру, — тот же `llm_bad_response` сразу, а
  не 60 с ожидания и замена воркера. `not_applied` — короче (без «правка пропущена» и без совета);
  совет «назовите слой» — полем `detail.hint:'name_layer'`, только когда причина в выборе слоя.
* **Круг 32.** `document_reason: 'schema'` — Document service отвечает `503` с
  `detail.storage:'schema'`: его база восстановлена из копии до миграций и он догоняет схему
  (обычно секунды). Команда до потока — `503 document_down` с `detail.document_reason:'schema'` и
  словами «Сервер обновляет базу данных — команда не выполнена…». brain называет код валидатора
  `bad-children` в сводке замечаний («слои с негодным списком детей»).
* **Круг 39 — нагрузка и честный диагноз.** Полные чтения стейта (снимок + хвост) — под
  семафором агента: не больше `DSLR_FULL_CONCURRENCY` одновременно и не больше `DSLR_FULL_BYTES`
  байтов JSON документов, которые команды ещё держат (команда держит свою долю до конца расчёта;
  документ больше всего предела читается один; размер ещё не читанного проекта — последний
  известный, иначе 1 МБ). Чтения библиотек DUIL байтов не держат и ждущих байтов обходят.
  Ждущей команде — `queued {position, scope:'read'}`, дождалась — снова стадия `read`; ждущих
  больше 64 или чтение не уложилось в 60 с — `error busy` («Сервис документов перегружен…»).
  Сервис ответил `503 busy` — ждём его `Retry-After` в том же бюджете; принял запрос и не ответил в
  срок — один повтор, потом `busy`, а не `document_down`; оборвалось соединение — один повтор через
  0,15 с. Дедлайн запроса — таймер своего цикла событий: опоздал он больше чем на 0,1 с (главный
  поток был занят), срок продлевается (до трёх раз) — ответ, уже лежащий в сокете, не теряется.
  Проверка перед командой: сервис не ответил на `/api/health` за 1,5 с, но отвечал на что-то
  последние 5 с — жив; иначе ещё одна проверка на 5 с, и молчание — `503 busy` (сервис перегружен;
  если опаздывал наш поток — «Агент перегружен», `detail.cause:'agent'`), а не `document_down`.
  Одновременные проверки здоровья — одним запросом. `intentOf` — линейно: реплика длиннее 2000
  знаков командой редактора не бывает (кроме слэш-формы), вид работы читается по её началу.
* **Круг 39 — итог.** `result.title` (и `summary`) — что сделано, то же, что подпись записи в
  истории («Нарисовал «Печенька»: 4 детали»); пересказ плана, написанный до работы, — отдельным
  полем `plan`. DSLV не принимает патч, после которого раскрытие экземпляров выходит за предел
  ядра (`MAX_EXPANDED_NODES`): нарушение `expand-limit` уходит модели в круг починки, не
  починилось — `422 not_applied` словами, без записи.
* **Один экземпляр.** Очередь проекта, наборы вариантов и семафор чтений живут в памяти
  процесса: правило «команды агента одного проекта — по одной» (§8.3) держится только при одном
  Orchestrator. Несколько экземпляров — только с липкостью по проекту на балансировщике (и
  варианты тогда выбираются там же); иначе команды одного проекта идут разом.
* **Транзакция агента** несёт `command_id` (если он не длиннее 64 знаков; Document service
  хранит до 128), `client` вкладки автора команды и (круг 30) `command_author` — имя из `author`
  тела `/agent/command` (без пробелов по краям, чистый текст, ≤ 200 знаков; у варианта — имя
  автора команды, запомненное с набором). По нему «История» подписывает «Агент · Аня» у любого
  браузера, а не только у видевшего Аню в сети. Нет имени — поля нет.
