# Document service

Процесс «документ» из SPEC §8.1: модули **DSLR** (чтение), **DSLTS** (секвенсор — единственный
писатель) и **Hub** (рассылка по WebSocket) в одном процессе Node 22, без фреймворков.
Контракт — SPEC §9 (укрепление круга 23 — §9.8, круг 24 — §9.9, круг 25 — §9.10, хранилище
круга 25 — §9.11, круг 26 — §9.12, круг 27 — §9.13, круги 29–30 — §9.14): он нормативен и для
клиента `src/sync.js`.

```
server/document/
  index.js              вход: окружение и пределы, сборка модулей, graceful shutdown; export launch(opts), start(opts)
  http.js               маршруты §9.2 (node:http), статика клиента для прогонов без nginx
  hub.js                WebSocket §9.3 (пакет ws): hello → догон → живой поток, presence, ping/pong
  dslr.js               чтение: open (снимок + хвост), since (догон или gone со снимком)
  dslts.js              секвенсор §9.4: голова в памяти, мьютекс, rebase → applyOps → commitTx → снимок
  errors.js             DocError → {error:true, code, message, retryable, detail?} — одно тело для HTTP и WS
  limits.js             все пределы и умолчания (клиент держит те же в src/sync.js LIMITS); чистка строк для jsonb
  storage/pg.js         PostgreSQL (pg.Pool с дедлайном), LISTEN/NOTIFY, раннер миграций
  storage/migrations/   NNN_имя.sql|mjs: 001 схема · 002 chain и эпоха · 003 chain старого журнала пачками ·
                        004 traces · 005 надгробия снимка, command_id · 006 дозаполнение и CHECK chain ·
                        007 надгробия «неизвестно» (tombstones_meta, tombstones_chain) · 008 индекс страниц проектов ·
                        009 вес записи (ops_bytes, ops_count) · 010 command_author
  storage/memory.js     тот же интерфейс в памяти (с уведомлениями и backup/restore) — тесты и соло-режим
  storage/committed.js  форма записи журнала, chain, выжимка dropped — общие для адаптеров
```

Движок — `src/core.js` без изменений: `rebase`, `applyOps`, `collectTombstones`, `hashDoc`,
`createDoc`, `ENGINE_VERSION`. Тот же модуль исполняется на клиенте, поэтому картинка
совпадает (§8.3 «движок один»).

## Запуск

```sh
npm install                       # pg, ws
DATABASE_URL=postgres://imago:imago@127.0.0.1:5432/imago node server/document/index.js
# или: npm run server
```

| переменная | по умолчанию | что |
|---|---|---|
| `PORT` | `8080` | HTTP и WebSocket на одном порту (`/api`, `/ws`); `0` — случайный |
| `HOST` | `0.0.0.0` | адрес |
| `DATABASE_URL` | — | Postgres; не задан — хранилище в памяти (данные живут до перезапуска) |
| `DB_TIMEOUT_MS` | `8000` | дедлайн обычного запроса к базе (statement_timeout + query_timeout); миграции — без него |
| `SNAPSHOT_EVERY` | `50` | снимок раз в N транзакций (асинхронно, после ответа); `0` — только при создании |
| `SNAPSHOT_KEEP` | `5` | сколько последних снимков хранить; снимок seq 0 (затравка) не удаляется никогда |
| `PRESENCE_TTL_MS` | `45000` | присутствие без вестей столько — `left` (клиент шлёт сердцебиение раз в 15 с) |
| `WS_INFLIGHT` | `2` | необработанных транзакций на сокет; сверх — пауза чтения сокета и `error busy` (`socket_inflight`) |
| `WS_CONNECTING` | `6` | сокетов одновременно от upgrade до `hello` (чтения проекта, якоря, эпохи); остальные ждут очереди в памяти — шторм подключений не занимает весь пул базы (круг 29) |
| `HTTP_WRITE_CONCURRENCY` | `8` | запись по HTTP (`POST …/tx`, `POST /api/projects`, `PATCH`) одновременно (семафор записи) |
| `HTTP_WRITE_QUEUE` | `64` | запись по HTTP в очереди семафора; сверх — `503 busy` + `Retry-After` |
| `WRITE_BODY_BYTES` | `67108864` | бюджет читаемых тел HTTP-записи на экземпляр, байт (64 МиБ; по заявленному `Content-Length`, без него — по пределу тела 4 МБ); сверх — `503 busy` (`body_bytes_total`), тело не читается |
| `BODY_TIMEOUT_MS` | `30000` | тело записи не пришло за столько — `408 timeout` (`body_timeout`), соединение закрывается; от `1000`. Запрос целиком node и так обрывает через 35 с (`requestTimeout`) — больше 35000 смысла нет |
| `QUEUE_PROJECT_BYTES` | `33554432` | очередь мьютекса проекта, байт тел транзакций (32 МиБ); пустая очередь принимает всегда |
| `QUEUE_PROJECT_TXS` | `256` | очередь мьютекса проекта, транзакций |
| `QUEUE_TOTAL_BYTES` | `134217728` | очереди всех проектов экземпляра, байт (128 МиБ); сверх — `503 busy` (`queue_total`) |
| `TOMB_KEEP_SEQ` | `10000` | надгробия головы: на границе прореживания уходят удалённые раньше, чем за столько seq до неё (не делайте меньше окна переигрывания 5000) |
| `TOMB_PRUNE_EVERY` | `500` | граница прореживания надгробий — номер головы, кратный этому |
| `TOMB_MAX` | `50000` | надгробий в голове (и в снимке) не больше стольких — самые старые уходят |
| `RECENT_TXS` | `500` | выжимок последних транзакций в памяти головы (идемпотентность, окно `stale`) |
| `RECENT_BYTES` | `16777216` | те же выжимки, байт (16 МиБ) |
| `INTERNAL_TOKEN` | — | токен `POST /api/internal/traces` (заголовок `X-Internal-Token`); не задан или `change-me` — 403 |
| `STATIC_DIR` | — | каталог клиента (`index.html`, `app.js`, `styles.css`, `src/*.js`) — раздаётся с верными MIME, чтобы гонять без nginx: `STATIC_DIR=. node server/document/index.js` из корня репозитория |

Числа пределов — целые; пустая переменная — умолчание из `limits.js`; негодная (не целое,
меньше допустимого) — строка в лог и то же умолчание: опечатка в окружении не снимает предел.
Опция `start()`/`launch()` (`snapshotEvery`, `snapshotKeep`, `presenceTtlMs`, `dbTimeoutMs`,
`maxInflight`, `writes: {max, queue, bodyBytes, bodyTimeoutMs}`, `queueProjectBytes`,
`queueProjectTxs`, `queueTotalBytes`, `tombKeepSeq`, `tombPruneEvery`, `tombMax`, `recentTxs`,
`recentBytes`) главнее окружения; итог — `svc.config` (ключи `writes.*` там — `writesMax`,
`writesQueue`, `writesBodyBytes`, `writesBodyTimeoutMs`).

### Старт, миграции, останов

Порт открывается **сразу**, до миграций (SPEC §9.11): пока хранилище готовится, любой
HTTP-запрос, и `/api/health` тоже, получает `503 {code:'migrating', retryable:true,
detail:{phase:'connect'|'lock'|'migrate'|'init', migration, progress}, retry_after:5}` с
`Retry-After: 5`, upgrade сокета — тот же 503. Проверка здоровья видит живой процесс и знает,
что он делает. В логе: «порт … открыт · … 503 migrating», затем — когда готов —
«слушаю http://…» (по этой строке сервис ждут скрипты и тесты).

Миграции — файлы `storage/migrations/NNN_имя.sql|mjs` по порядку, учёт в
`schema_migrations`, отдельное соединение под advisory-lock (два экземпляра на одной базе не
мешают друг другу), каждая — своя транзакция с `SET LOCAL statement_timeout = 0`. Все
годятся для смешанных версий: экземпляры прежней версии (и круга 22) пишут в ту же базу,
пока идёт обновление.

| файл | что | замок |
|---|---|---|
| 001 | схема круга 22 | — |
| 002 | chain, эпоха, `project_epochs`; триггеры `operations_chain`, `snapshots_chain` (chain за экземпляр прежней версии) | миг |
| 003 | chain старого журнала пачками по 5000 (каждая — своя транзакция), с первой записи без chain | строки пачки |
| 004 | `traces` | — |
| 005 | `snapshots.tombstones`, `operations.command_id`; триггеры ещё раз | миг |
| 006 | дозаполнение без замка → короткий `SHARE ROW EXCLUSIVE` → `CHECK (chain IS NOT NULL) NOT VALID` → `VALIDATE` | писатели ждут миллисекунды |
| 007 | `snapshots.tombstones` без `NOT NULL`, умолчание `NULL`; `tombstones_meta`, `tombstones_chain` (надгробия «неизвестно», SPEC §9.13) | миг |
| 008 | индекс `projects_updated_id (updated_at DESC, id DESC)` — обычно `CONCURRENTLY`; если замок миграций ждёт экземпляр прежней версии — обычный `CREATE INDEX` | без замка / `SHARE` на миллисекунды |
| 009 | `operations.ops_bytes`, `ops_count` (вес записи для окна страницы журнала и истории без чтения jsonb); триггер `operations_size` считает их за экземпляр прежней версии; старые записи — дозаполнение пачками ≤ 32 МБ по первичному ключу (~0,5 с на пачку), прерванная продолжает | миг; пачки — строки пачки |
| 010 | `operations.command_author` (имя автора команды агента, круг 30); без умолчания и дозаполнения — экземпляр прежней версии её не пишет и не читает | миг |

DDL ждёт замок не дольше `lock_timeout` (1 с) и повторяется (до 60 раз). Замок миграций
этот круг берёт опросом (`pg_try_advisory_lock`), чтобы ждущий экземпляр не держал снимок
(иначе `CREATE INDEX CONCURRENTLY` в 008 ловил взаимную блокировку). Упавшая миграция
откатывается и не учитывается, ошибка называет файл, процесс выходит с кодом 1; следующий
старт продолжает с неё. `SIGTERM`/`SIGINT` (обработчики ставятся до миграций) во время
миграций обрывают их соединение — база откатывает текущую пачку, выход 0. Останов готового
сервиса: сокеты закрываются кодом 1001, новые транзакции получают 503, снимки в полёте
дописываются, пул закрывается; через 10 с — выход жёстко.

Программно:

```js
import { launch, start } from './server/document/index.js';
const l = await launch({ port: 0 });   // промис — когда открыт порт: {port, url, ready, close, state, config}
const svc = await l.ready;             // готовый сервис: {url, storage, dslr, dslts, hub, config, close}
const same = await start({ port: 0 }); // то же одним шагом: промис — когда готов
```

Несколько экземпляров над одной базой работают: номер и якорь (`head_chain`) выдаёт
`UPDATE projects SET head_seq = head_seq + 1, head_chain = sha256(…) … RETURNING` в одной
транзакции базы с `INSERT` в журнал и `NOTIFY imago_doc`; остальные экземпляры по
уведомлению дочитывают хвост и рассылают его своим сокетам. Экземпляр, чья голова в памяти
отстала, получает «не тот» номер, перечитывает хвост и сливает заново (до 12 попыток,
дальше 503 — клиент держит очередь). Голова, которая оказалась ВПЕРЕДИ базы или с другой
цепочкой, — признак отката базы из бэкапа: эпоха меняется, сокеты проекта закрываются
кодом 4410, клиенты переоткрываются со снимком и переигрывают свои правки (SPEC §9.8).
Под нагрузкой (два экземпляра, 30 клиентов, один проект) попытки кончаются у ~0,2 %
транзакций — 503, клиент повторяет (цифры — SPEC §9.9).

Присутствие ходит между экземплярами (§9.9) по отдельному каналу `imago_doc_presence`:
эфемерные `NOTIFY` через соединение слушателя (не через пул), с id экземпляра против эха;
выделение режется до 200 id и под предел NOTIFY (`truncated: true`); `left` — при закрытии
сокета, по TTL (45 с без вестей), при остановке экземпляра (`bye`) и при его падении (TTL
записей чужого экземпляра). Слушатель LISTEN после обрыва переподключается (200 мс → … →
10 с) и сверяет все головы с базой: пропущенное за обрыв дочитывается.

## Быстрая проверка

```sh
curl -s localhost:8080/api/health
curl -s -X POST localhost:8080/api/projects -H 'content-type: application/json' -d '{"name":"Проба"}'
curl -s localhost:8080/api/projects/<id> | head -c 300
curl -s -X POST localhost:8080/api/projects/<id>/tx -H 'content-type: application/json' -H 'X-Author: Аня' \
  -d '{"tx_id":"tx_1","base_seq":0,"engine":1,"ops":[{"op":"set","id":"<id доски>","path":"name","value":"Главная"}]}'
curl -s 'localhost:8080/api/projects/<id>/ops?since=0'
```

Имя в `X-Author` не-ASCII шлите в percent-encoding (`encodeURIComponent`): заголовки —
latin1, а `fetch` в браузере не-latin1 значение отвергает.

## Что важно знать клиенту (уточнения к §9)

* `hello.project` — сводка `{id, name, kind, head_seq, updated_at}`, не строка-id.
* Сокет без `since` — только живой поток (клиент открыл проект по HTTP и знает голову).
  `since=-1` — «ничего не знаю»: придёт `gone` со снимком. После `gone` по сокету сразу
  идёт хвост за снимком до головы; после HTTP `410` клиент сам просит `ops?since=snapshot.seq`.
* `gone`/`410` — когда `since < 0`, `since` впереди головы, хвост не начинается сразу за
  `since`, или присланный `tip` не совпал с журналом (SPEC §9.8: таблица разбора).
* Повтор своей `tx` по сокету (после разрыва) отвечает рассылкой `tx`, если этот сокет её
  ещё не получал, иначе — `{type:'ack', tx_id, seq, chain, existing:true}`. Клиенту без
  `tip`, `epoch` и `proto=2` в адресе (круг 22, `ack` не знает) вместо `ack` —
  `error {code:'duplicate', retryable:false, existing:true, tx_id, seq}`.
* `presence` — `{type, client, author, selection (≤ 200), board?, truncated?, busy?, queued?, at}`;
  `busy`/`queued` (агент работает над командой человека) — как прислал клиент, булево или
  число. Сердцебиение — раз в 15 с; тишина 45 с — `left`.
* Читатель, у которого неотправленного больше 32 МиБ, закрывается кодом 4503 — догонит с `since`.
* Хвост — страницами (`more: true` — есть ещё); `?head=1` — только голова; `?lean=1` — без
  документа снимка; полный снимок — под семафором (503 `busy` + `Retry-After`).
* Автор на сокете: query `author=`, поле `author` в `tx` или `presence`; тело `tx` без
  автора берёт автора сокета.
* Тело больше 4 МБ — `413` (сокет: ws закрывает соединение кодом 1009), транзакция с
  более чем 5000 операций — `413`. Неизвестный вид операции — `400`; операция известного
  вида, которую строгий `applyOps` не принял, — `dropped: invalid`, остальные ложатся;
  документ сверх 24 МиБ / 20 000 узлов — `dropped: invalid` с `limit` у всего, кроме `remove`.
* `dropped` в журнале и ответе — не больше 50 записей и `{more: N}`; большие операции — выжимкой.
* Мусор в несуществующий проект — `404`, а не `400`.
* Транзакция, у которой отброшены все операции, всё равно получает `seq` и пишется
  (`ops: []`): автору нужен ответ с `dropped`, идемпотентности — запись.

Круг 25 (SPEC §9.10):

* Строки: id (`tx_id`, `undo_of`, `redo_of`, `client`, id в операциях) с U+0000 или
  одиночной суррогатной половиной — `400`; значения (`author`, `title`, всё в операциях,
  ключи тоже, имя проекта, документ проекта, автор присутствия) — чистятся: U+0000 убирается,
  половина → U+FFFD. Поля операций, которые читает движок (`id`, `parent`, `after`, `index`,
  `path`, `node.id`, `node.parent`), — не того типа → `400`; отсутствуют → `dropped: invalid`.
  Вложенность значений глубже 64 — `400`.
* Запись: на сокет — не больше 2 транзакций в полёте (сверх — пауза чтения и `error busy`
  с `detail.limit: 'socket_inflight'`); очередь проекта ≤ 32 МиБ и 256 транзакций, всего
  экземпляра ≤ 128 МиБ (сверх — `503 busy` + `Retry-After`, `detail.limit:
  'queue_project'|'queue_total'`); `POST …/tx` — под семафором (8 одновременно, 64 в очереди).
* `POST /api/projects` без `doc` — пустая страница; демо-документ — только `{demo: true}`.
* `command_id` транзакции (строка-id ≤ 128) уходит в журнал и возвращается в `Committed`.
  `command_author` (круг 30) — имя автора команды агента: строка, чистится, обрезается до 200
  знаков; не строка или пустая — поля нет (правка не отклоняется). Возвращается в `Committed`,
  рассылке и `/history`.
* Снимок несёт надгробия (`snapshot.tombstones`, объект id → родитель; пустые не отдаются).
* `replay_of_epoch` + `replay_at` — переигрывание своей правки после отката базы: `set` /
  `setToken` на лист, который после `replay_at` переписала чужая транзакция, — `dropped:
  stale`; старше суток — `stale` целиком.
* Предел документа в байтах считается точно (разницей по изменённым узлам), а не оценкой.

Круг 26:

* `GET /api/projects?kind=design|library&limit=N&after=<next>` — страница списка, новые по
  `updated_at` первыми (при равенстве — по id); `limit` по умолчанию 200, не больше 1000;
  ответ `{projects, more, next?}`, `next` — непрозрачный курсор следующей страницы. Ключ, а
  не смещение: проект, созданный или изменённый между страницами, уходит в начало и не
  сдвигает остальные. Негодные `kind`, `limit`, `after` — `400`.
* Голова поднимается из снимка и хвоста (и догоняет запись другого экземпляра) одним
  черновиком на страницу (`core.applyBatches`); бюджет слияния (2 с) действует и внутри
  `rebase`, а не только в поиске виноватой операции.

Круг 27:

* Надгробия в снимке — v2 `{v:2, parents:{id: родитель}, seq:{id: seq удаления}}`; прежний
  плоский `{id: родитель}` (v1) читается по-прежнему; `null` — «неизвестно» (снимок записал
  экземпляр прежней версии): голова поднимается с ближайшего более раннего снимка с
  известными надгробиями (`storage.snapshotBefore`) и переигрывает журнал от него, потом
  пишет свежий снимок. Клиенту `snapshot.tombstones` по-прежнему плоский v1.
* Надгробия прореживаются по номеру, а не по часам: на каждой границе 500 seq уходят
  удалённые раньше, чем за 10 000 seq до неё; сверх 50 000 — самые старые. Голова в памяти и
  поднятая со снимка на одном seq знают одно и то же. Последствие: `create` в давно удалённого
  родителя — `dropped: orphan`, а не `reparented`.
* Голова помнит последние транзакции выжимкой (tx_id, seq, chain, client, время, автор,
  листья set/setToken) — не больше 500 штук и 16 МиБ; повтор известного `tx_id` берёт
  запись целиком из базы (`findTx`).
* `?lean=1` читает только мету снимка (`latestSnapshotMeta`, без документа); хранилище без
  неё — полный снимок под семафором тяжёлых чтений. `?head=1` снимка не читает вовсе.
* Запись по HTTP (`POST …/tx`, `POST /api/projects`, `PATCH`): тело читается в бюджете байт
  экземпляра (64 МиБ по заявленному `Content-Length`, без него — по пределу тела; сверх —
  `503 busy`, `detail.limit: 'body_bytes_total'`, тело не читается); слот семафора записи
  берётся только после того, как тело дочитано. Тело не пришло за 30 с — `408`
  (`code: 'timeout'`, `detail.limit: 'body_timeout'`), соединение закрывается; заголовки — 20 с,
  запрос целиком — 35 с (таймауты `http.Server`).
* Пропал проект (базу восстановили без него, I3): при сверке или загрузке головы всем
  сокетам проекта — `{type:'error', code:'not_found', retryable:false}` и закрытие `4404`;
  голова выгружается. Новый сокет к нему — то же.
* `PATCH /api/projects/:id` (I4) — сокетам проекта на всех экземплярах (эфемерная шина
  присутствия) `{type:'project', project:{id, name, kind, head_seq, updated_at}}`; сокет,
  который ещё не получил `hello`, получает его сразу за `hello`.
* Переигрывание после отката (I5): для транзакции с `replay_of_epoch` не нынешней эпохи
  окно поиска `stale` — от seq начала нынешней эпохи (`project_epochs`), а не от `base_seq`
  (номер в журнале, которого больше нет).
* Чистка ключей: ключ `__proto__`, `constructor`, `prototype` (в том числе ставший им после
  чистки, `"__proto__\u0000"`) отбрасывается вместе со значением; ключи, совпавшие после
  чистки, не перетирают данные — исходно чистый главнее, из очищенных — последний.

Круг 29:

* `GET /api/health` — и хранилище (J1): `storage.ping({timeoutMs: 1000})` (кеш 1 с — у
  хранилища; без `ping` — чтение строки проекта с тем же дедлайном и своим кешем) →
  `200 {ok:true, engine, storage:'up'}` или `503 {error:true, code:'unavailable', retryable:true,
  detail:{storage:'down'}}` + `Retry-After: 1`.
* `GET /api/projects/:id/history?limit=50&before=<seq>` (J2) — журнал «Истории» без операций,
  новые первыми: `{items:[{seq, tx_id, author, author_kind, title, created_at, client,
  command_id, ops_count, dropped_count, empty?}], more}`; `limit` 1…200 (50), `before` ≥ 1 —
  только `seq < before` (следующая страница — `before` = наименьший `seq` прежней). Источник —
  `storage.recentTxMeta` (без чтения jsonb); хранилище прежней версии — страницы `txsAfter`.
  `empty: true` — запись без операций (см. ниже).
* Пустые транзакции — по замыслу: правка, у которой при слиянии выпали все операции
  (`/agent/apply` поверх ушедшего документа, переигранная после отката правка, вся `stale`),
  и транзакция с `ops: []` получают `seq` и пишутся — автору нужен ответ с `dropped`, повтору
  того же `tx_id` — идемпотентность. В «Истории» они помечены `empty: true`.
* По сокету при сбое хранилища (J4): транзакция — `{type:'error', code:'unavailable',
  retryable:true, detail:{cause:'storage'|'timeout'}, tx_id}`, сокет не закрывается; догон
  после `hello` — тот же `error` (или `busy` от предела чтений журнала), и догон повторяется (0,5 → 1 → 2 → 4 → 8 с; живое тем временем
  копится), после 5 неудач подряд — закрытие `4503`. До `hello` — `error` и `4503`, как прежде.
* `POST /api/projects` с `doc` (J7): узлов больше `MAX_DOC_NODES` (20 000) — `413`
  (`detail.limit: 'doc_nodes'`); затем `core.checkImportDoc(doc, {maxNodes: MAX_DOC_NODES})`, если
  движок его даёт (строго, без починки: форма каждого поля, токены, циклы, глубина ≤ 256), и
  своя проверка глубины приведённого дерева — иначе `400` с `detail: {limit, max?}`: `limit`
  движка (`'depth'` + `max: 256`, `'nodes'`) или `'import'` (форма полей, цикл, id). Круг 30:
  прежде ответ движка `{code, message}` принимался за «годен» — отказы формы полей не доходили
  до клиента. Исключение `createDoc` на чужом документе — `400`, а не `500`. `name` — строка
  (или число), объект — `400`.
* Чужие значения в текст ошибок — только `showValue` (limits.js): строка обрезается, прочее —
  название типа. `{"type":{"toString":1}}` по сокету раньше ронял процесс (шаблон строки →
  TypeError, `uncaughtException` не ловился), `{"engine":{"toString":1}}` давал 500 вместо 426.
  Обработчики `message` и `connection` сокета — целиком под `try`; процесс ставит
  `installCrashGuard`: необработанное исключение или отказ промиса — строка в лог со стеком,
  работа продолжается; фатально (выход 1 через мягкий останов) — до готовности, системные коды
  (`EADDRINUSE`, `ENOMEM`…) и больше 20 таких ошибок за минуту.
* Рассылка: кадр `tx` сериализуется один раз на событие (Buffer, общий для всех сокетов;
  `ws` без маски его не копирует) — раньше кадр больше предела кеша (1–4 МБ) собирался заново
  на каждый сокет: 300 сокетов × 3,9 МБ — цикл событий стоял ~8 с, теперь ≤ 0,5 с.
* Подключение не встаёт в мьютекс записи: Hub снимает номер головы (`dslts.peek`) до чтения
  строки проекта и отдаёт обоих в `dslts.attach`; та же эпоха и тот же номер с той же цепочкой
  (или база впереди, и её якорь на номере снимка совпадает) — ответ сразу; иначе — прежний путь
  под мьютексом (там ловится откат). Голову незагруженного проекта грузит первый сокет,
  остальные ждут его. Сшивка `hello` с догоном прежняя: сокет в комнате до решения, догон
  читает журнал из базы после номера `hello` и сшивает с буфером живого потока по `seq`.
* Предел чтений журнала (хранилище pg): `txsAfter` и `recentTxMeta` — не больше
  `min(4, max − 4)` одновременно, очередь 64, ожидание `DB_TIMEOUT_MS`; снимки и журнал вместе —
  не больше `max − 4` (4 соединения пула всегда остаются записи). Сверх — `503 busy`,
  `detail.cause: 'journal_reads'|'heavy_reads'`. Окно страницы журнала считается по колонке
  `ops_bytes` (009): jsonb читается только у записей самой страницы.

Круг 30:

* Чтения журнала самого секвенсора — загрузка головы, её сверка с базой и сбор «своего» для
  `stale` — идут `txsAfter(…, {internal: true})`, мимо предела чтений журнала: во время шторма
  `ops?since=0` анонимов запись не ждёт места до `DB_TIMEOUT_MS` (их ограничивает мьютекс
  проекта).
* `command_author` транзакции агента (миграция 010) — см. выше; `/history` отдаёт его полем
  (`null` у человеческих и старых записей).

Круг 31:

* База, восстановленная из копии, снятой до миграций (например, до 009/010), под работающим
  экземпляром: флаги колонок журнала больше не считаются раз навсегда. Ошибка схемы (SQLSTATE
  `42703` — нет колонки, `42P01` — нет таблицы) или переподключение слушателя LISTEN
  (восстановление рвёт соединения; на нём сверяется `schema_migrations` с каталогом миграций) —
  сверка: флаги по факту (запросы снова идут, пусть без новых колонок), миграции заново под
  тем же advisory-lock, флаги ещё раз. Упавший запрос повторяется один раз (сверку ждёт не
  дольше 1 с). Пока сверка не закончена (или не удалась — тогда её повторяет `/api/health` не
  чаще раза в 2 с), `GET /api/health` → `503 {code:'unavailable', detail:{storage:'schema',
  phase:'check'|'migrate'|'failed', migration?, since}}` + `Retry-After: 5`; запрос, которому и
  повтор не помог, — `503 unavailable`, `detail.cause: 'schema'`. В логе: «в базе не учтены
  миграции … — базу восстановили из старой копии? Догоняю», затем «схема базы сверена».
* Числовые параметры запросов (`limit`, `before`, `since` — `/history`, `/ops`, `?lean=1&since=`,
  список проектов, `/traces`; `since` сокета; `base_seq` транзакции) — только десятичные цифры
  в пределах `[min, Number.MAX_SAFE_INTEGER]`, иначе `400 «before: целое от 1 до
  9007199254740991»` (`detail: {param, min, max}`) до всякого SQL.
* Метаданные — `author` (и `X-Author`), `title`, `command_author`, имя проекта, имя в
  присутствии — чистятся `limits.cleanMeta`: кроме U+0000 и одиночных суррогатов — управляющие
  C0/C1, DEL, bidi-переключатели (U+061C, U+200E/F, U+202A–U+202E, U+2066–U+2069), U+2028/9;
  `\t \n \r` — пробел. Пустое после чистки — поля нет. `/history`, список проектов и сводка
  проекта чистят и записи, сделанные раньше. Содержимое документа (значения операций) так не
  чистится.
* Части большой отмены (K1): несколько транзакций с одним `undo_of` допустимы; поле
  `undo_part: {i, n}` — метаданные клиента, сервер его не хранит и не проверяет (любое
  значение — не ошибка).


Без `TEST_DATABASE_URL`/`DATABASE_URL` (или если база не отвечает) прогоны над Postgres
помечаются `skip`, над памятью идут всегда. **Каждый тестовый файл работает в своей
временной базе** `<база>_t<pid><случайное>_x` на кластере `TEST_DATABASE_URL` (SPEC §9.11):
она создаётся при первой проверке доступности и удаляется после всех тестов файла (`DROP …
WITH (FORCE)`), базы умерших прогонов убираются при следующем старте; без права CREATE
DATABASE — своя схема (`search_path`) и свой канал NOTIFY. Названная база не трогается, но
рабочую всё равно не указывайте. Тесты Orchestrator берут порт `0` (круг 26), поэтому
несколько полных `npm test` с одной `TEST_DATABASE_URL` идут параллельно.
