# Конституция Imago Studio

Imago Studio — AI-first редактор макетов: человек говорит словами, агент строит и правит макет
живьём. Нормативная спецификация системы — `SPEC.md` (разделы по кругам); эта конституция —
правила, по которым меняется и сама спецификация, и код.

## Основные принципы

### I. Структура — источник истины, геометрия — функция от неё
Документ — структурный DSL (`Doc`, SPEC §1.2); геометрию считает детерминированный решатель
`core.solve`. Любой быстрый путь раскладки (`solveAfter`, `solveNext`, кеши) обязан давать тот же
`hashGeometry`, что полная раскладка, и проверяться против неё в тестах. Операций пять
(`create, remove, set, move, setToken`) и они не растут (SPEC §5.2): новая возможность — новое
поле или тип узла, а не новая операция.

### II. Движок один, формат версионируется
`src/core.js` исполняется в браузере, в Document service и в Orchestrator без изменений (§8.3).
Любое изменение формата документа или его отрисовки — только с подъёмом `ENGINE_VERSION`, строкой
в `FORMAT_HISTORY` (`test/core-r43.test.mjs`) и подъёмом записей прежнего движка (`liftOps`).
Пределы, которые не меняют формат (например, `MAX_EXPANDED_NODES`), версию не поднимают.

### III. Журнал — истина, слияние не отказывает
Журнал транзакций — источник истины, снимок — производная (§8.3). Сервер — единственный арбитр
порядка; транзакция целиком не отклоняется никогда — отдельные операции уходят в `dropped` с
причиной. Идемпотентность по `tx_id`; отмена — новая транзакция. Правки человека не теряются:
ни при обрыве, ни при откате базы (реплика переигрывает свои).

### IV. Тесты — до «готово», с Postgres
Каждая правка поведения приходит с тестом (`node:test`, файл `test/<область>-r<круг>.test.mjs`).
«Готово» — это `npm test` зелёный **с Postgres** (`service postgresql start`, `TEST_DATABASE_URL`):
без базы pg-прогоны пропускаются и проверено не всё. Тест не отключают и не пропускают ради
зелёного прогона.

### V. Без лишних зависимостей и сборки
Клиент — ES-модули без бандлера; сервер — Node 22, `node:http`, из зависимостей только `pg`, `ws`
и необязательный `@resvg/resvg-js`. Новая зависимость — решение человека, записанное в SPEC.
Новый клиентский модуль — в `SRC_MODULES` (`tools/build.mjs`).

### VI. Человеку — по-русски и без жаргона
Всё, что видит человек (оболочка, ошибки, итоги агента, история), — по-русски, словами, без
кодов, URL и stack (`shell.isJargon`). Команды оболочки — открытая таблица `SHELL_COMMANDS`
(§13): клиент узнаёт и исполняет их сам; агенту уходит только то, что таблица не узнала.

### VII. Рядом с кодом — заметка для LLM (сайдкар)
У каждого файла кода (`*.js`, `*.mjs`, `*.html`, `*.css` вне `test/`) лежит рядом заметка
`<файл>.llm.md` по шаблону `.specify/templates/sidecar-template.md`: назначение, главное (экспорт и
ключевые функции, для больших файлов — карта разделов со строками), поток данных, инварианты,
подводные камни, отладка, ссылки на SPEC и тесты. Каталог из многих коротких однородных файлов
(миграции, `deploy/`, `test/`) описывается одной заметкой `README.llm.md`.

- **Меняешь файл — обнови его заметку в том же коммите**: новые экспорт и функции, сдвинутые
  разделы, новые инварианты и ловушки. Переименовал или удалил файл — то же с заметкой.
- Заметка — карта, а не копия кода: источник истины — код и SPEC. Не пересказывать тела функций.
- Проверка: `node tools/sidecars.mjs` (входит в `npm test` через `test/sidecars.test.mjs`);
  перед PR — `node tools/sidecars.mjs --changed origin/<база>`: файлы, изменённые в ветке, чья
  заметка не менялась.

## Ограничения

- Публичный репозиторий: текст диплома (главы, выводы, черновики) в репозиторий не кладётся
  никогда; здесь — только код, SPEC, схемы и инструменты замеров.
- Ветка `handoff-from-cowork` не сливается в рабочую.
- Безопасность: ключи модели не покидают главный поток Orchestrator и не попадают в ответы,
  логи и трассы (`redact`); чужие строки чистятся (U+0000, одиночные суррогаты) на обеих сторонах.

## Порядок работы

- Работа идёт **кругами**: круг = одна связная правка = одна ветка `r<круг>-<суть>` = один PR,
  стопкой на предыдущий. Номера кругов и разделы SPEC делятся между потоками по договорённости
  (сейчас: раскладка и кеш экземпляров — §18.7+, живой дизайн — §19+).
- Новый круг через Spec Kit: `/speckit-specify` (номер фичи = номер круга, `--number <круг>`) →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`. Черновики — в `specs/<NNN>-<суть>/`;
  итог круга переносится в нормативный раздел `SPEC.md` («Круг N», §…), черновик остаётся как
  история решения. Подробнее — `specs/README.md`.
- После реализации — проход критиков (архитектура, код, UX) и правка по их замечаниям до цели.
- База ветки подтягивается слиянием (merge), не rebase: history чужих веток не переписывается.
- Слияние PR — решение человека; агент PR не сливает.

## Управление

Конституция главнее привычек и шаблонов. Правка конституции — отдельным коммитом с объяснением
и новой версией (семантически: MAJOR — убран или переопределён принцип, MINOR — добавлен принцип
или раздел, PATCH — уточнение формулировок). Проверка соответствия — в каждом плане
(«Constitution Check» шаблона плана) и в каждом проходе критиков. Рабочие подсказки агенту —
`CLAUDE.md`.
