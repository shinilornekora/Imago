## 3. «Ответ старого чтения» (строка 5 таблицы 1) у Z: механизм и доказательства

**Постановка.** Проверка обязана показать: данные страницы X ЗАПРОШЕНЫ до команды, ДОСТАВЛЕНЫ после неё,
итоговое состояние — послекомандное, отката нет. У H/Q это делает HTTP‑хук `POST /api/test/delay` (задержка
в `onSend`: ответ вычислен на старой ревизии). Для Z путь чтения — WebSocket, хук к нему неприменим.

**Что найдено при подборе механизма (важно для интерпретации Z).** Регистрация synced query идёт через
`POST /api/zero/query` (ZERO_QUERY_URL), и её задержка действительно откладывает гидратацию страницы. Но
данные, подтверждения мутаций и обновления запросов у Z идут по ОДНОМУ упорядоченному соединению: при
задержке трансформации на 1800 мс собственная команда клиента подтверждалась через **2076 мс**, тогда как
страница приходила через **1950 мс**, — то есть задержка чтения задерживает и команду того же клиента.
**Переупорядочить чтение и команду «изнутри» одного клиента Zero невозможно**; это свойство механизма
(единый упорядоченный поток), а не недостаток проверки, и его следует назвать в отчёте как причину, по которой
класс ошибок «поздний ответ восстановил старый цвет» для Z структурно отсутствует.

**Принятый механизм.** Команду подаёт ВТОРОЙ УЧАСТНИК — оболочка по HTTP от имени alice (как это сделал бы
второй клиент), пока чтение X у испытуемого клиента ещё в полёте:
* **P**: `selectPage(X)` регистрирует новый synced query (его трансформация задержана на 1800 мс) → команда по HTTP;
* **F**: правило задержки ставится ДО открытия, все запросы страниц регистрируются в `open()` (то есть до
  команды), команда подаётся, когда ни одна страница ещё не доставлена.

**Доказательства (приёмочный документ, `…-acceptance/Z*.json`, поле `details.timings` и `details.probeRecords`):**

| Конфигурация | запрос X → отправка команды | команда завершена | X доставлена | «позже команды на» |
|---|---|---|---|---|
| Z/P/1, X = `doc-acc-50x500-p2` | 158 мс до команды | +183 мс | +1908 мс | **1725 мс** |
| Z/F, X = `doc-acc-50x500-p50` | 425 мс до команды | +434 мс | +7066 мс | **6632 мс** |

Зонд снимков (опрос `getPageSnapshot` каждые ~2 мс) у **Z/P/1** зафиксировал самое интересное:

```
t=681.8   size=null   revision=null            ← страница не загружена (запрос в полёте)
t=2593.7  size=500    revision=0  fill=#1d4d90 ← ПЕРВАЯ доставка: ДОКОМАНДНОЕ содержимое и ревизия
t=2604.9  size=500    revision=1  fill=#112233 ← через 11 мс: послекомандное состояние
```

То есть поздняя доставка действительно принесла устаревший снимок (страница была опубликована на прежней
ревизии со старой заливкой), и клиент сошёлся к послекомандному состоянию за 11 мс, после чего отката не было
(`assertNoRegression`: после первого кадра с ревизией ≥ ревизии команды и новым цветом ни одной записи зонда
с более низкой ревизией или старым цветом). Готовность (`page-ready`) наступила на ревизии 0 — это **корректно**:
испытуемый клиент не выдавал команды, его `lastAckedRevision` = 0, и §1.2 требует учитывать именно
ПОДТВЕРЖДЁННЫЕ этим клиентом команды. У **Z/F** первая же доставка пришла уже на ревизии 1 с новым цветом
(`t=7018.0 size=500 revision=1 fill=#112233`) — устаревшего кадра не было вовсе.

**Если механизм не срабатывает** (например, `--zero-query-api` указывает не на тот API, который zero‑cache
вызывает как `ZERO_QUERY_URL`), проверка помечается `skip` с точной причиной и конфигурация получает
«допуск с оговоркой», а не молчаливый `pass`. В прогонах 13.09 механизм сработал во всех четырёх случаях
(Z/F и Z/P/1 на малом и приёмочном документах), `skip` не потребовался.

## 4. Безопасность Zero (Б3): принудительная регистрация чужого запроса

Раньше самая сильная часть проверки («bob напрямую выполняет synced query страницы alice») возвращала
`{available:false}` и **проходила**, потому что клиент не публикует реестр запросов (`queries` — модульный
импорт в `ZAdapter`). Теперь она заменена на эквивалентную по смыслу, но выполнимую:

1. alice открывает свой документ — запрос `shapesByPage({doc-alice, p1})` **уже зарегистрирован** в zero‑cache
   (так проверяется и кеш трансформаций по паре (name, args));
2. клиент bob запускается с **поддельным** ответом `GET /api/documents/<alice>` (`route.fulfill` в браузере) —
   это единственная HTTP‑проверка прав на пути открытия. `ZAdapter` доходит до создания Zero и материализует
   `docMeta` и `shapesByPage` чужого документа **настоящим токеном bob** по WebSocket;
3. за 6 с наблюдения: `retained.shapes == 0`, реальных строк в клиентском хранилище Zero — 0,
   `getLoadedPages() == []`, снимок `null`, `page-ready` не было, ни одного HTTP‑ответа 200 на чужие страницы;
   доказательство, что запрос действительно ушёл, — ошибка клиента от zero‑cache:
   `page: zero query error: {"error":"app","name":"shapesByPage","message":"forbidden"}`.

Если попытка регистрации не доказана, проверка **падает** (а не проходит). Прямой `zero.run(...)` остаётся
дополнительной ветвью и выполняется, только если клиент опубликует handle Zero и реестр запросов.

## 6. Наблюдения (не дефекты)

1. **«Ответ старого чтения» у H и у Q реализован по‑разному.** H (F и P) после подтверждения команды
   *отменяет* незавершённое чтение затронутой страницы (`AbortController`, в журнале `net::ERR_ABORTED`
   через ~135–160 мс) и запускает новое — задержанный ответ до приложения не доходит. Q *получает*
   задержанный ответ (200 через ~1500 мс), отбрасывает его в `readPageFresh` (ревизия ниже требуемой) и
   перечитывает. Итог одинаков (старый цвет не возвращается, ≥ 2 чтения X), но путь «старый ответ пришёл и
   отвергнут» покрывается только конфигурациями Q. Сообщение проверки фиксирует, какой путь сработал.
2. **Z: `getRetained()` — кеш с асинхронным пересчётом** (P: сразу + повторы через 150/450 мс после
   вытеснения; F: debounce 300 мс). Проверки ждут «устаканивания» до 2,5 с (`retainedSettled`); оболочка
   измерений снимает `retained` через `getRetainedAsync()` (`docs/DEVIATIONS.md` 2.4).
3. **Порядок `command-acked` / `command-drawn` больше не фиксируется проверками.** После перехода на
   «`command-drawn` = момент фактической отрисовки» (§1.8) у Z отрисовка законно наступает РАНЬШЕ
   подтверждения (ack включает отдельное чтение журнала операций). Проверки требуют лишь, чтобы оба момента
   наступили и холст был на ревизии ≥ подтверждённой; проверка 6 берёт момент `.server` из события
   `command-server`, а `commandTimings` адаптера — только как запасной вариант.
4. **Окно кеша шире документа — законный случай.** При P/cache=10 на документе из 10 страниц вытеснения нет
   по построению; проверка 2 в этом случае утверждает обратное (страница осталась загруженной и не
   перечитывалась), а не требует вытеснения. На приёмочном документе (50 страниц) P/3 и P/10 вытесняют.
5. **Z и обрыв соединения.** `context.setOffline(true)` рвёт WebSocket: мутация, отправленная в офлайне,
   доставляется после переподключения (`.server` через ~730 мс при 700 мс офлайна); ровно одна строка
   `operations`, ревизия +1; событий `command-retry` у Z нет (повтор делает сам клиент Zero по mutationID).
6. **Совпадение локального цвета с цветом источника не снимает переопределение** (§1.1) — подтверждено
   снимком и БД для всех адаптеров и обоих документов.
7. **Инварианты на приёмочном документе.** H/F и Q/F: все 50 страниц, 25 000 фигур, ровно одно чтение на
   страницу, параллелизм ≤ 4. Z/F: 50 материализованных страниц, `retained=50/25000`. P/1: `retained.pages ≤ 2`
   на каждом шаге маршрута, 11 чтений по LRU‑модели.

## 7. Ограничения этого допуска

* На приёмочном и прочих документах выполняется СОКРАЩЁННЫЙ набор: проверки безопасности Б1/Б2/Б3 прогоняются
  только на малом документе. Обоснование: они не зависят от масштаба документа (403/401 по HTTP, очистка
  хранилищ при выходе, отказ synced query по правам) и их время на 25 000 фигурах не окупается. Это
  **зафиксированное ограничение**, а не умолчание.
* Допуск выполняется без сетевого ограничителя (шейпера): его счётчики принадлежат измерительной серии.
  Сетевое ограничение не меняет предметных исходов, а каждый прогон серии дополнительно сверяется эталоном
  (`reference_ok`). Это тоже ограничение и названо здесь явно.
* Стенд разделяется несколькими исполнителями: прогон стадии B от 00:32 13.09 (исходный) был испорчен сторонним сбросом
  документа `doc-acc-50x500` (в середине проверки `operations` оказывался пуст, ревизия — 0, заливки —
  исходные) и **повторён** при свободной базе; итоговый набор прогонов — 00:46–00:55 13.09. Результаты первого прогона удалены, чтобы не
  публиковать испорченные данные. При чтении результатов стоит помнить: одновременный прогон сценариев по
  тому же документу делает функциональные проверки недостоверными.

## 8. Как воспроизвести

```bash
export PATH=/opt/node24/bin:$PATH PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers
# A. полная матрица 12 конфигураций на малом документе (~3,5 мин)
scripts/run-functional.sh --adapters H,Q,Z --port 3007 --zero-url http://127.0.0.1:4848 \
  -- --zero-query-api http://127.0.0.1:3000 --caches 1,3,10 --doc data/small-10x200.json --timeout 180000
# B. приёмочный документ 50×500: строки таблицы 1 + инварианты (~2 мин)
scripts/run-functional.sh --adapters H,Q,Z --port 3007 --zero-url http://127.0.0.1:4848 \
  -- --zero-query-api http://127.0.0.1:3000 --caches 1 --doc data/acceptance.json --timeout 600000 \
     --only 1-open,2-local-fill,3-source-fill,4-late-nav,5-stale-read,6-retry,I1-full-load,I2-window
# C. окна кеша 3 и 10 на приёмочном документе
scripts/run-functional.sh --adapters H,Q,Z --port 3007 --zero-url http://127.0.0.1:4848 \
  -- --zero-query-api http://127.0.0.1:3000 --modes P --caches 3,10 --doc data/acceptance.json \
     --only 2-local-fill,4-late-nav,I2-window --timeout 600000
# D. документы прочих серий
scripts/run-functional.sh --adapters H,Q,Z --port 3007 --zero-url http://127.0.0.1:4848 \
  -- --zero-query-api http://127.0.0.1:3000 --caches 1 --doc data/large-100x500.json \
     --only 1-open,3-source-fill,4-late-nav,I1-full-load,I2-window --timeout 900000
# ворота покрытия
node packages/bench/src/functional/admission-gate.mjs \
  --series packages/bench/series/main.json,packages/bench/series/cache3.json \
  --summaries results/functional/<A>/summary.json,results/functional/<B>/summary.json --allow-caveat
```

Всё это вместе выполняет `scripts/run-all-series.sh` перед сериями (стадии A–D + `admission-gate`).
