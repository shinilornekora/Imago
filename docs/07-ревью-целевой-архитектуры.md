# Ревью целевой архитектуры (независимый рецензент, круг 21)

Рецензировались: SPEC §5–8, `docs/04-целевая-архитектура.mermaid`, `docs/06-схема-базы.mermaid`,
экспорты `src/core.js` и `src/brain.js`. Ниже — отчёт рецензента без правок.

## Вердикт

1. Как набор принципов (журнал — истина, модель не пишет DSL, один движок, отмена — новая транзакция,
   неизменяемые версии библиотеки) это правильная основа. Как спецификация, по которой можно начать писать
   бэкенд, — нет: перекладка транзакций и отмена в общем журнале не спроектированы, а с нынешней семантикой
   `invertOps` они молча теряют чужие правки.
2. До первой строки бэкенда: (а) определить в `core` перекладку для пяти операций и правило «инверсию считает
   сервер при записи»; (б) решить, где живёт библиотека — в документе (§5) или в таблицах (§8): сейчас два
   несовместимых описания, и ни в одном нет потока записи новой версии; (в) закрыть разрыв «одна картинка»:
   на сервере нет canvas, текст меряется эвристикой; (г) признать, что движок нужен четырём сервисам,
   и свернуть их до двух процессов.
3. Схему базы начинать после (б): `SNAPSHOTS` теряет токены, `tx_id` не уникален (нет идемпотентности),
   `COMPONENT_USAGE.component_id uuid` ссылается на узлы со строковыми id.

## Дефекты, теряющие данные или ломающие работу

- **D1. Отмена затирает чужие правки.** Инверсия `set id layout.gap` в движке — это `set id layout = <весь
  старый объект>`; `setToken colors.accent` — вся палитра. А правит gap, Б — padding, А отменяет → правка Б
  исчезла без предупреждения. Инверсия `remove` — снимок поддерева на момент базы клиента. Предложение:
  инверсию считает DSLTS при записи относительно фактической головы, на уровне листа пути; отмена старой
  транзакции — перекладка её инверсии поверх записанного после.
- **D2. Двойная отмена = повтор.** В журнале нет пометки «это отмена той транзакции»: второе «отмени»
  отменяет отмену. Нужны `undo_of`/`redo_of`.
- **D3. DSLTS перекладывает, но не проверяет.** Две по отдельности годные транзакции в сумме дают
  `unknown-prop`, `dead-instance`, `overflow`. `applyOps` атомарен, а §8.3 обещает «операция над удалённым
  узлом отбрасывается» — разные политики. Предложение: проверка задетых узлов после перекладки; для
  агентной транзакции — круг починки на свежем стейте.
- **D4. Перекладка не определена.** Тай-брейк двух `create` по одному индексу; `move` по абсолютному индексу
  вместо «после соседа»; `create` с усыновлением удалённого ребёнка; взаимный `move` → цикл; удалён родитель
  всего, что построил агент. Клиент тоже обязан перекладывать (очередь неподтверждённых) — значит функция
  живёт в `core`, а §8.4 обещает «core без изменений».
- **D5. «Один движок → одна картинка» неверно.** На клиенте текст меряется canvas с веб-шрифтами, в Node —
  эвристикой 0,52·кегль: расхождение 10–20 % на `hug`-текстах. Предложение: единый измеритель по файлам
  шрифтов на обеих сторонах — крючок `solve(doc, {measureText})` уже есть.
- **D6. Библиотека описана дважды и несовместимо; никто не пишет `LIBRARY_VERSIONS`.** Смена пина версии
  не в журнале → replay даёт другой документ. «Обновить до v5» не описано: удалённый компонент →
  `dead-instance`, переименованный пропс → `unknown-prop`, оба блокирующие. Предложение: библиотека =
  проект вида `library` со своим журналом; версия = помеченный seq снимка; в проекте — материализованные
  импортированные мастера под стабильными id; обновление = одна транзакция с миграционными операциями.
- **D7. `SNAPSHOTS.state` без `tokens` и `meta`.** Открытие со снимка: палитры нет, все ссылки на шкалы —
  `dead-scale-ref`. Снимок = документ целиком + версия движка + версия библиотеки.
- **D8. Нет идемпотентности.** Падение DSLTS между записью и рассылкой → клиент переотправляет →
  `id занят` → откатывает правку, которая в журнале есть. Нужен `UNIQUE(project_id, tx_id)`, рассылка через
  outbox, реконнект с `head_seq`.
- **D9. Id узлов не уникальны между клиентами** (`uid` — счётчик процесса + случайные цифры).
- **D10. Нет версии формата движка** в журнале и снимках; следующая миграция сделает старый хвост
  неприменимым.
- **D11. Orchestrator — и горячий путь ручных правок, и WS-хаб, и агент с 120-секундными вызовами.**
  Падение теряет очередь и рабочую копию. Два владельца сокетов (DSLTS «рассылает» и 6a). Предложение:
  отдельный Hub (WS, присутствие, fan-out), агент — воркер с очередью в базе, cancel как сообщение.
- **D12. Движок нужен Orchestrator, DSLR, DSLTS и DSLV.** Предложение: Document service = DSLR + DSLTS в
  одном процессе с головой в памяти; DSLV — библиотека внутри Orchestrator. Имена с доски — как модули.
- **D13. Чистка журнала ломает отставшего клиента и отмену** (перекладывать не поверх чего; инверсия
  пятничного `remove` упрётся в удалённого родителя). Предложение: не удалять, уносить в холодную
  партицию; чистить только снимки.

## Хотелось бы лучше

JEV даёт метку, а командам нужны слоты («отмени **два** раза», «**второй**») и контекст переспроса;
логичнее JEV на клиенте. Контракт шага 3 не описан (`selection`, `activeArtboardId`, память разговора,
показанные варианты). Импорт документа как транзакция. Конфликт намерений одного автора (агент vs рука
за время команды). Очередь агента на проект мало что даёт. Права проверяются где? `COMPONENT_USAGE` пишет
DSLTS в той же транзакции базы. `LIBRARY_VERSIONS.content` одним JSONB — нужна производная таблица
компонентов. `AGENT_RUNS`: статусы queued/running, `plan`, `parent_run_id`. `ASSETS`: `sha256`, `bigint`.
Присутствие при нескольких инстансах — pub/sub. Лимиты ops/сек (drag без коалесинга раздует журнал).
Снимки асинхронно. Локальная сборка: один процесс с адаптером хранилища или отдельная ветка. `doc.version`
vs `seq`. `core.js` содержит `Stage` (DOM) — разнести на `engine` и `stage`. `docs/README.md` устарел.

3. Модель отмены: серверная инверсия, `undo_of`/`redo_of`, отмена не последней. 4. Проверка после
перекладки. 5. Источник истины для ширины текста. 6. Топология сокетов и инстансов. 7. Контракт шага 3.
8. Память разговора, варианты, очередь при падениях. 9. Хранение журнала. 10. Импорт и миграции формата.
11. Аутентификация и права. 12. Локальная сборка. 13. Чьи токены и шкалы. 14. Где исполняется JEV и слоты.
15. Нужна ли очередь агента.

## Что сделано хорошо — не переделывать

Журнал транзакций с операциями по id (большинство коммутирует; алгебру из пяти операций можно описать
формально). «Модель не пишет DSL». Детерминированный решатель с `hashGeometry`; `measureText` уже
инжектируется. Все действия с библиотекой и шкалами уже возвращают операции. `applyOps` иммутабелен и не
бросает. Неизменяемые версии библиотеки. Команды оболочки без модели. `PROJECTS.head_seq` как точка
сериализации: `UPDATE … head_seq + 1 RETURNING` в одной транзакции с `INSERT` делает «единственного
писателя» инвариантом базы — DSLTS можно поднимать в нескольких экземплярах.
