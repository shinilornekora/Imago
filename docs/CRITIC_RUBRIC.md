# Рубрика независимой критической оценки стенда

Критик оценивает выполненную работу по отношению к тексту диссертации (введение и глава 1:
`/home/claude/thesis/thesis.md`) и к спецификации `SPEC.md`. Оценка выставляется по каждому
критерию по шкале 0–10 с шагом 0.1 и итоговая (среднее критериев, применимых к данному проходу).
Критик обязан перечислить конкретные дефекты с путём к файлу/строке и указать, что именно
нужно исправить, чтобы поднять оценку. Стиль: строгий рецензент диссертации + технический
ревьюер. Похвала не нужна; нужны найденные проблемы и их серьёзность.

Шкала: 10 — нет замечаний, всё соответствует главе 1 и хорошей практике; 9.5 — только косметика;
9.0 — мелкие недочёты, не влияющие на выводы; 8 — есть недочёт, который может исказить один
показатель или один вывод; 7 — есть дефект, который ставит под сомнение раздел результатов;
≤6 — требование главы 1 не выполнено или методика непригодна.

## Критерии

K1. Соответствие архитектуры главе 1: предметная модель §1.1 (источник, экземпляры,
переопределение, команда над серверным документом), контракт §1.2 (идентификатор операции,
ревизия, идемпотентность, 24 ч), три адаптера с обязанностями по таблице 2, режимы F/P и окно
кеша, единый отрисовщик активной страницы, общий предметный модуль с интерфейсом транзакции
§1.6, безопасность §1.2/§1.6, стек §1.5 (TypeScript, React 19 + Canvas 2D, Vite, Node 24, Fastify 5,
PostgreSQL, Compose+Caddy, Playwright), Zero 1.9 и TanStack Query 5.

K2. Функциональные проверки и эталон: таблица 1 (6 строк) проверяется для каждой конфигурации;
независимый эталон не использует серверный модуль; безопасность (две учётки, очистка при
выходе); допуск конфигураций до измерений (§1.7–1.8).

K3. Методика измерений §1.2/§1.8: приёмочный сценарий (50×500, маршрут, команда после 5‑го
перехода, паузы 1 с), холодный клиент, сеть RTT 50 мс / 20 Мбит/с, метрики (готовность первой
страницы, переходы, команда до холста, обмен, JS‑куча, частная память всех процессов Chromium,
серверные ресурсы включая zero‑cache, фактически удерживаемые записи), ≥30 повторений,
перемешивание порядка, сброс состояния, паспорт серии, бюджеты, честный учёт ошибок; отсутствие
подмены механизмов ради показателя (§1.7); корректность момента «готовности» и «завершения
команды» (§1.2 рис. 3, §1.6).

K4. Воспроизводимость и качество: README с воспроизведением с нуля, pin версий, тесты, скрипты,
compose‑файлы, отклонения от главы 1 явно задокументированы (DEVIATIONS), отсутствие
скрытых допущений; код читаем, без заглушек в измеряемом пути.

K5. Анализ и отчёт (только проход по результатам): статистика (медианы, p95, интервалы, доля
успеха с интервалом), сравнение внутри адаптера и между адаптерами §1.8, выводы не выходят за
данные, границы применимости, план внедрения §1.9, сверка чисел отчёта с сырыми данными.

## Формат отчёта критика

Файл `reviews/<pass>/<critic-name>.md`:

```
# Критик: <имя/фокус>
## Оценки
K1: x.x  K2: x.x  K3: x.x  K4: x.x  K5: x.x|n/a
Итог: x.x
## Дефекты (по убыванию серьёзности)
1. [K3][серьёзность: high|medium|low] <файл:строка> — что не так — что сделать
...
## Что проверено лично (команды, которые критик запускал)
```
и в конце блок JSON:
```json
{"critic":"...","pass":N,"scores":{"K1":..,"K2":..,"K3":..,"K4":..,"K5":..},"overall":..,"defects":[{"k":"K3","severity":"high","where":"...","what":"...","fix":"..."}]}
```
