# Круг 45 — CORE: заметки для SPEC

Файлы: `src/core.js`, `test/core-r43.test.mjs` (строка версии 2 и проверки корпуса), новый `test/core-r45.test.mjs` (3 теста).

## 1. Поведенческий раздел отпечатка формата (§8.3)

Таблицы круга 43 не видели правок ВНУТРИ функций проверки (opacity 0..2, pos без y, PROTECTED_PATHS,
props — любое, угол градиента). Теперь в отпечатке есть раздел `behavior.*`: фиксированный
детерминированный корпус проб прогоняется через настоящие проверки, и вектор «принял/отказал» по
семействам хэшируется (`formatBehavior()` — сами векторы; `FORMAT_SIGNATURE.sections['behavior.<семейство>']`).

Корпус строится из таблиц (новое поле получает пробы само) плюс явный список особых проб:
* палитра: строки — все значения перечислений формата и особые строки (ссылки шкал, тени, цвета, пути);
  числа — плотная сетка и КАЖДАЯ граница из таблиц пределов (MAX_SIZE, ROTATE_LIMIT, STATE_LIMITS,
  VECTOR_LIMITS, TEXT_STYLE_FIELDS, STROKE_FIELDS…) ±0,001 и ±1, со знаком; составные — частичные
  объекты осей ({x}, {y}, {x,y}…), размеры, краски, градиенты, состояния, глубина PLAIN_DEPTH±1;
* `fields` — каждое поле STRING_FIELDS/BOOL_FIELDS/FIELD_RULES (и неизвестное) × каждый тип узла ×
  палитра через `fieldProblem` и через `checkNode` (там есть свои проверки opacity, pos, override, size);
* `nested` — ключи составных полей (pos, override, size и ось size, layout, padding, stroke, style, обёртка
  краски, градиент линейный/радиальный, стоп, viewBox, контур vector, патч и имена состояний, motion,
  пропс компонента, enum-пропс, component, props экземпляра, size экземпляра): база, палитра в каждый
  ключ, снятие каждого ключа, лишний ключ; счёт стопов и контуров, длина пути и суммарная длина у границ;
* `nodes` — структура (checkNode): у экземпляра нет детей, `of` на себя/пустой, страница с родителем
  (и библиотека), дети у не-контейнера, нет size/viewBox/paths/characters, id/type, ссылки шкал, radius,
  ключи прототипа как поля;
* `tokens` — каждая группа TOKEN_RULES и чужая × пути (группа, шаги, номера, поля стиля, глубже) ×
  палитра и снятие через `tokenWriteProblem`;
* `svg` — `parsePath` на особых строках и на каждой команде PATH_ARGS с n−1, n, n+1, 2n аргументами;
* `ops` — настоящий `applyOps` на документе-пробе: пути set (PROTECTED_PATHS, UNSAFE_KEYS, ключи
  прототипа, пустые сегменты, индексы контуров…) на каждом узле, каждое поле таблиц через set на
  каждом узле, create/remove/move/setToken/set component/of у границ, каждая операция и неизвестные.
Размер ~395 тыс. проб, ~1 с; считается лениво при первом обращении к `FORMAT_SIGNATURE`/
`formatBehavior()` (загрузке модуля не мешает), логгер ядра на это время молчит (`logQuiet`).
Тест `core-r45`: отдельный экземпляр модуля с нагруженными кешами даёт тот же вектор.

Мутации (`scratchpad/c39/mut45.py`): все 8 из `critic-arch/r44/mut.py`, все из `mut2.py` (opacity и pos
во всех местах, size без MAX_SIZE в обоих местах, PROTECTED без prototype), T01–T08 и T10–T15 критика
кода и ещё 10 своих (rotate 0..720, дети у экземпляра, страница с родителем, точка в имени пропса, enum без
values, motion.delay, стоп at 0..2, флаг дуги 2, число в colors) — тест формата падает на каждой,
с разделом behavior (и таблицей, если она задета). T09 (снять раннюю проверку OP_NAMES) — эквивалентный:
`switch` в applyOne отказывает неизвестной операции тем же кодом и текстом, поведение не меняется.

Прямые тесты границ (`core-r45`): opacity 0 / 0,0001 / 0,9999 / 1 — да, −0,0001 / 1,0001 / 1,5 / 2 / строка /
null / NaN — bad-node (set, create, импорт); pos — обе оси числами обязательны (set, снятие `pos.y`,
create, override, импорт).

## 2. Почему ENGINE_VERSION поднимать не нужно

Формат (что ядро принимает и отвергает) в этом круге не менялся: проверки остались те же, тексты отказов те
же, все 287 тестов ядра и полный прогон зелёные без правок. Изменился только СОСТАВ отпечатка — к таблицам
добавлен раздел `behavior.*`, поэтому изменилось значение хэша. Отпечаток — средство проверки, а не часть
формата: ни записи журнала, ни снимки, ни операции его не содержат, и ни один экземпляр не сверяет его с
другим (DSLTS опирается на `engine` записей, а не на отпечаток). Экземпляры движка 2 до и после этого круга
принимают и отвергают одно и то же. Поэтому строка версии 2 в `FORMAT_HISTORY` обновлена на месте с
пометкой «круг 45: состав отпечатка шире», а не добавлена строка 3. Правило таблицы «старые строки не
меняются» относится к изменению ФОРМАТА; смена способа снятия отпечатка — единственный случай, когда
строку текущей версии переписывают, и делать это можно только вместе с доказательством, что поведение
то же (здесь — зелёный прогон всех тестов приёма/отказа без правок).

Предлагаемый текст §8.3 (дополнение): «Отпечаток формата = таблицы ядра + поведенческий корпус проб
(вектор принял/отказал настоящих проверок на детерминированном наборе граничных значений). Изменение
диапазона, обязательного ключа, защищённого пути или правила структуры без подъёма ENGINE_VERSION
роняет тест. Изменение состава отпечатка при неизменном поведении — переписывается строка текущей
версии».

## Ограничения корпуса
* Граница, которая попадёт строго между точками сетки и не совпадёт ни с одним числом из таблиц
  пределов (например, новый литерал 0,63 внутри функции), может пройти незамеченной. Сетка плотная у
  типичных границ (0, 1, 0,8/1,2, 24, 360, 900, 1000, 2000, 1e5, 1e6); литералы в проверках лучше выносить в
  таблицы пределов — тогда их граница попадает в палитру автоматически.
* Проверки, зависящие от документа (цели пропсов внутри мастера, циклы, глубина дерева, предел раскрытия),
  пробуются только через `ops` на маленьком документе — не исчерпывающе.
