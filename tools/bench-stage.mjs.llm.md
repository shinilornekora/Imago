# `tools/bench-stage.mjs` — заметка для LLM

> Сайдкар к `bench-stage.mjs`: что здесь происходит, чтобы отлаживать, не перечитывая файл целиком.
> Источник истины — код и SPEC.md; заметка — карта. Меняешь файл — обнови заметку в том же коммите.

## Назначение
Правка мастера у предела в Chromium: раскладка по месту (`solveAfter`) и перерисовка сцены
(`Stage.render`) по её геометрии. Показывает выигрыш круга 62 для сцены: неизменённые раскрытые узлы —
те же объекты, и `Stage._patchSVG` перерисовывает только копии правленого узла.

## Главное
- Аргументы: число экземпляров (по умолчанию 999 — около 50 тыс. раскрытых узлов) и, необязательно,
  корень с `src/` другой ветки для сравнения (например, git worktree).
- Внутри страницы: мастер из 50 узлов, экземпляры сеткой; `Stage` на скрытом host; девять правок
  текста мастера подряд, цепочкой (`geo` из прошлого `solveAfter`).
- Выход — таблица `{count, layout, render}`, медианы в мс.

## Поток данных
document service (память) на свободном порту → Chromium → `import('/src/core.js')` из корня →
сборка документа → `solve` + `stage.render` → цикл: `applyOps` → `solveAfter` → `stage.render`.

## Инварианты
- Правки идут цепочкой, как в оболочке: память раскладки переходит от геометрии к геометрии.

## Подводные камни
- Шум большой (до ±30 %): сравнивать ветки подряд, по два-три прогона.
- Корень для сравнения должен содержать весь `src/` (страница грузит модули оттуда).

## Отладка
`env -u NODE_OPTIONS node tools/bench-stage.mjs 999` и
`env -u NODE_OPTIONS node tools/bench-stage.mjs 999 <worktree другой ветки>`.
