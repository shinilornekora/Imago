# `tools/critic/fmtloss.mjs` — заметка для LLM

> Сайдкар к `fmtloss.mjs`: что здесь происходит, чтобы отлаживать, не перечитывая файл целиком.
> Источник истины — код и SPEC.md; заметка — карта. Меняешь файл — обнови заметку в том же коммите
> (конституция, принцип VII; проверка — `node tools/sidecars.mjs`).

## Назначение
Инструмент критика (круг 45, воссоздан по `r44/fmtloss.mjs`): проверяет, что правка «будущей сборки»
той же версии движка не теряется при скользящем обновлении Document service (SPEC §9.18, §9.20).
Запускается руками, в `npm test` не входит.

## Главное
- Копирует `src`, `server`, `package.json` во временный каталог и мутирует копию ядра: opacity 0..2
  без подъёма `ENGINE_VERSION` (строки замены должны встретиться ровно по разу, иначе исключение).
- Поднимает два сервиса на одном хранилище: A — нынешний код, N — мутант.
- N пишет `set opacity 1.5` на доску демо-проекта, затем через A идут 55 правок имени.
- Ждём: A отвергает запись своей версии громкой строкой «…СВОЕЙ версии…» в `log.warn` и не пишет снимков.

## Поток данных
Хранилище — общий объект в памяти или одна база pg (`TEST_DATABASE_URL`, два пула). HTTP к обоим
сервисам через `fetch`; итог — `storageA.latestSnapshotMeta(id)` и собранные строки `log.warn` A.

## Инварианты
- Снимок поверх отвергнутой записи своей версии — потеря правки у всех; тогда выход 1.
- Нет громкой строки в логе — тоже выход 1.

## Подводные камни
- `node_modules` в копии — симлинк на корень; временный каталог удаляется в `finally`.
- Если в ядре поменяется текст правила opacity, строки `from` перестанут находиться — правьте их вместе
  с `tools/critic/format-mutants.mjs` (тот же мутант).
- `snapshotEvery: 50` — 55 правок нужны, чтобы снимок точно попытался записаться.

## Отладка
`env -u NODE_OPTIONS node tools/critic/fmtloss.mjs` (память) или с `TEST_DATABASE_URL=postgres://…`
(pg). Печатает статус записи N, голову, последний снимок и наличие громкой строки.
