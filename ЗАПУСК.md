# Запуск Imago Studio

## Совместная работа и агент на сервере — Docker Desktop

1. Установить и запустить Docker Desktop.
2. Запустить модель в LM Studio (если агент нужен): вкладка **Developer → Start Server**,
   загрузить модель. По умолчанию агент ждёт её на `http://localhost:1234/v1` этой машины.
3. Двойной клик по `START.cmd` в корне репозитория. Он создаёт `.env` из
   `deploy/env.example` (при первом запуске), собирает образы и ждёт, пока все сервисы
   станут здоровыми (`docker compose up --build -d --wait`), затем открывает браузер.
   Без `START.cmd`: `docker compose up --build -d --wait`.
4. Открыть http://localhost:8123/ — создастся первый проект, ссылка вида `?project=<id>`.
   Её можно открыть во втором окне или на другой машине в той же сети
   (`http://<ip-компьютера>:8123/?project=<id>`) — правки видны вживую.
5. Остановить — `STOP.cmd` (`docker compose down`); база остаётся в томе `imago-db`
   (`docker compose down -v` — стереть).

Что поднимается:

| Сервис | Что это | Здоровье |
|---|---|---|
| `db` | PostgreSQL 16, том `imago-db` | `pg_isready` |
| `document` | Document service (`server/document`: DSLR + DSLTS + Hub) | `GET /api/health` |
| `orchestrator` | агент (`server/orchestrator`: DUIL, DSLV, LLM); к базе не ходит; команды оболочки не узнаёт и не исполняет — это делает редактор | `GET /agent/health` |
| `web` | NGINX: статика клиента, `/api` и `/ws` → document, `/agent` → orchestrator | `GET /` |

Сервисы стартуют по очереди, каждый — когда предыдущий здоров. `/api/internal/` снаружи
закрыт (403): трассы агента пишет только orchestrator по внутренней сети.

## Модель агента

Настройки — в `.env` рядом с `docker-compose.yml` (образец с пояснениями: `deploy/env.example`):

| Переменная | По умолчанию | Что это |
|---|---|---|
| `LLM_BASE_URL` | `http://host.docker.internal:1234/v1` | адрес OpenAI-совместимой модели; `host.docker.internal` — это машина, где запущен Docker |
| `LLM_MODEL` | `local-model` | имя модели (как в LM Studio) |
| `LLM_KIND` | `openai` | `anthropic` — для Claude по API |
| `LLM_API_KEY` | пусто | ключ облачной модели; в ответы, трассы и логи не попадает |
| `INTERNAL_TOKEN` | `change-me` | общий секрет orchestrator → document для записи трасс; заглушку document не принимает — трассы не пишутся, всё остальное работает. Своё значение: `openssl rand -hex 24` |
| `IMAGO_PORT` | `8123` | порт редактора |
| `SNAPSHOT_EVERY` | `50` | снимок документа раз в столько правок |
| `SNAPSHOT_KEEP` | `5` | сколько последних снимков хранить (самый первый остаётся всегда) |
| `DB_TIMEOUT_MS` | `8000` | сколько ждать ответа базы, мс; дольше — сервис отвечает «занят», редактор повторит сам |

**Живой дизайн (круг 47).** На «собери экран …» агент сначала решает образ (палитра из материалов
предмета, пара шрифтов Google Fonts с кириллицей, мотивы), раскладывает по нему, затем критик
смотрит на снимок доски и при «шаблонно» даёт один круг доработки — это два-три вызова модели
сверх прежних. Под итогом команды видны образцы палитры, образ, шрифты и оценка критика.

| Переменная | По умолчанию | Что это |
|---|---|---|
| `AGENT_DIRECTION` | `1` | `0` — без шага арт-направления |
| `AGENT_CRITIC` | `1` | `0` — без критика и доработки |
| `AGENT_RENDER` | `1` | `0` — критик без снимка, по описанию доски |
| `LLM_VISION` | пусто | видит ли модель картинки: `1`/`0`; пусто — узнаётся по первому отказу (у `anthropic` — да) |

Снимок рисует `@resvg/resvg-js` (ставится с `npm ci` сам, необязательная зависимость), шрифты для
него orchestrator берёт с `fonts.googleapis.com` / `fonts.gstatic.com`; нет сети или модель без
зрения — критик судит по описанию доски, команда от этого не страдает.

Пределы сервисов (очереди, сроки, надгробия, воркеры агента — `WS_INFLIGHT`, `HTTP_WRITE_QUEUE`,
`WRITE_BODY_BYTES`, `BODY_TIMEOUT_MS`, `TOMB_*`, `RECENT_*`, `WORKERS`, `WORKER_JOBS`,
`QUEUE_MAX` и другие) тоже задаются в `.env`: полный список с умолчаниями и пояснениями — в
`deploy/env.example`, подробно — `server/document/README.md` и `server/orchestrator/README.md`.
Без строки в `.env` действует умолчание кода. NGINX пускает с одного адреса не больше 32
одновременных записей и 64 сокетов (вкладка держит один); сверх — `429 busy`, редактор
повторяет сам.

После правки `.env`: `docker compose up -d` (пересоберёт только то, что изменилось).

Если LM Studio запущена, а агент пишет «модель недоступна»: в LM Studio включить
**Serve on Local Network** (на Linux без этого контейнер до неё не достучится) и проверить
имя модели в `LLM_MODEL`.

## Команды оболочки — без агента

Отмену, масштаб, выделение, порядок слоёв, «обернуть в рамку», экспорт и ещё полсотни команд
редактор выполняет сам — без сети и без модели, поэтому они работают, даже когда агент
недоступен. Список открывается **Ctrl+K** (на Mac — **⌘K**) или знаком **«/»** в начале строки
команд: поиск по названию и по фразам, ↑/↓ — выбрать, Enter — выполнить, Esc — закрыть.
Полная справка по группам — `/помощь` или фраза «команды». Команду можно набрать и точно:
`/масштаб 150`, `/zoom 150`, `/тема тёмная`, `/удалить`, `/выровнять влево`; правки (дублировать,
скрыть, выровнять детей, зазор на шаг шкалы…) — обычные правки руками, отменяются одним Ctrl+Z.
Всё, чего в списке нет, — просьба к агенту: её говорят словами, без «/».

## Где работает агент

В шапке рядом с синхронизацией видно, кто выполняет команды. Решает это ответ
`/agent/health` (раз в 30 с и перед каждой командой), а не связь с документом:

* **агент: сервер** — команда уходит в orchestrator, стадии идут потоком, правка приходит
  всем участникам транзакцией. «Стоп» останавливает её на сервере. Если связь с агентом
  оборвалась посреди команды, редактор проверяет orchestrator и ждёт её транзакцию до
  25 секунд: пришла — правка на холсте (даже если пришла раньше, чем оборвался поток);
  не пришла или orchestrator перезапустился — «Команда «…» не выполнена — сервер агента
  перезапустился», текст команды возвращается в строку, рядом «Повторить». Если orchestrator
  останавливается штатно (`docker compose restart orchestrator`, обновление), идущая команда
  и ждавшие в очереди получают «Сервер агента перезапускается — команда не выполнена» с
  «Повторить»; когда ответит новый процесс, карточка сменится на «Сервер агента снова на связи».
* **агент: в браузере** — только если модель в браузере включил сам человек (шестерёнка →
  «Агент» → LM Studio). В серверной сборке своей модели у браузера по умолчанию нет.
* **агент недоступен** — orchestrator не отвечает, а своей модели в браузере нет. Команда
  не выполняется: «Сервер агента не отвечает — команда не выполнена. Правки руками
  сохраняются.», текст остаётся в строке, «Повторить» спрашивает orchestrator заново.

Если модель не отвечает самому orchestrator (`llm: "down"`), человек видит карточку
«Модель на сервере не отвечает» с подписью «Попробуйте позже.» и кнопкой «Повторить»; чинит это
администратор (LM Studio, `LLM_BASE_URL`). Когда модель вернулась, карточка сама сменяется на
«Модель на сервере снова отвечает».

Если проекта больше нет на сервере (базу восстановили из резервной копии без него), вкладка
показывает «Проекта больше нет на сервере» и кнопку «Сохранить как новый проект» — документ из
вкладки станет новым проектом. Работа лежит в журнале браузера (IndexedDB), поэтому переживает
и перезагрузку страницы: ссылка `?project=…` на пропавший проект откроет эту копию с той же
карточкой, а не другой проект. Пока проекта нет, в строке состояния есть кнопка «сохранить как
новый» (карточку можно закрыть), а команды агенту не отправляются — агенту нечего читать. Большой
документ (больше 3,5 МБ) отправляется частями — прогресс виден в карточке. Работа потеряется,
только если очистить данные сайта в браузере до сохранения.

## Проверить здоровье

```
docker compose ps                                  # все сервисы — healthy
curl http://localhost:8123/api/health              # {"ok":true,"engine":…}
curl http://localhost:8123/agent/health            # {"ok":true,…,"llm":"up","document":"up","model":"…"}
docker compose logs -f orchestrator                # что делает агент
```

`llm: "down"` — модель не отвечает (LM Studio не запущена или не тот адрес);
`llm: "unconfigured"` — `LLM_BASE_URL` пуст. Если сервис лежит, nginx отвечает JSON
`{"error":true,"code":"upstream_down","upstream":"orchestrator"|"document",…}` с
заголовком `X-Imago-Upstream: down`.

## Обновить

```
git pull
docker compose up --build -d --wait
```

Миграции базы идут сами при старте document (`server/document/storage/migrations`), данные в
томе `imago-db` сохраняются. Пока миграции идут, document отвечает на всё `503 migrating`, а
редактор держит правки в очереди и досылает их после.

* **Первая миграция на большой базе долгая.** Миграция 003 считает цепочку (`chain`) всего
  журнала пачками по 5000 записей: на миллионах правок это минуты. Healthcheck document
  ждёт до 10 минут (`start_period: 600s`) и не считает это падением; `--wait` вернётся, когда
  сервис здоров. Следить: `docker compose logs -f document`.
* **Несколько экземпляров document.** Миграции берут `pg_advisory_lock`: их выполняет один
  экземпляр, остальные ждут. Схема после каждой миграции годится и для старой, и для новой
  версии сервиса — смешанные версии на время обновления безопасны. Но обновлять
  рекомендуется **по одному**: остановили экземпляр (`stop_grace_period: 15s` — он
  дописывает начатое и закрывает сокеты), подняли новый, дождались `healthy`, потом
  следующий. Клиенты переподключаются сами.
* **Orchestrator** состояния не хранит: при перезапуске идущие команды теряются (люди видят
  «команда не выполнена — сервер агента перезапустился» и «Повторить»), записанное — уже в
  журнале.
* Открытые вкладки после обновления лучше перезагрузить: клиент со старой версией движка
  получит от сервера отказ (426) и покажет «Вышла новая версия редактора — обновите
  страницу»; его правки ждут в очереди вкладки и уйдут после обновления. Если наоборот
  страница уже новая, а сервер ещё старый, — «Сервер ещё не обновился»: правки тоже ждут.
* Версия движка (формата документа) у всех экземпляров document и orchestrator должна быть
  одна. Новый движок читает документы прежнего; экземпляр со старым движком проект, в
  журнале которого уже есть записи нового, не обслуживает (`503`, проект на нём «устарел»)
  — поэтому после обновления не оставляйте экземпляров старой версии.

### Резервная копия и восстановление из неё

Копию базы снимать **перед** обновлением:

```
docker compose exec -T db pg_dump -U imago -Fc imago > imago-$(date +%F).dump
```

Вернуть копию можно и под работающими сервисами — останавливать их не обязательно:

```
# 1. копию — в новую базу, затем подменить ею рабочую (соединения рабочей рвутся)
docker compose exec -T db createdb -U imago imago_restore
docker compose exec -T db pg_restore -U imago -d imago_restore < imago-2026-10-17.dump
docker compose exec -T db dropdb -U imago --force imago
docker compose exec -T db psql -U imago -d postgres -c 'ALTER DATABASE imago_restore RENAME TO imago'
```

**Лучше — в новую базу**, как выше: работа стоит секунды (пока подменяют базу), а не всё время
восстановления. **Восстановить в ту же базу** (`dropdb --force imago; createdb imago;` затем
`pg_restore -d imago …` или `psql -d imago -f копия.sql`) под работающими сервисами тоже можно — в
базу посреди восстановления никто не пишет:

* пока база пуста или в неё льётся копия, Document service отвечает на **все** запросы, кроме
  `/api/health`, `503` с `"detail":{"cause":"schema"}` и в базу не ходит (ни правки, ни новые
  проекты, ни трассы агента); `/api/health` → `503`, `"storage":"schema"`, `"phase":"empty"` или
  `"restore"`. Всё это время работа стоит: вкладки держат правки в очереди и дошлют их после;
* восстановление он узнаёт и по `pg_restore`, и по `psql`: подключён `pg_restore`; у таблиц ещё нет
  первичных ключей или триггеров (копия ставит их последними); чужой сеанс выполняет
  `COPY … FROM stdin`; чужой сеанс дольше полсекунды в запросе, а схема ещё меняется;
* конец восстановления замечает сам за 1–3 с (`/api/health` снова `200`), перезапуск не нужен.
  Не держите в это время открытым psql с долгим запросом к этой базе — сервис дождётся его конца.

Резервная копия (`pg_dump`) работе не мешает — её можно снимать под нагрузкой.

Чего ждать:

* Несколько секунд запросы получают `503` (соединения с базой оборвались) — редактор повторяет
  сам, правки ждут в очереди вкладки («сервер не может сохранить — правки ждут»).
* **Копия снята до обновления** (в ней нет миграций новой версии). Экземпляры document сами это
  замечают — при переподключении к базе или на первом же запросе, — догоняют миграции (под
  `pg_advisory_lock`: по одному) и продолжают работу; перезапуск не нужен. В логе: «в базе не
  учтены миграции … — базу восстановили из старой копии? Догоняю», затем «схема базы сверена».
  Пока догоняют, `/api/health` **честно отвечает `503`** (`"storage":"schema"`): проверка
  здоровья и балансировщик видят «не готов», а не «здоров» на схеме, которой код не знает. Это
  секунды: сначала догоняется схема, а долгое дозаполнение старых записей (на большом журнале —
  минуты) идёт фоном — сервис уже работает, `/api/health` отвечает `200` с `detail.backfill`.
  Дозаполняет один экземпляр; остальные не ждут его — здоровы и пишут сразу (`detail.backfill.by`:
  «другой экземпляр»). Так же и при старте на старой копии: сервис готов через секунды, а не после
  дозаполнения.
* **Откат развёртывания на прежнюю версию.** Проекты, в которых новая версия уже записала правки
  нового формата, прежний экземпляр не открывает и не пишет: `503` с `"detail":{"cause":"engine"}`
  (в логе одна строка «… движок N, а этот экземпляр работает с M»). Сборки старше той, где это
  появилось, такой проект откроют без новых правок, но и они не затрут его: база не примет снимок
  прежнего формата поверх правок нового. Верните новую версию — проекты откроются со всеми правками.
* Всё, что записано после снятия копии, из базы ушло — это и есть откат. Открытые вкладки
  получают снимок и переигрывают свои неподтверждённые правки (до суток давности); чего
  переиграть не удалось, называют словами. Проектов, созданных после копии, на сервере нет: у
  того, чья вкладка их держит, — карточка «Проекта больше нет на сервере» с «Сохранить как новый
  проект» (работа берётся из журнала браузера; сохранение большого проекта частями переживает
  перезагрузку вкладки и продолжается в тот же новый проект).
* Если `/api/health` долго держит `"phase":"failed"` — смотрите `docker compose logs document`
  («сверка схемы базы не удалась: …»): обычно это недоступная база или права.

Без сети клиент продолжает работать: правки копятся в браузере (IndexedDB), переживают
перезагрузку вкладки и досылаются, когда сервер вернулся; в шапке — «сервер недоступен · N правок ждут».
Если сервер на связи, но не может записать (лежит база), — «сервер не может сохранить — правки
ждут»: правки так же ждут в браузере и уходят, когда база вернулась. «Всё сохранено» в шапке
значит «на сервере»; до этого работа цела в браузере, и перезагрузка страницы её не теряет.

## Без Docker

* Свой PostgreSQL: `npm install`, затем
  `DATABASE_URL=postgres://… STATIC_DIR=. PORT=8123 node server/document/index.js` — сервис
  сам отдаёт клиент, NGINX не нужен. Агента на сервере тогда нет (`/agent/` — 404): в шапке
  «агент недоступен», и команды не выполняются, пока вы не включите модель в браузере
  (шестерёнка → «Агент» → LM Studio) — тогда «агент: в браузере». Правки руками и совместная
  работа от этого не зависят. Orchestrator отдельно:
  `DOCUMENT_URL=http://127.0.0.1:8123 LLM_BASE_URL=http://127.0.0.1:1234/v1 PORT=8090 node server/orchestrator/index.js`
  (до клиента он доходит через NGINX: `deploy/nginx.conf`).
* Соло без сервера: `node tools/build.mjs`, затем `dist/local/START.cmd` — агент в браузере.
  Проектов много, как файлов: кнопка-папка «Проекты» (Ctrl/⌘+O, `/проекты`, `/новый проект`,
  `/открыть <имя>`). Тела проектов — в IndexedDB браузера, список — в localStorage; без IndexedDB —
  только localStorage (около 5 МБ на все, о чём сказано плашкой), в приватном режиме — память
  вкладки («проекты не сохраняются в этом браузере»). Прежний единственный документ при первом
  открытии становится первым проектом. Импорт JSON без сервера — новым проектом.

## Тесты

`npm test` — все; с базой: `TEST_DATABASE_URL=postgres://… npm test`. Проверка конфигов
развёртывания — `test/deploy.test.mjs`; если в системе есть `nginx`, он же проверяет
настоящий `deploy/nginx.conf` (`nginx -t` и живые маршруты).
