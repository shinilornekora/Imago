# Imago Studio — MVP агентного редактора макетов

AI-first редактор: человек формулирует задачу словами (текстом, а в локальной сборке — голосом),
агент строит и правит макет; ручные инструменты есть, но нужны редко. Документ построен по
архитектуре A3 из архитектурного проекта: структурный DSL — источник истины, геометрия
вычисляется решателем, ручные сдвиги хранятся как `override` отсоединённого узла.

Две оболочки, один код:
* **артефакт claude.ai** — агент через `claude.use("sample")`, команды текстом (микрофон в артефактах запрещён платформой);
* **локальная сборка** — статические файлы + `START.cmd`, агент через OpenAI‑совместимый API LM Studio
  (`http://localhost:1234/v1`), голосовой ввод через Web Speech API.

## 1. Модули и контракты

Файлы (ES‑модули, без сборки, без зависимостей кроме шрифтов):

```
index.html      каркас, разметка панелей
styles.css      токены темы, вёрстка оболочки
src/core.js     документ, операции, решатель, отрисовка, взаимодействия  ← агент A
src/brain.js    провайдеры моделей, схемы, промпты, конвейер команд      ← агент B
src/app.js      оболочка: панели, командная строка, голос, история       ← оркестратор
```

### 1.1 `core.js` экспортирует

```js
export function createDoc(seed?) -> Doc
export function applyOps(doc, ops) -> {doc, error?}        // иммутабельно, с проверкой
export function invertOps(doc, ops) -> ops                 // для отмены
export function solve(doc) -> Geometry                     // детерминированно
export function validate(doc, geo) -> Violation[]
export class Stage {                                       // отрисовка + ввод
  constructor(host: HTMLElement, opts: {onSelect, onCommit, onHover})
  render(doc, geo, state)                                  // state: {selection, preview, diff, zoom, pan}
  fitTo(ids?: string[])                                    // вписать во вьюпорт
  screenshot() -> Promise<Blob>                            // PNG активного артборда
  toSVG(artboardId) -> string
}
export const ops = { create, remove, set, move, setToken } // конструкторы операций
```

### 1.2 Модель документа

```ts
Doc = { id, version:int, root:NodeId, nodes:Record<NodeId,Node>, tokens:Tokens, meta:{name, createdAt} }
Node =
  | {type:'page',   id, name, parent:null, children:NodeId[]}
  | {type:'frame',  id, name, parent, children, layout, size, fill?, stroke?, radius, pos?, override?, clip?}
  | {type:'text',   id, name, parent, characters, style, color?, align, size, pos?, override?}
  | {type:'rect'|'ellipse', id, name, parent, size, fill?, stroke?, radius, pos?, override?}
  | {type:'image',  id, name, parent, src?, fill?, radius, size, pos?, override?}
Layout = {mode:'none'|'row'|'column', gap, padding:{t,r,b,l}, align:'start'|'center'|'end'|'stretch', justify:'start'|'center'|'end'|'between', wrap:boolean}
Size   = {w:SizeSpec, h:SizeSpec},  SizeSpec = {mode:'fixed', value} | {mode:'hug'} | {mode:'fill'}
Tokens = {colors:Record<string,'#rrggbb'>, type:Record<string,{fontSize,fontWeight,lineHeight,letterSpacing?,font?}>, spacing:number[], radii:number[]}
Override = {x,y,w,h}   // абсолютная геометрия отсоединённого узла относительно родителя
```

Артборд — фрейм, чей `parent === root`; у него обязателен `pos:{x,y}` (координаты на бесконечном холсте).

### 1.3 Операции

Пять, как в архитектурном проекте: `create{node,index?}`, `remove{id}`, `set{id,path,value?}`,
`move{id,parent,index}`, `setToken{path,value?}`. Применение иммутабельно и перепроверяет узел схемой;
защищённые пути (`id`, `type`, `parent`, `children`) менять нельзя. `remove` уносит поддерево.
Каждая пользовательская или агентная правка — **транзакция**: массив операций + инверсия для отмены.

### 1.4 Решатель

Порядок: для каждого артборда рекурсивно сверху вниз. Режимы `row`/`column` раскладывают детей в поток
с `gap`, `padding`, `align`, `justify`, `wrap`; `none` — свободное размещение по `pos`. Размеры: `fixed` —
значение; `hug` — по содержимому (текст меряется через `measureText` на offscreen‑canvas с теми же
шрифтами, что и отрисовка); `fill` — остаток по главной оси, растяжение по поперечной. Узел с `override`
позиционируется абсолютно внутри родителя и не участвует в потоке.
Решатель обязан быть чистой функцией: одинаковый документ → одинаковая геометрия (тест на равенство хэшей).

### 1.5 Отрисовка

`Stage` рисует в **SVG** (чёткий текст, простой хит‑тест, экспорт «как есть»), поверх — слой
интерфейса (рамки выделения, ручки, подсказки). Поддержать: зум колесом (к курсору), панорама
пробелом/средней кнопкой, выделение кликом, Shift+клик, рамка выделения, перетаскивание (создаёт
`override` или меняет порядок в потоке — по проекции сдвига: вдоль главной оси ≥0.7 → `move`, иначе
`override`), ресайз за 8 ручек, двойной клик по тексту — инлайн‑правка, Delete, Ctrl/Cmd+Z/Shift+Z,
Ctrl/Cmd+D дублирование, стрелки — сдвиг на 1/10 px. Анимация применения агентной транзакции:
изменённые узлы подсвечиваются и плавно переезжают (FLIP, 220 мс, уважая `prefers-reduced-motion`).

### 1.6 `brain.js` экспортирует

```js
export function makeProvider(cfg) -> {name, complete(messages, schema, opts) -> Promise<object>}
   // cfg.kind: 'claude' (claude.use('sample').json) | 'lmstudio' (OpenAI-совместимый /chat/completions)
export async function runCommand({doc, selection, utterance, provider, onStage, signal}) -> {
  ops, preview:{doc, geo}, plan:{title, summary, steps[]}, warnings[], usage
}
export async function runVariants({doc, selection, utterance, provider, n}) -> [{label, ops, preview}]
export const SCHEMAS = { plan, tree, patch }
```

Конвейер одной команды: классификация (создать / изменить / оформление / вопрос) → выбор области
(выделение, иначе активный артборд, иначе весь документ) → план (короткий JSON) → генерация
(дерево для создания либо список точечных правок для изменения) → материализация в операции → решатель
→ валидаторы → при ошибках одна попытка починки с обратной связью → результат.
Стадии транслируются в `onStage({stage, text, partial?})`, чтобы интерфейс показывал ход работы.

Схема ответа модели — компактное дерево (как в layout-agent): `{type, name?, layout?, size?, fill?, text?, style?, children?}`,
где размер — число | `"hug"` | `"fill"`, цвет — имя токена или `#rrggbb`, отступы — число | `[v,h]` | `[t,r,b,l]`.
Точечная правка — `{op:'set'|'remove'|'create'|'move', target:'<id|name|роль>', path?, value?}` с разрешением цели по имени/роли.

### 1.7 Голос (локальная сборка)

`webkitSpeechRecognition`/`SpeechRecognition`, язык `ru-RU`, непрерывный режим с промежуточными
результатами; кнопка удержания (Space вне ввода) и режим «всегда слушать» с ключевой фразой.
В артефакте API недоступен — кнопка скрыта, в подсказке сказано, где голос работает.

## 2. Что должно работать в MVP

1. Пустой холст с примером: два артборда (мобильный экран и десктопный блок), заполненные реальным содержимым.
2. Команда текстом → план → макет; видно, что делает агент; результат появляется анимацией.
3. Правка выделенного: «сделай заголовок крупнее», «замени кнопку на две», «сделай тёмную тему».
4. Три варианта по одной команде, выбор кликом.
5. Ручная правка: перетащить, изменить размер, поменять текст, удалить; агент уважает ручные сдвиги (`override`).
6. Отмена/повтор любой транзакции, включая агентные, с понятной историей.
7. Экспорт: PNG артборда, SVG, JSON документа; импорт JSON.
8. Сохранение: в артефакте — `db` (документы пользователя), локально — файл рядом с приложением.
9. Тема интерфейса светлая/тёмная, документ живёт в своих токенах независимо от темы интерфейса.

## 3. Дизайн

Тёмный «студийный» интерфейс, светлый холст. Токены:

```
--ink        #0D0E12   фон приложения
--panel      #14161C   панели
--line       #222735   разделители
--text       #E8EAF0
--muted      #8A92A6
--accent     #FF6B3D   действие пользователя (команда, выделение)
--agent      #38D6B0   активность агента (стадии, подсветка изменений)
--warn       #F0B429
```
Шрифты: интерфейс — IBM Plex Sans; числа и ярлыки — IBM Plex Mono; заголовок приложения и пустые
состояния — Instrument Serif. В светлой теме те же роли, ground `#F7F6F3`, панели `#FFFFFF`.

Композиция: слева узкий рельс со страницами и слоями (сворачивается), в центре холст во всю высоту,
справа инспектор (появляется только при выделении), снизу по центру — командная строка: она и есть
главный элемент, над ней лентой идут стадии работы агента.

## 4. Отклонения реализации от этого проекта

Проект писался до сборки; ниже — где готовое приложение сознательно разошлось с ним.
Полностью изменения и их причины описаны в `ОТЧЁТ.md`.

* **Акцент интерфейса — холодный индиго, а не `#FF6B3D`.** Оранжевый остался цветом
  ДОКУМЕНТА (кнопка внутри макета), и два оранжевых на одном экране спорили за роль
  «главное действие». Интерфейсный акцент уведён в индиго; цвет агента (`--agent`) и
  предупреждения сохранены.
* **Голос — кнопка микрофона (или клавиша V), а не удержание пробела.** Пробел занят
  панорамой холста; одновременное срабатывание включало панораму и распознавание сразу.
  Из §1.7 сделано: непрерывное распознавание с промежуточными результатами, граница команды
  по паузе 1,2 с, режим «слушать постоянно» отдельным переключателем в настройках
  (по умолчанию выключен, микрофон сам гаснет после 10 с тишины). Не сделана только
  ключевая фраза: режим включается кнопкой, а не словом.
* **Часть команд выполняет сама оболочка, не обращаясь к модели.** Отмена и повтор
  («верни как было», «отмени два раза»), просьба о вариантах, выбор варианта, переключение
  артборда, масштаб и «вписать», выделение слоя по имени, экспорт, открытие панелей.
  Так голосом управляется не только макет, но и сам редактор — в том числе когда модель
  не подключена. Артборд, который человек видит, задаёт область работы агента, поэтому
  «покажи сводку недели» — это ещё и указание агенту, где работать.
* **Кнопка микрофона в артефакте не скрыта, а выключена** с пояснением: так видно, что
  голос существует и где он работает.
* **Появилось намерение `clarify`** (переспрос) сверх четырёх из §1.6: для голоса это
  обязательный случай — недослышанная фраза не должна становиться макетом.
* **Выжимка документа описывает весь документ**, а не выбранную область: область работы
  размечается пометками внутри полной картины. Без этого агент не мог сослаться на
  соседний экран.
* **`Stage.fitTo(ids, {padding, inset, maxZoom})`** принимает поля вьюпорта: командная
  строка лежит поверх холста, и без вычета её высоты низ макета всегда срезан.

## 5. Компоненты: библиотека как словарь агента (круг 19)

Проектное решение, принятое по итогам разговора с пользователем: сначала строится
UI-библиотека, потом продукт собирается из неё. Раздел описывает, КАК это лежит в
документе. Он обязателен к соблюдению всеми тремя частями (`core`, `brain`, оболочка) —
это общий контракт, а не предложение.

### 5.1 Почему именно так

Документ и без того хранит структуру, а не геометрию, поэтому компонент здесь — это
не «связанная копия, которую надо синхронизировать», а **именованное поддерево плюс
объявленные пропсы**. Синхронизировать нечего: геометрию всё равно считает решатель.

Главное следствие — не переиспользование, а **сужение словаря агента**: модель выбирает
из компонентов продукта вместо того, чтобы сочинять кнопку с нуля. Из этого:
выжимка документа схлопывается (экземпляр — одна строка вместо поддерева),
генерация дешевеет и попадает точнее, а «агент собрал не из нашей системы»
перестаёт быть вопросом ревью и становится невозможным состоянием документа.

### 5.2 Пять операций не растут

Новых операций НЕТ. Компонент — это поле на обычном узле, поэтому `create/remove/set/
move/setToken` покрывают всё, а `applyOps` (неизменяемость), `invertOps` (отмена) и
транзакция оболочки работают без единой правки в своей механике.

### 5.3 Где живут мастера

У корня документа появляется ещё один потомок — **библиотека**: узел с `role: 'library'`,
`type: 'page'`. Не «второй» по счёту: контракт — «ребёнок корня с `role: 'library'`»,
индекс не фиксирован (в демо она идёт последней, чтобы номера досок не поехали).
Это единственное место, где странице разрешён родитель.

Библиотека НЕ доска: `isArtboard` для неё ложь, в список досок не попадает, в «все доски»
при оформлении не считается, в экспорт «всё» не идёт. Её **прямые** дети — мастера
компонентов; поле `component` на узле, лежащем не в библиотеке, мастером его не делает.
На холсте библиотека при этом РИСУЕТСЯ, рядом с досками и без подписи доски: иначе
обещание «правка мастера меняет все экземпляры» человеку нечем показать.

Такое размещение выбрано сознательно: одна карта узлов на документ, поэтому операции,
отмена, валидатор и решатель не получают особых случаев.

### 5.4 Мастер

Мастер — обычный узел (чаще `frame`), лежащий в библиотеке, с новым полем:

```js
component: {
  name: 'Кнопка',            // как его назовёт человек и модель
  props: [                    // что разрешено менять у экземпляра
    { name: 'текст', kind: 'text',   target: '<id узла внутри мастера>', path: 'characters' },
    { name: 'вид',   kind: 'enum',   target: '<id>', path: 'fill', values: ['accent', 'surface'] },
    { name: 'виден', kind: 'bool',   target: '<id>', path: 'visible' }
  ]
}
```

`kind` — один из `text | enum | color | number | bool`. `target` обязан быть узлом ВНУТРИ
этого мастера, `path` — тем же путём, что понимает `set`. Реестра компонентов в документе
нет: список компонентов — производная от детей библиотеки, считается на лету.

### 5.5 Экземпляр

Новый тип узла — `instance`:

```js
{ id, type: 'instance', parent, name?, of: '<id мастера>',
  props: { 'текст': 'Оплатить', 'вид': 'accent' },
  size?, override?, visible? }
```

Детей у экземпляра нет: его содержимое — это мастер. `props` могут содержать ТОЛЬКО
объявленные имена; неизвестное имя — негодная операция (`bad-op`), как и любое другое
нарушение схемы, а в документе, пришедшем из файла, такое имя просто не применяется
и ловится валидатором (`unknown-prop`).

Оси `size` необязательны по отдельности: незаданная берётся у мастера. Поэтому экземпляр
кнопки получает её размер сам, а тяга за одну кромку не превращает вторую ось в `fixed`.

### 5.6 Раскрытие при решении

`solve` раскрывает экземпляр на лету: раскладывает поддерево мастера, применяя пропсы,
и кладёт прямоугольники под **синтетическими** идентификаторами `"<id экземпляра>/<id
узла мастера>"`. Корень мастера — исключение: он раскрывается под id САМОГО экземпляра,
поэтому `geo.rects[<id экземпляра>]` и есть рамка экземпляра, а не вторая рамка поверх неё.

В `doc.nodes` раскрытых узлов нет и не будет — в этом и смысл: документ остаётся
коротким, а геометрия по-прежнему функция от структуры. `geo.order` тоже содержит только
узлы документа: поэтому клик попадает в экземпляр целиком, а не в его внутренность.

Требования к раскрытию: оно детерминировано (тот же документ — тот же `hashGeometry`);
глубина вложенных экземпляров ограничена (предел выбрать и назвать); компонент,
который прямо или косвенно содержит экземпляр самого себя, — нарушение, а не зависание.

### 5.7 Отсоединение

«Отсоединить» превращает экземпляр в настоящую копию поддерева (`cloneSubtree`) —
одна транзакция `remove` + `create`, отменяемая как всё остальное. Это тот же приём,
которым уже описан ручной сдвиг: исключение помечено явно, а не спрятано.

### 5.8 Новые коды валидатора

* `dead-instance` — `of` указывает на узел, которого нет, или на узел вне библиотеки;
* `unknown-prop` — в экземпляре пропс, которого мастер не объявлял;
* `component-cycle` — компонент содержит экземпляр самого себя;
* `instance-too-deep` — вложенность экземпляров глубже предела.

Первые три — блокирующие (документ нельзя показать как верный), четвёртый — `warn`.

### 5.9 Что видит модель

В выжимке библиотека идёт отдельным блоком ПЕРЕД документом — это словарь:

```
БИБЛИОТЕКА (собирать только из этого):
  Кнопка(текст, вид: accent|surface)
  Карточка товара(заголовок, цена, картинка)
```

Экземпляр в выжимке — одна строка: `Кнопка "Оплатить" вид=accent`, без внутренностей.
Создавать экземпляр модель может только ссылкой на существующий компонент; выдуманное
имя отсекается там же, где сейчас отсекаются выдуманные слои.

### 5.10 Чего этот круг НЕ делает

Зазоры, скругления и размеры остаются числами. Перевод их на ссылки в шкалу
(`spacing.4` вместо `16`) — следующий шаг, он стоит на компонентах, а не наоборот.

## 6. Шкалы как ссылки: в документе нет числа 16 (круг 20)

Второй шаг плана «библиотека, потом сборка». Сейчас `layout.gap: 16` — просто число; шкала
`tokens.spacing` нужна только для мягкого замечания «вне шкалы» и шага по умолчанию. То есть
система есть, но документ ей не подчинён: смена шкалы ничего не переверстывает, а «сделай
просторнее» — это прибавка пикселей, а не шаг по шкале. Раздел описывает, как это меняется.
Он обязателен для всех трёх частей приложения.

### 6.1 Ссылка на шаг шкалы

Значение отступа или скругления может быть **ссылкой на шаг шкалы** — строкой вида
`'spacing.<индекс>'` или `'radii.<индекс>'`, где индекс — позиция в массиве
`tokens.spacing` / `tokens.radii`:

```js
layout: { gap: 'spacing.6', padding: { t: 'spacing.8', r: 'spacing.7', b: 'spacing.8', l: 'spacing.7' } }
radius: 'radii.4'
```

Число по-прежнему допустимо — это значение «мимо шкалы», и валидатор о нём говорит как
сейчас (`off-scale`, info). Ссылка на несуществующий шаг — `dead-scale-ref` (error).

Индекс, а не имя, выбран сознательно: индексы устойчивы при самой частой правке шкалы —
изменении значений (в том числе всей лестницы разом), — и не требуют менять формат
`tokens.spacing`, который уже понимают `setToken` и мозг. Вставка шага В СЕРЕДИНУ шкалы
сдвигает ссылки; это редкая операция, и она оформляется отдельной функцией ядра, которая
переписывает ссылки вместе со вставкой. Правка шкалы «в лоб» через `setToken spacing.6`
меняет только значение шага — ровно то, ради чего всё делается.

### 6.2 Какие поля

Ссылками становятся: `layout.gap`, `layout.padding.{t,r,b,l}` → `spacing`; `radius`
(и покорнерные формы, если они есть) → `radii`. Размеры (`size.*.value`), позиции и
типографика этим кругом НЕ трогаются — у размеров нет шкалы, а у типографики уже есть
своя система (`tokens.type`).

### 6.3 Решатель и всё, что читает эти поля

Ссылка разрешается в число на входе решателя — одной функцией ядра, и той же функцией
пользуются валидатор, экспорт, инспектор и мозг. Читать `layout.gap` как число напрямую
больше нельзя нигде; это правило проверяется тестом на демо-документе, где все отступы
и скругления — ссылки.

### 6.4 «То же самое» — одно на всех

`set layout.gap = 16` при текущем `'spacing.6'` (= 16) — правка тем же значением: поле
остаётся байт в байт (`keepFieldForm`), мозг считает её пустой (`sameAsNow`). Обратное
тоже: `set layout.gap = 'spacing.6'` при текущем `16` — НЕ пустая правка: число становится
ссылкой, и это изменение смысла, хотя картинка та же. Механический тест мозга «зеркало
совпадает с настоящим `applyOps`» расширяется на эти формы.

### 6.5 Миграция

`ensureScaleRefs(doc)` — один вызов, идемпотентный: число, ТОЧНО совпадающее с шагом
шкалы, становится ссылкой на этот шаг; число мимо шкалы остаётся числом. Демо-документ
после `createDoc()` уже целиком на ссылках. Оболочка зовёт миграцию там же, где
`ensureLibrary`.

### 6.6 Что видит модель

В выжимке шкалы печатаются с индексами и значениями один раз, в шапке:
`spacing: 0=0 1=2 2=4 3=6 4=8 5=12 6=16 7=20 8=24 9=32 10=40 11=48 12=64`. У узлов отступы
печатаются как `gap spacing.6(16)` — и ссылка, и число, чтобы модель могла и рассуждать
о пикселях, и отвечать ссылкой. Правило промпта: отступы и скругления задавать ссылкой на
шаг; «плотнее/просторнее» — это шаг вниз/вверх по шкале, а не прибавка пикселей. Число
от модели, совпадающее с шагом, мозг превращает в ссылку сам. Число мимо шкалы: если его
назвал сам человек (оно есть в реплике) — остаётся числом, и об этом сказано; если число
придумала модель (16 + 8 вместо шага вверх) — берётся ближайший шаг, и об этом тоже
сказано («28 — мимо шкалы скруглений, взял ближайший шаг 24. Скажите «ровно 28», если
нужно именно это число»). Ноль — «без отступа», не обсуждается.

### 6.7 Что видит человек

Человек шкалу не обязан знать. Инспектор показывает значение в пикселях и признак «по
шкале»; выбор — из шагов шкалы с возможностью «своё число». В сообщениях: «Зазор 16 → 24
(шаг шкалы)». Редактор шкал — отдельная шторка: значения шагов, и правка любого сразу
переверстывает всё, что на него ссылается. Слово для человека — «шкала отступов» и
«шкала скруглений», без «spacing» и «radii».

## 7. Распознавание намерений оболочки: не словарь, а классификатор (решение, круг 21)

Сейчас команды оболочки — отмена, повтор, «стоп», варианты, переключение доски, «сделай из
этого компонент», «отсоедини» — узнаются словарём русских регулярок (`shellIntent`,
`recognizeAction`, `recognizeVariants`, `recognizeComponentIntent`). Это работает быстро
и без модели, но привязано к языку: человек может говорить на любом, а словарь — нет.
Решение: **словарь заменяется классификатором намерений на многоязычных эмбеддингах.**

* Намерения оболочки (двадцать-тридцать) описываются примерами на нескольких языках.
  Реплика превращается в вектор маленькой локальной моделью (миллисекунды, CPU) и
  сравнивается с примерами. Уверенное попадание — команда исполняется сразу, без большой
  модели; иначе реплика идёт планировщику, как сейчас. Язык перестаёт быть параметром.
* «Стоп» дополнительно держится точным совпадением по короткому списку на языках
  интерфейса: цена промаха у команды прерывания — продолжающаяся работа агента.
* Ответы на переспрос и выбор варианта («второй», «этот») — тот же классификатор, но с
  контекстом «сейчас задан вопрос».
* Основной конвейер (план → патч) от языка не зависит и не меняется: большая модель
  понимает любой, имена слоёв и компонентов берутся из документа.

Пока классификатора нет, словарь остаётся как есть; **расширять его новыми формами
больше не нужно** — следующие правки распознавания делаются классификатором.

## 8. Целевая архитектура системы (решение, круг 21; уточнено в круге 22)

Принято на доске вместе с пользователем. Имена ниже — канонические; код и разговоры
ведутся в них. Текущее приложение (§1–7) — всё в браузере; этот раздел описывает, во что
оно разъезжается, когда библиотека становится общей на команду и продукты, а документ
правят несколько человек и агент одновременно.

Круг 22 уточнил (после независимого ревью, `docs/07`): процессов два, а не восемь; имена
с доски — модули с чёткими границами внутри них; клиент — полная реплика с локальным
журналом; слияние транзакций не отказывает; библиотека — проект вида `library`.

### 8.1 Действующие элементы

| Имя | Где живёт | Обязанность |
|---|---|---|
| **CLIENT** | браузер | оболочка + движок `core`; **полная реплика**: локальный журнал (IndexedDB), свои правки применяет всегда и сразу, отправка и приём — отдельный процесс синхронизации (`src/sync.js`); присутствие (кто в сети, выделение) по тому же сокету, без записи |
| **NGINX** | вход | TLS, статика клиента, прокси `/api` и `/ws` → Document service, `/agent` → Orchestrator |
| **Document service** | процесс «документ» | модули **DSLR** (чтение: снимок + хвост журнала = стейт и номер головы), **DSLTS** (секвенсор и единственный писатель: перекладка, номер, запись, снимок раз в N), **Hub** (рассылка транзакций и присутствия по WebSocket). Держит голову каждого открытого проекта в памяти. Содержит движок |
| **Orchestrator** | процесс «агент» | ведёт команду по шагам; модули **JEV** (классификатор: команда оболочки и какая), **DUIL** (чтение библиотек — срез проекта вида `library`: компоненты с пропсами, шкалы, версии), **DSLV** (движок: применяет патч к копии стейта, считает раскладку, судит форму и смысл), **LLM** (клиент к модели). **К базе не прикасается**: стейт берёт у DSLR, пишет через DSLTS как любой клиент |
| **LLM** | внешняя модель | Claude / LM Studio / любой OpenAI-совместимый; получает промпт, отдаёт патч в терминах DSL |
| **База** | PostgreSQL | журнал операций каждого проекта (источник истины), снимки, проекты — в том числе вида `library`, трассы агента |

Каждое имя с доски — каталог-модуль со своим интерфейсом; вынести модуль в отдельный
процесс потом — это добавить транспорт, а не переписать.

Модель не пишет DSL никогда: она предлагает патч, DSLV превращает его в операции,
DSLTS записывает. Два места, где недоверенный ответ становится доверенным: DSLV и
слияние в DSLTS.

### 8.2 Поток одной команды (нумерация с доски)

```
0   CLIENT ↔ Document service (DSLR): открыть проект — снимок + хвост, номер головы; дальше WS
1   человек → NGINX (HTTPS)            2   NGINX → CLIENT (статика)
3   CLIENT → Orchestrator: команда (текст, выделение, активная доска, номер базы)
4/5 Orchestrator ↔ JEV: команда оболочки?  да → событие shell по 7b: клиент исполняет команду
    оболочки сам (отмена, масштаб, выделение…; модель и запись не нужны, §10.5); нет → дальше
4a/5a Orchestrator ↔ DSLR: стейт + номер головы
6/7 Orchestrator ↔ DUIL: словарь компонентов (DUIL читает проекты-библиотеки через DSLR по HTTP)
8/9 Orchestrator ↔ LLM: промпт → патч
10/11 Orchestrator ↔ DSLV: стейт + патч → годные операции | нарушение → снова 8 (ретрай, один раз)
12/13 Orchestrator ↔ DSLTS: транзакция (base_seq, ops) → seq, применённые операции, отброшенные
12a DSLTS → база (журнал, раз в N — снимок);  Hub → всем подписчикам проекта, автору тоже
7b  Orchestrator → CLIENT: стадии по ходу работы, событие shell, итог
T   Orchestrator → Document service: трасса команды, POST /api/internal/traces (§10.4)
M   CLIENT → DSLTS: ручная правка = транзакция тем же путём, что 12; мимо очереди агента
```

Клиент после открытия документ целиком не получает: только транзакции и номера, применяет
их своим движком — картинка совпадает с той, что посчитал DSLV, потому что движок один.

### 8.3 Правила, без которых это не работает

* **Движок один.** `core` исполняется в CLIENT, в DSLTS (слияние и применение) и в DSLV
  без изменений. Переигрывание журнала — строгий `applyOps` записанных операций в порядке
  `seq`; детерминизм решателя делает картинку сервера и клиента одинаковой.
* **Журнал — источник истины, снимок — производная.** Снимок = документ целиком (`root`,
  `nodes`, `tokens`, `meta`) + версия движка. Каждая транзакция получает номер `seq` от
  DSLTS; клиент и Orchestrator шлют операции с номером базы `base_seq`.
* **Модель согласованности — CP по проекту.** Сервер — единственный арбитр порядка;
  когда он недоступен, никто не фиксирует правки — это цена единственного арбитра, её
  платят все серверно-авторитетные редакторы. Актуальность отстаёт всегда (чужие правки
  приходят с задержкой на круг до сервера), при разрыве — неограниченно. Клиент при этом
  **продолжает работать**: он реплика с локальным журналом, правки принимаются всегда,
  переживают перезагрузку вкладки и досылаются при воссоединении. Неподтверждённое видно
  как неподтверждённое — молча потерять работу нельзя.
* **Слияние не отказывает.** DSLTS перекладывает транзакцию поверх пришедших после
  `base_seq` по правилам §9.6 — операция за операцией. Транзакция целиком не отклоняется
  никогда; отдельная операция отбрасывается только по этим правилам (узел уже удалён,
  перемещение в цикл), и автору об этом сказано (`dropped`). Отказа «документ изменился»
  человек не видит никогда. В журнал ложится **применённая** форма операций.
* **Валидатор — линтер для человека, ворота для агента.** Ручные правки не проверяются
  перед записью: документ может временно содержать `dead-instance`, `overflow`,
  `dead-scale-ref` — это бейджи в слоях, а рендер такое переживает (заглушка вместо
  мёртвого экземпляра, запасное число вместо мёртвой ссылки). Агентная транзакция
  проходит DSLV до записи — чтобы ловить ошибки модели, а не чужие правки; после слияния
  агент при необходимости делает круг починки на свежем стейте.
* **Живое — это оптимистичное применение + рассылка транзакций.** Своя правка рисуется
  сразу своим движком; сервер присылает её применённую форму с номером; чужие прилетают
  транзакциями и применяются тем же движком. На клиенте: `view = replay(confirmed, pending)`.
* **Идемпотентность.** `tx_id` генерирует клиент; `UNIQUE(project_id, tx_id)` в журнале;
  повторная отправка возвращает тот же результат. Переподключение — с последнего
  известного `seq`; если он ниже хранимого хвоста, клиент получает снимок и переигрывает
  свою очередь поверх него — штатный путь.
* **Id узлов и транзакций генерирует клиент**, глобально уникальные: 12 случайных
  символов base36 (~62 бита; на проект в сто тысяч узлов столкновение ~10⁻⁹) — длиннее
  нельзя без причины, id ходят в выжимке к модели и стоят токенов на каждой команде.
  `create` с уже занятым id — повтор, не конфликт: отбрасывается как `exists`.
* **Отмена — новая транзакция, а не откат.** «Отменить» = дописать обратные операции
  своей транзакции с пометкой `undo_of`, повтор — `redo_of`; второе «отмени» отменяет
  предыдущую *свою* транзакцию, а не отмену. Инверсия считается на клиенте от его текущего
  вида **на уровне пути операции**: `set id a.b.c` ↔ `set id a.b.c <было>`; если до правки по
  голове пути лежал скаляр, а стал объект (или наоборот), возвращается голова целиком —
  иначе форму не восстановить. Пересечение с чужой правкой того же листа решает порядок
  `seq`: позже — побеждает.
* **Версия формата движка** (`core.ENGINE_VERSION`) — в каждой транзакции и снимке. Клиент
  со старой версией получает `426` и просьбу обновиться; миграция формата — системная
  транзакция, а не тихая правка снимка.
* **Ретрай ограничен** одним кругом починки; не помогло — берётся лучший вариант, и
  человеку сказано, что не удалось.
* **«Стоп»** ловится на клиенте точным совпадением до сети.
* **Команды агента — в очередь на проект.** Две одновременные команды разным людям
  выполняются по очереди: модель рассуждает над стейтом, который вторая команда уже
  меняет. Ручные правки идут мимо очереди и не ждут агента.
* **Текст меряется одинаково там, где судят раскладку.** DSLTS геометрии не считает —
  операции структурны. DSLV обязан мерить текст тем же измерителем, что клиент (по файлам
  шрифтов; крючок `solve(doc, {measureText})` есть); пока измеритель не общий,
  `overflow` у агента — предупреждение, не отказ.
* **Библиотека = проект вида `library`.** Свой журнал, как у любого проекта; версия —
  помеченный снимок (`library_versions`); продукт **импортирует** мастера: они
  материализуются в его документе под стабильными id системной транзакцией; «обновить
  до v5» = одна транзакция миграции, которую строит DUIL по разнице мастеров. Один
  механизм записи на всё.
* **Чистка журнала — по запасу, не по календарю, и не удаляет.** *(Не реализовано, открыто:
  холодной партиции и суточной чистки в коде нет — журнал растёт целиком в одной таблице,
  снимки хранятся последние 5 и seq 0, §9.8. Ниже — решение, по которому её делать.)* Раз в сутки операции
  старше последнего снимка, кроме последних N транзакций каждого автора и всего моложе
  недели, **уносятся в холодную партицию** — история «кто что менял» сохраняется, горячий
  хвост остаётся коротким. Клиент, чья база ушла за горячий хвост, получает снимок и
  переигрывает свою очередь (см. идемпотентность).
* **Авторизация и права** в этом круге не решаются: автор — самоназванное имя. Это
  открытый вопрос из ревью (№ 11), он закрывается до внешнего запуска.

### 8.4 Что из текущего кода куда

`src/core.js` — общий модуль движка: его импортируют CLIENT (как сейчас), Document
service (`rebase` + `applyOps`) и DSLV. `brain.js` → Orchestrator (конвейер, промпты,
компилятор патча) и DSLV (`patchToOps` + `validate`). `app.js` → CLIENT; из него уходят
автосохранение в `localStorage` и прямые вызовы модели (второе — при переезде
Orchestrator). Новый `src/sync.js` — реплика: локальный журнал, очередь, сокет.
Библиотека из узла документа → проект вида `library` под DUIL. Словарь регулярок → JEV (§7).

Порядок переезда: **(1) Document service + клиент-реплика** — истина переезжает на сервер,
два окна правят один документ вживую; **(2) Orchestrator** — `brain.js` на сервер, DSLV,
JEV как заглушка на нынешнем словаре, DUIL; **(3) библиотека как проект и импорты**;
**(4) поток стадий 7b по сокету**, потому что до серверного агента уведомлять не о чем.
Локальный запуск — Docker Compose (Postgres + Document service + NGINX); артефакт на
claude.ai к серверу подключиться не может (CSP) и остаётся демонстрацией без сервера.

## 9. Контракт Document service (круг 22)

Дополнения идут по кругам и стоят в тексте в порядке кругов, вперемежку с §10:
§9.8 и §10.5 — круг 23, §10.6 и §9.9 — круг 24, §9.10 и §9.11 — круг 25, §9.12 и §10.7 —
круг 26 (в конце). Номера внутри §9 и §10 сквозные и не повторяются.

По этому разделу пишутся сервер (`server/document/`) и клиент (`src/sync.js`); он
нормативен для обоих. JSON, UTF-8; все id — строки; `seq` — целое ≥ 0 (0 — только что
созданный проект); `engine` = `core.ENGINE_VERSION`. Авторизации нет: заголовок
`X-Author` (или поле `author`) — отображаемое имя.

### 9.1 Транзакция

```ts
Tx = {
  tx_id: string,            // генерирует клиент (core.uid('tx')); ключ идемпотентности
  base_seq: number,         // номер головы, которую клиент видел, когда строил ops
  ops: Op[],                // пять операций §1.3; у create узел уже с id (клиентским)
  undo_of?: string,         // tx_id отменяемой транзакции
  redo_of?: string,         // tx_id отменённой транзакции (повтор)
  author?: string,          // отображаемое имя
  author_kind?: 'human' | 'agent' | 'system',   // по умолчанию human
  client?: string,          // clientId вкладки — чтобы отличать своё в рассылке
  title?: string,           // как показать в истории
  engine: number
}
Committed = Tx & {
  seq: number,              // присвоил DSLTS
  ops: Op[],                // ПРИМЕНЁННАЯ форма (после слияния; она и лежит в журнале)
  dropped: { index: number, op: Op, reason: DropReason }[],
  notes?: { index: number, note: 'reparented' }[],   // что слияние поправило, не отбросив
  created_at: string        // ISO
}
DropReason = 'removed' | 'exists' | 'orphan' | 'cycle' | 'invalid'
```

`create` и `move` могут нести `after: NodeId | null` — намерение «после этого соседа»
(`null` — первым); сервер сначала разрешает `after` в индекс, и только без него берёт
`index` (с зажимом в границы). Клиент проставляет `after` всегда, когда знает соседа.

### 9.2 HTTP (`/api`)

| Метод и путь | Тело | Ответ |
|---|---|---|
| `GET /api/health` | — | `200 {ok, engine}` |
| `GET /api/projects?kind=&limit=&after=` | — | `200 {projects: [{id, name, kind, head_seq, updated_at}], more, next?}` — новые по `updated_at` первыми; `kind` — `design`\|`library`; страница `limit` (200, ≤ 1000), `after` — `next` прежней страницы (§9.12) |
| `POST /api/projects` | `{name?, kind?: 'design'\|'library', doc?}` | `201 {id, name, kind, head_seq: 0}`; без `doc` — `createDoc()`; документ = снимок при `seq 0` |
| `GET /api/projects/:id` | — | `200 {id, name, kind, head_seq, snapshot: {seq, doc, engine}, tail: Committed[]}` — хвост = транзакции с `seq > snapshot.seq` |
| `PATCH /api/projects/:id` | `{name}` | `200 {id, name, kind, head_seq}` |
| `GET /api/projects/:id/ops?since=<seq>&limit=<n>` | — | `200 {head_seq, txs: Committed[]}`; `since` ниже хранимого хвоста → `410 {snapshot, head_seq}` |
| `POST /api/projects/:id/tx` | `Tx` | `201 Committed`; повтор `tx_id` → `200` с тем же `Committed`; `400` — негодная форма; `404`; `426 {engine}` — версия движка; `503` — хранилище недоступно (клиент держит очередь). `409` не бывает: конкуренция решается слиянием |

### 9.3 WebSocket (`/ws?project=<id>&since=<seq>&client=<clientId>`)

Сервер → клиент:

* `{type:'hello', project, head_seq, engine}` — затем догон: `{type:'tx', tx: Committed}`
  для каждой `seq > since` по порядку, затем живой поток.
* `{type:'tx', tx: Committed}` — каждая зафиксированная транзакция, **своя тоже** (клиент
  узнаёт её по `tx_id`; это и есть подтверждение).
* `{type:'gone', snapshot: {seq, doc, engine}, head_seq}` — `since` ниже хранимого хвоста:
  клиент берёт снимок как `confirmed` и переигрывает очередь.
* `{type:'error', tx_id?, code, message}` — негодная транзакция (форма, версия движка).
* `{type:'presence', client, author, selection: NodeId[], board?: NodeId, at}` — чужое
  присутствие; `{type:'left', client}`.

Клиент → сервер:

* `{type:'tx', tx: Tx}` — то же, что `POST …/tx`; ответ приходит рассылкой `tx` (или `error`).
* `{type:'presence', selection, board}` — эфемерно, не пишется, не чаще 10 раз в секунду.

Гарантия порядка: по одному сокету `tx` приходят с возрастающим `seq` без пропусков
(догон, потом живое). Увидев `seq > last + 1`, клиент запрашивает `GET …/ops?since=last`.

### 9.4 Секвенсор DSLTS

1. Голова проекта в памяти: снимок + хвост → документ, `head_seq`, надгробия (id
   удалённых узлов → последний родитель; восстанавливаются из `remove` в хвосте).
   Загружается лениво при первом обращении, выгружается по бездействию.
2. На транзакцию — под мьютексом проекта (очередь в процессе):
   `tx_id` известен → вернуть сохранённое. Иначе `concurrent` = транзакции с
   `seq > base_seq`; `merged = core.rebase(head, tx.ops, {tombstones})` → `{ops, dropped, notes}`;
   строгий `applyOps(head, merged.ops)` обязан пройти (это гарантирует `rebase`); если нет —
   виноватая операция отбрасывается с `reason:'invalid'`, применение повторяется.
3. В одной транзакции базы: `UPDATE projects SET head_seq = head_seq + 1 … RETURNING head_seq`
   → `seq`; если `seq ≠ память + 1`, писал другой экземпляр — хвост перечитывается, шаг 2
   повторяется (ограниченно); `INSERT INTO operations … ON CONFLICT (project_id, tx_id) DO NOTHING`
   — при конфликте вернуть существующую запись.
4. Обновить голову, отдать `Committed` в Hub (всем подпискам проекта), каждые N = 50
   транзакций — снимок (асинхронно, после ответа).

### 9.5 Клиент-реплика (`src/sync.js`)

* Состояние: `confirmed = {seq, doc}`, `pending: Tx[]` в порядке отправки,
  `view = replay(confirmed.doc, pending)` — теми же `rebase` + `applyOps`, что на сервере.
* Локальный журнал: IndexedDB `imago`, хранилище `projects`, ключ — id проекта:
  `{seq, doc, pending, clientId, updatedAt}`; пишется после каждого изменения (не чаще
  раза в 200 мс). При открытии сначала читается он → рисуется → потом сокет.
* Отправка: `pending[0]` уходит, как только сокет открыт; своя `tx` в рассылке →
  `pending.shift()`, `confirmed = apply(confirmed, tx.ops)`, `seq = tx.seq`, уходит
  следующая. Чужая `tx` → `confirmed = apply(...)`, `view = replay(...)`.
* Переподключение: `since = confirmed.seq`; `gone` → `confirmed = snapshot`; очередь
  досылается с начала (сервер вернёт сохранённое для уже зафиксированных).
* `dropped` своей транзакции показывается человеку конкретно — что, почему и кто помешал:
  «Переименование «Карточка встречи» не применилось — Аня удалила этот слой»; «остальное в
  правке применено» — только если что-то легло; `stale` — «правка сделана до восстановления
  базы…». Карточку закрывает человек (круг 25). `view` пересчитывается по применённой форме.
* Статус в интерфейсе (точка и слова рядом с именем проекта; на узкой шапке — только точка
  значком на кнопке «Проекты», слова — в подсказке): «открываю проект…» · «синхронизация…» ·
  «в сети · всё сохранено» · «не в сети» / «не в сети · N правок ждут» (браузер без сети) ·
  «сервер недоступен» / «сервер недоступен · N правок ждут» (сеть есть, сервер не отвечает) ·
  «версия движка устарела — обновите страницу». Рядом — где работает агент: «агент: сервер» /
  «агент: в браузере» / «агент недоступен» (по `/agent/health`, §10). Присутствие — кружки с
  инициалами соавторов справа в шапке (сверх трёх — «+N»; пульс и «Аня ждёт агента…», когда у
  неё `busy`/`queued`, §9.9), чужие выделения — цветной рамкой с именем.
* Отмена/повтор — как в §8.3: инверсия от `view`, транзакция с `undo_of`/`redo_of`.

### 9.6 Правила слияния (`core.rebase(doc, ops, {tombstones})`)

Вход — документ-голова и операции, построенные относительно более старой базы; выход —
применимые операции, отброшенные с причиной и пометки. Правила по операциям:

| Операция | Условие | Результат |
|---|---|---|
| `set` | узел жив | остаётся; поздняя по `seq` побеждает (LWW на уровне листа; `keepFieldForm` как в §6.4) |
| `set` | узел удалён | `dropped: removed` — remove побеждает |
| `setToken` | всегда | остаётся |
| `create` | id занят | `dropped: exists` (повтор) |
| `create` | родитель жив | остаётся; `after` → индекс, иначе `index` с зажимом; дети, которых уже нет, вычёркиваются |
| `create` | родитель удалён | переприкрепляется к ближайшему живому предку по цепочке надгробий, `notes: reparented`; живых предков нет — `dropped: orphan` |
| `remove` | узел жив | остаётся |
| `remove` | уже удалён | `dropped: removed` (нет операции) |
| `move` | узел удалён | `dropped: removed` |
| `move` | новый родитель удалён | ближайший живой предок, иначе `dropped: orphan` |
| `move` | цель внутри поддерева узла (в том числе из-за чужого `move`) | `dropped: cycle` — отбрасывается только поздний |
| `move` | иначе | остаётся; `after` → индекс, иначе `index` с зажимом |

`rebase` детерминирован и не бросает; после него строгий `applyOps` обязан пройти.
Тест сходимости: три реплики, случайные операции над общим документом, любые порядки
доставки через один журнал → одинаковый документ у всех (сравнение по `hashDoc`).

### 9.7 Уточнения по итогам реализации (круг 22)

* `hello.project` — сводка `{id, name, kind, head_seq, updated_at}`. После `gone` по сокету
  сразу идёт хвост за снимком до головы; после HTTP `410` клиент сам просит `ops?since=snapshot.seq`.
* Автор: query `author=` сокета, поле `author` в `tx`/`presence`; `X-Author` — только в
  percent-encoding (заголовки latin1). Тело больше 4 МБ — `413`; неизвестный метод — `405`;
  транзакция без `engine` — `426`.
* Транзакция, у которой отброшены все операции, всё равно получает `seq` и пишется с `ops: []`.
* `rebase`: `create` вычёркивает и тех детей, что из-за чужого `move` стали предками родителя;
  сосед из `after`, переехавший в другой контейнер, считается отсутствующим; при
  переприкреплении `after`/`index` игнорируются (в конец); операции без `id` и `create` без
  `node.id` — `invalid`; надгробия внутри одной транзакции `rebase` не пополняет — это делают
  DSLTS и клиент между транзакциями.
* Листовая инверсия шире листа в двух случаях: форма скаляр↔объект меняется, и операция
  снимает существующий ключ (тогда возвращается объект-родитель — сохраняется порядок ключей).
* Клиент входит в серверный режим по `?project=` в ссылке или по отметке `imago.server.v1`
  даже без ответа `/api/health`: документ и очередь берутся из журнала IndexedDB. «В сети» —
  только после `hello`; до него очередь и присутствие не отправляются. Журнал клиента хранит
  ещё `tombstones` и `extra` (история, диалог оболочки).
* Открыто: присутствие между экземплярами Document service (нужен pub/sub — **закрыто в
  круге 24, §9.9**); Hub не хранит
  список присутствующих — новичок узнаёт о других по их ответному присутствию; две вкладки
  одного браузера делят `clientId`; id библиотеки при миграции выводится из id проекта
  (иначе два клиента заведут две) — перенести в сервер при `POST /api/projects`.

## 10. Контракт Orchestrator (круг 23)

Нормативен для `server/orchestrator/` и для клиента `src/agent.js`. Orchestrator — второй
процесс (§8.1): ведёт команду по шагам 3–13 с доски. **К базе не прикасается**: стейт
читает у Document service (`GET /api/projects/:id`, стрелки 4a/5a), пишет транзакцией
(`POST /api/projects/:id/tx`, стрелки 12/13) с `author_kind:'agent'`. Движок, промпты и
компилятор патча — те же `src/core.js` и `src/brain.js`, что раньше работали в браузере.

### 10.1 Модули

| Модуль | Каталог | Обязанность |
|---|---|---|
| JEV | `server/orchestrator/jev/` | «команда оболочки или работа для модели»: `classifyUtterance` из `brain.js` (§7) за интерфейсом `classify(text, ctx) → {kind:'shell', action, args} \| {kind:'model'} \| {kind:'variants', n}` |
| DSLR (клиент) | `server/orchestrator/dslr/` | чтение стейта и головы у Document service; кеш по `(project, head_seq)` |
| DUIL | `server/orchestrator/duil/` | срез библиотек: проекты вида `library` (через тот же DSLR) → словарь компонентов (`describeLibrary`) |
| DSLV | `server/orchestrator/dslv/` | патч → операции на копии стейта, раскладка, `validate`; тяжёлое — в `worker_threads` |
| LLM | `server/orchestrator/llm/` | клиент к модели: OpenAI-совместимый (`LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`) или Anthropic (`LLM_KIND=anthropic`); адрес собирается через `URL`, ключ никогда не попадает в ответы, трассы и логи |
| DSLTS (клиент) | `server/orchestrator/dslts/` | запись транзакции в Document service, повтор по тому же `tx_id` при сетевой ошибке |
| pipeline | `server/orchestrator/pipeline.js` | шаги 4→13, очередь команд на проект (по одной), «стоп» |

### 10.2 HTTP (`/agent`)

| Метод и путь | Тело | Ответ |
|---|---|---|
| `GET /agent/health` | — | `200 {ok, engine, llm: 'up'\|'down'\|'unconfigured', document: 'up'\|'down', model?, instance, started_at}` (`instance`, `started_at` — круг 26, §10.7) |
| `POST /agent/command` | `{command_id, project, text, selection?: NodeId[], board?: NodeId, base_seq?, client?, author?, mode?: 'run'\|'variants', n?}` | `200 text/event-stream` (§10.3) |
| `POST /agent/stop` | `{command_id}` | `200 {stopped: bool}` |
| `POST /agent/apply` | `{command_id, variant}` | выбранный вариант → транзакция; `200` событие `result` одним JSON |

Ошибки — единое тело `{error: true, code, message, retryable, detail?}`; коды: `400 bad_request`,
`404 not_found`, `405`, `413 too_large`, `429 busy` (очередь проекта полна), `502 llm_failed`,
`503 document_down`/`llm_down` с `Retry-After`.

### 10.3 Поток событий (стрелка 7b)

SSE, каждое событие — `event: <тип>\ndata: <JSON>\n\n`:

* `queued {position}` — команда ждёт очереди проекта;
* `stage {key, label, at}` — `key` из `jev, read, library, llm, validate, repair, write`;
* `shell {action, args}` — JEV узнал команду оболочки (отмена, выделение, масштаб…): её
  исполняет клиент сам, модель не зовётся;
* `variants {items: [{key, label, description, ops_count, preview}]}` — режим вариантов,
  ничего не записано; выбор — `POST /agent/apply`;
* `result {tx_id, seq, applied, dropped, summary, warnings, select?: NodeId[]}` — записано;
  клиент получит ту же транзакцию по своему сокету Hub;
* `error {code, message, retryable, retry_after?}` (`retry_after`, с — когда срок повтора известен, круг 26); последним всегда `done {}`.

Разрыв SSE командой не управляет: команда доводится до конца (или до «стоп»), результат
приходит клиенту по сокету как обычная транзакция.

### 10.4 Трассы

Каждая команда оставляет трассу (шаги, длительности, число вызовов модели, без ключей и без
полных промптов): Orchestrator шлёт её в Document service `POST /api/internal/traces` с
заголовком `X-Internal-Token: $INTERNAL_TOKEN`; nginx снаружи отдаёт на `/api/internal/` `403`.

### 10.5 Уточнения по итогам реализации (круг 23)

* **Ошибки до потока и в потоке.** Всё, что решается до открытия SSE (форма тела, очередь
  полна, Document service не отвечает на `/api/health`, модель не подключена или её `/models`
  не отвечает — кеш 10 с), приходит HTTP-статусом с телом §10.2 и `Retry-After` для 429/503.

  `503 shutting_down`, `500 worker_failed`, `504 timeout`, `426 engine`, `500 internal`;

* **`/agent/health`**: `ok: true` значит «агент отвечает»; состояние зависимостей — только в

* **Команда оболочки** (`shell`) не занимает очередь проекта и не требует ни модели, ни

  brain и узкий перенос `shellIntent` из app.js~~ — **закрыто в круге 24** (§10.6): словарь

* **Тело команды** дополнительно принимает `history: [{utterance, summary}]` (до 5) — память
  разговора для планировщика; «покажи варианты» без команды берёт последнюю реплику оттуда.
  `base_seq` клиента принимается, но агент строит патч по своему свежему чтению головы и пишет
  с её номером; расхождение с видом клиента решает слияние (§9.6).
* **`result` без записи.** Переспрос, ответ, отказ и «нечего менять» приходят событием
  `result` с `tx_id: null, seq: null, applied: 0` и полями `clarify`/`clarifyOptions`,
  `answer`/`followups`, `cannot`, `nothingChanged`/`nothingToChange`.
* **Запись агента:** `author:'Агент'`, `author_kind:'agent'`, `client` — вкладка, приславшая
  команду (её реплика помечает транзакцию как свою), `title` — заголовок плана.
  `select` в `result` — созданные корни и изменённые узлы (до 50).
* **Варианты:** событие `variants {base_seq, items}`; `preview` элемента — `{ops, summary,

### 9.8 Укрепление (круг 23)

Дополняет §9.1–9.7; нормативно для `server/document/` и `src/sync.js`. Числа — в
`server/document/limits.js` (клиент держит те же в `LIMITS`, тест сверяет).

**Ошибки.** Любой ответ-ошибка, HTTP и WS, — `{error: true, code, message, retryable,
detail?, retry_after?}` (WS: то же с `type:'error'` и `tx_id`). Коды: `bad_request` 400 ·
`forbidden` 403 · `not_found` 404 · `method_not_allowed` 405 · `gone` 410 · `too_large` 413 ·
`engine` 426 · `internal` 500 · `unavailable`/`busy` 503 (с `Retry-After`). Поля, которые
прежние клиенты читали сверху, остаются там же: `engine` у 426, `snapshot`/`head_seq` у 410,
`tx_id`. Клиент снимает транзакцию с очереди только при `retryable:false`.

**Якорь и эпоха.** У каждой записи журнала `chain = sha256(prev_chain + tx_id + seq)` (hex;
до первой записи — `''`), у проекта — `head_chain`, у снимка — `chain` его seq. `Committed`
несёт `chain`. Эпоха проекта `epoch` — случайная метка (12 hex; счётчик после restore
совпал бы с уже бывшей), все известные базе эпохи — в `project_epochs`. Клиент держит
`tip` = chain своей последней подтверждённой и `epoch`, шлёт их при переподключении:
`/ws?…&since=&tip=&epoch=`, `GET …/ops?since=&tip=&epoch=`. Разбор (`dslr.classify`):

| что прислал клиент | ответ | эпоха |
|---|---|---|
| tip совпал с chain журнала на since (при любой эпохе) | хвост | — |
| since < 0 или впереди головы | снимок (`gone`/410) | не меняется (зажим) |
| tip не совпал, эпоха нынешняя; или эпохи база не знает | снимок | меняется, если нынешнюю начал не клиент |
| tip не совпал, эпоха прежняя (известна базе) | снимок | не меняется |
| нет tip и нет epoch (прежний клиент) | по номерам, как в §9.3 | — |

Эпоху, начатую по слову клиента (`epoch_cause = 'client'`), клиент сменить не может: один
неисправный клиент иначе закрывал бы всем сокеты по кругу. Экземпляр сервиса меняет эпоху
сам, когда видит откат: голова базы позади головы в памяти, цепочка на том же seq другая,
запись пришла с «чужим» chain (compare-and-set: один откат — одна смена). При смене эпохи
все сокеты проекта со старой эпохой закрываются кодом **4410** (перед этим — `error` с
`code:'epoch'`), голова в памяти выбрасывается, кеш кадров Hub чистится; кадры кешируются
по ключу `seq:chain`. `base_seq` впереди головы — зажим до головы, не отказ.

**Протокол.** `hello {project, head_seq, engine, epoch, tip, gone}` (`gone: true` — следом
придёт снимок; `false` — подтверждённое клиента цело, новая эпоха — сразу его); `gone {snapshot: {seq, doc,
engine, chain}, head_seq, epoch, tip}`; новое сообщение `ack {tx_id, seq, chain, existing:
true}` — повтор уже записанной транзакции, которую этот сокет уже получил (раньше — тишина,
и клиент после `gone` ждал подтверждения вечно). Ответы `GET …/ops` — `{head_seq, epoch, tip,
txs, more}`; `GET /api/projects/:id` — плюс `epoch`, `tip`, `more`; `POST /api/projects` —
плюс `epoch`, `tip`.

**Клиент при 4410.** Переоткрывается сразу (с разбросом до 250 мс), получает снимок и
переигрывает поверх очередь **и** свои транзакции, подтверждённые в прежней эпохе (`mine`,
последние 50, в журнале клиента): уцелевшие сервер узнаёт по `tx_id` (`ack` или `tx`),
потерянные при restore записывает заново. Правки не теряются.

**Несколько экземпляров.** Запись транзакции и смена эпохи шлют `NOTIFY imago_doc` в той же
транзакции базы (`{k:'tx', p, s, c, e, i}` · `{k:'epoch', p, e, i}`); каждый экземпляр слушает
(LISTEN, своё соединение, переподключение со сверкой всех голов). По уведомлению экземпляр
сверяет голову с базой (`head_seq`, `head_chain`, `epoch`), дочитывает хвост с проверкой
цепочки и отдаёт его своим сокетам. Сверка ещё — при подключении каждого сокета и по таймеру
(5 с). Присутствие между экземплярами по-прежнему не ретранслируется.

**Чтение.** Хвост — страницами по числу (`limit` ≤ 5000) и, мягко, по байтам (2 МиБ; первая
запись — всегда), `more: true` — есть ещё. `GET /api/projects/:id?head=1` — только голова
`{id, name, kind, head_seq, updated_at, epoch, tip}`; `?lean=1[&since=N]` — снимок без
документа `{seq, engine, chain}` и хвост после `since` (по умолчанию — после снимка). Полный
снимок (`GET /api/projects/:id`, `gone`, 410) — под семафором (4 одновременно, 32 в
очереди); переполнение — 503 `busy` + `Retry-After` (WS: `error` и закрытие 4503).

**Пределы.** Тело ≤ 4 МБ и операций ≤ 5000 — иначе 413 (`detail.limit`: `body_bytes`,
`ops_per_tx`). Документ ≤ 24 МиБ JSON и ≤ 20 000 узлов: транзакция, после которой он
превысил бы предел и вырос бы, **не отклоняется** — все её операции, кроме `remove`,
отбрасываются с `reason:'invalid'`, `limit:'doc_nodes'|'doc_bytes'`; транзакция получает
seq (ответ автору, идемпотентность). Бюджет слияния — 2 с: поиск операции, которую не
принял строгий `applyOps`, дальше не идёт, остаток — `invalid` с `limit:'merge_budget'`.

**dropped в журнале** — выжимка: не больше 50 записей, остаток — последней записью
`{more: N}`; операция длиннее 1 КБ JSON — без значения: `valueBytes` + `preview` (120
символов), у `create` остаются `node.{id,type,name,parent}`. Клиент: `droppedLine(dropped)`.

**Снимки** — раз в N (50) транзакций, хранятся последние 5 и всегда seq 0 (затравка —
исходный документ проекта: без неё журнал не переиграть с начала). Снимок пишется, только
если chain его seq совпадает с журналом, и отдаётся только такой: снимок, посчитанный до
отката базы и дописанный после, не отравит открытие.

**Миграции** — `server/document/storage/migrations/NNN_имя.sql|mjs`, учёт в
`schema_migrations`, отдельное соединение под `pg_advisory_lock`, каждая — своя транзакция с
`SET LOCAL statement_timeout = 0`; `.mjs` режет тяжёлую работу на пачки-транзакции (003
считает chain старого журнала по 1000 записей). Обычные запросы — с дедлайном
`DB_TIMEOUT_MS` (8000; statement_timeout + query_timeout), просрочка — 503.

**Трассы агента.** `POST /api/internal/traces` с `X-Internal-Token` = `INTERNAL_TOKEN`; без
переменной, с неверным токеном или с заглушкой `change-me` — 403. Тело — объект `{project
(или project_id), command_id, …}` ≤ 64 КБ (иначе 413), хранится целиком в `traces.body`;
ответ `201 {id, created_at}`. `GET /api/projects/:id/traces?limit=` (20, ≤ 200) — последние,
новые первыми, без токена.

### 10.6 Круг 24

Дополняет §10.1–10.5; нормативно для `server/orchestrator/` и `src/brain.js`, для клиента
`src/agent.js` — формы тела команды и событий.

**Тело `POST /agent/command`.** `history?: [{utterance: string, summary?: string}]` — память
разговора, старые первыми. Берутся последние 5 записей; `utterance` и `summary` режутся до
500 символов; запись без строки `utterance` пропускается; не массив — `400 bad_request`.
История идёт в прогон brain как есть (`runCommand({history})`, в воркере — так же) и попадает
в промпт планировщика и всех последующих вызовов блоком «ПРЕДЫДУЩИЕ КОМАНДЫ» (каждая строка
там ещё раз ужимается: реплика — до 160, итог — до 200 символов). Так «синий» после переспроса
«в какой цвет?» понимается как ответ на него. Клиент кладёт в `summary` то, что агент ответил
(итог правки, переспрос, ответ).

**`result` без записи** — `{tx_id: null, seq: null, applied: 0, dropped: [], summary, warnings}`
и ровно одно из:

| поле | когда | форма |
|---|---|---|
| `clarify`, `clarifyOptions` | переспрос | строка; массив готовых ответов-команд (обычно 3, может быть пуст) |
| `answer`, `followups?` | вопрос о макете | строка; до 3 строк-предложений следующей команды |
| `cannot` | так в этой модели документа нельзя | строка «почему» |
| `nothingChanged`, `nothingToChange?` | правка ни на что не повлияла / всё названное уже так | `true`; объяснение — в `warnings` |

`summary` — та же фраза (`clarify`/`answer`/`cannot`) или заголовок плана. При
`nothingChanged` агент **не пишет** транзакцию, даже если brain вернул (пустые по смыслу)
операции. `result` с записью может нести `cannot` (часть просьбы невыполнима) и
`libraryAdded` (ниже).

**`variants`.** `{base_seq, items: [{key, label, description, ops_count, preview}]}`, где
`preview = {ops: Op[], summary: string, warnings: string[]}` — ровно эти поля: документа и
геометрии нет, клиент накладывает `ops` своим движком на свой стейт с `base_seq`. id созданных
узлов в `ops` — глобальные (`core.uid`), те же, что запишет `apply`.

**DSLR: кеш и откат.** Кеш проекта — `{seq, doc, chain, epoch}`: документ на своей голове,
`chain` её записи и эпоха (§9.8). Дочитывание — `GET …/ops?since=<seq>&tip=<chain>&epoch=<epoch>`
(`tip` не шлётся, пока он `''`), страницы по `limit=5000`, конец — по `more:false` (страница
режется и по байтам, её длина о конце не говорит; сервис без `more` — по `head_seq`). Полное
чтение (`GET /api/projects/:id`) с `more:true` дочитывается так же. Каждая запись хвоста
проверяется: `seq` подряд, `chain = sha256(prev + tx_id + seq)` от якоря кеша, строгий
`applyOps`. Кеш проекта выбрасывается и стейт читается целиком, когда: ответ `410`; эпоха в
ответе не та, что в кеше; chain пришедшей записи не продолжает якорь; пустая страница при
голове позади кеша или впереди него; якорь пустой головы не совпал; запись не легла. Полное
чтение повторяется до 3 раз (журнал может переписываться под чтением), потом `502
document_failed`. Чтения одного проекта идут по одному. `503` с `Retry-After` на чтении —
ожидание до 5 с, до двух повторов.

**DSLTS: ответы Document service.**

| ответ | агент |
|---|---|
| сеть, 5xx | повтор с **тем же** `tx_id`, всего 3 попытки; у `503` — пауза по `Retry-After` (не больше 5 с, всего на запись — не больше 12 с), иначе 300·n мс; исчерпано — `503 document_down` с `Retry-After` |
| `413` | `too_large`, без повтора |
| `426` | `engine` (`detail.engine` — версия сервиса), без повтора |
| `404` | `not_found`; прочие 4xx — `502 document_failed`, без повтора |

До сети: операций больше 5000 или тело больше 4 МБ (пределы §9.8; в образе агента
`server/document` нет, числа повторены в `server/orchestrator/limits.js`, тест сверяет) —
`413 too_large` с объяснением человеку («Правка слишком большая: N операций при пределе 5000…
Ничего не записано. Разбейте команду на части»), `detail.limit`: `ops_per_tx` | `body_bytes`.
Резать правку на несколько транзакций агент не станет: половина правки в журнале
отменяется не целиком и видна другим недоделанной.

**brain: внешняя библиотека.** `runCommand`/`runVariants` принимают `library?: [{doc, name?,
id?}]` — документы-библиотеки (или их выжимки `libraryDocOf(doc, core)`: корень, страница
библиотеки, мастера). Внешние компоненты дополняют словарь документа; при совпадении имён
(без учёта регистра и «ё») главнее документ, среди внешних — первая по порядку библиотека.
Прогон идёт над «документом плюс» — стейтом, в библиотеку которого временно положены внешние
мастера со свежими `core.uid`; в ответе к операциям спереди добавляется перенос **только тех**
мастеров, на которые правка сослалась (и вложенных в них), и создание страницы библиотеки,
если её не было; `preview` — настоящий документ после этих операций; `libraryAdded: [{name,

`libraries` и `library_components`.

**brain: id новых узлов** — `core.uid` движка (без него — та же форма своим генератором):
`f_…`, `t_…`. id, предложенный моделью в дереве, — только псевдоним: узел получает свежий id,
ссылки патча по псевдониму находят его. `globalizeIds` в Orchestrator остаётся страховкой и для
операций brain пуст.

**«Верни обратно» — повтор (redo)** и в оболочке (`app.js shellIntent`), и в brain

обратно», и те же слова голосом обязаны делать то же, что кнопка; разная трактовка давала

  seq}`: он снимает её с очереди (раньше ждал вечно и держал за ней всю очередь); реплика
  круга 24 понимает `duplicate` как `ack`;
* читатель, у которого неотправленного больше 32 МиБ, закрывается кодом 4503 (`slow`) —
  догонит с `since`; память экземпляра не копит кадры для вкладки, которая не читает;
* догон сокета, которому за снимком снова нужен тот же снимок (дыра в журнале), — `error
  unavailable` и 4503, а не чтение снимка по кругу; `ops?since=` с пустым хвостом при голове
  впереди — 410 со снимком, а не `more: true` с пустой страницей.

**LISTEN.** Переподключение слушателя назначается один раз на соединение (`error`, `end` и
сбой подключения приходят вперемешку — иначе заводился второй слушатель); после
переподключения — сверка всех голов (`resync`): пропущенное за обрыв дочитывается и без
таймера сверки. Проверено `pg_terminate_backend` слушателя под записью другого экземпляра
(три круга) и обрывом всех соединений экземпляра под нагрузкой реплик.

**Найдено и исправлено проходом по `server/document`.**

* Соединение, выданное пулом, без обработчика `error`: разрыв между запросами транзакции

### 9.10 Круг 25

Дополняет §9.8–9.9; нормативно для `server/document/` (кроме `storage/`) и `src/sync.js`.
Числа — в `server/document/limits.js` (клиенту нужные — в `LIMITS`, тест сверяет).

**Строки.** Postgres не принимает в jsonb/text U+0000 и одиночные суррогатные половины (а
`JSON.stringify` пишет их как `\ud800`): раньше такая строка давала 503 retryable, и очередь
клиента стояла вечно. Теперь: id — `tx_id`, `undo_of`, `redo_of`, `client`, id в операциях
(`id`, `parent`, `after`, `path`, `node.id`, `node.parent`) — с U+0000 или половиной → **400**;
значения — `author`, `title`, всё внутри операций рекурсивно (и ключи объектов), имя проекта
(`POST`/`PATCH`), документ `POST /api/projects`, тело трассы, автор и `clientId` сокета,
`X-Author` — **чистятся**: U+0000 убирается, одиночная половина → U+FFFD. Выделение и `board`
присутствия с такими id не пропускаются (`truncated: true`). Обрезка имён — по кодовым
точкам (пара не рвётся). Вложенность значений глубже 64 — 400. Клиент чистит свою правку
теми же правилами до отправки (прогноз совпадает с ответом). Страховка хранилища: ошибка
Postgres класса 22xxx — 400 `bad_request`, `retryable: false` (не 503).

**Форма операции.** Поля, которые читает движок, проверяются по типу: `id`, `parent`,
`node.id`, `node.parent`, `path` — строка; `after` — строка или `null`; `index` — конечное
число; `node` у `create` — объект. Не того типа → 400 (раньше `parent: {"toString":1}` давал
500 retryable). Отсутствующее поле (или `null`) — по-прежнему смысл, а не форма: `dropped:
invalid` (§9.7).

**`command_id`.** Транзакция может нести `command_id` (строка-id ≤ 128, связь с трассой
агента): пишется в журнал, возвращается в `Committed`. Негодное значение просто
выбрасывается — правку не губит.

**Предел входящих записей.**

* сокет: не больше `WS_INFLIGHT` = 2 необработанных транзакций; на пределе чтение сокета
  ставится на паузу (остальное ждёт в TCP у клиента), уже прочитанное сверх предела получает
  `error {code:'busy', retryable:true, retry_after:1, detail:{limit:'socket_inflight'}, tx_id}`;
* очередь мьютекса проекта: ≤ 32 МиБ тел и ≤ 256 транзакций; всего экземпляра ≤ 128 МиБ;
  пустая очередь принимает всегда. Сверх — 503 `busy` + `Retry-After: 1` (`detail.limit:
  'queue_project' | 'queue_total'`), по WS — `error busy`;
* `POST …/tx` — под семафором (8 одновременно, 64 в очереди; тело читается, когда есть
  место); сверх — 503 `busy` + `Retry-After`.

Поток из трёх сокетов по 10 транзакций в 3,8 МБ (5000 операций каждая): куча растёт на
~150 МБ, в очереди одновременно не больше 6 (раньше — все 30, и процесс падал по памяти).

**Клиент: отравленная транзакция.** 8 подряд одинаковых повторяемых ошибок на одну
транзакцию (`busy` не в счёт) — реплика проверяет, жив ли сервер (`GET …?head=1`); жив —
ещё одна попытка, и при той же ошибке транзакция снимается в «не сохранено»: `onError
{code:'not_saved', cause, tx, message}`, `replica.unsaved`, `replica.retryUnsaved(tx_id)`;
очередь идёт дальше. Сервер не отвечает и на чтение — повторяет, как прежде (правка не
теряется при лежащей базе). Паузы повтора растут: 1 → 2 → 4 … → 30 с.

**Надгробия в снимке.** Снимок несёт `tombstones` (объект id → последний родитель); голова,
загруженная со снимка, берёт их из него и пополняет `remove` из хвоста. Раньше одна и та же
офлайн-транзакция (create в группе, удалённой до снимка) давала в долгоживущей голове
`reparented`, а в загруженной заново — `orphan`. Снимок в `GET /api/projects/:id`, `gone`,
`410` отдаёт непустые `tombstones` — реплика берёт их в прогноз. У снимков до круга 25 —
`{}` (надгробия до них не восстанавливаются).

**Точный предел документа.** Байты документа в голове считаются точно — разницей по
изменённым узлам (applyOps копирует словарь узлов поверхностно, сравнение по ссылке находит
ровно их), токенам и прочим полям; раньше — оценкой по JSON операций, и create с длинным id
(ключ, `node.id`, ребёнок родителя — втрое) переходил предел.

**Новый проект.** `POST /api/projects` без `doc` — пустая страница (`createDoc('empty')`);
демо-документ — только `{demo: true}`.

**Откат базы: что переигрывается.** §9.8 «правки не теряются» уточняется:

* «свои» (`mine`) — транзакции вкладки **и** транзакции агента по её команде (`client` =
  clientId вкладки, `author_kind: 'agent'`) — их нигде больше не переиграют;
* окно — последние **200** своих и не больше 4 МБ JSON (было 50); переигрываются **все** из
  прежней эпохи, в порядке подтверждения (не по seq — номера разных эпох не сравнимы);
  вытесненные из окна, номер которых после снимка новой эпохи, — человеку: `onError
  {code:'replay_incomplete', count}` («N правок из прошлой версии не восстановлены»);
* давность: своё старше суток (`LIMITS.replayMaxAgeMs`, по времени первой записи) не
  переигрывается — `onError {code:'replay_expired', count, txs}`;
* переигрываемая транзакция несёт `replay_of_epoch` (эпоха, в которой была подтверждена) и
  `replay_at` (когда записана впервые, ISO). Сервер для неё отбрасывает `set`/`setToken` на
  лист (путь, пересекающийся по сегментам), который после `replay_at` переписала чужая
  транзакция (другой `client`) среди записанных после `base_seq`: **`dropped: stale`** —
  новая причина (`DropReason` += `'stale'`; `droppedLine`: «правка устарела — её уже
  переписали после восстановления базы»). Остальные операции ложатся как обычно. Переигранная
  раньше чужая правка считается по своему исходному `replay_at` (память головы). Окно поиска
  длиннее 5000 транзакций или `replay_at` старше суток — `stale` все листья. Уцелевшие при
  restore сервер, как прежде, узнаёт по `tx_id` (`ack`/`tx`) — их это не касается.

Так вкладка, закрытая до restore и открытая позже, больше не затирает своим старым
значением более новое чужое (сценарий критика: «СТАРОЕ» поверх «НОВОГО»), а лист, которого
после неё никто не трогал, возвращается.

**Реплика: журнал и «кто помешал»** (для оболочки).

* `replica.journal(limit = 200)` — последние подтверждённые транзакции, новые первыми:
  `{seq, tx_id, author, author_kind, title, created_at, client, command_id, ops_count,
  dropped_count, mine}`; в памяти не больше 500; опция `onJournal(list)` — при изменении
  (раз на микрозадачу). Снимок другой эпохи журнал очищает (это другая история).
* `replica.whoRemoved(nodeId)` → `{author, author_kind, seq, title} | null` — кто удалил узел
  (сам узел или поддерево с ним), по журналу в памяти.
* `onDropped(event)`: `event` — подтверждение своей транзакции плюс `label` (её `title`) и
  `by` (первый узнанный); у каждой записи `dropped` — `by` и `label`. `by` узнаётся: `removed`
  — кто удалил узел, `orphan` — кто удалил родителя, `exists` — кто создал тот же id, `stale` —
  кто переписал лист; иначе `null`.

**Открыто.** Надгробия копятся без предела (все удалённые за жизнь проекта; в снимке тоже).
`replay_at` чужой переигранной правки помнит только голова в памяти — после её выгрузки две
вкладки, обе потерявшие правку одного листа, решаются по времени переигрывания. Журнал
реплики — только в памяти (после перезагрузки вкладки пуст до новых транзакций).

### 9.11 Хранилище, круг 25

Дополняет §9.8–§9.10; нормативно для `server/document/storage/`, `server/document/index.js`,
`errors.js`. Исходные дефекты — разбор критиков круга 24 (миграции при работающем
экземпляре прежней версии, порт закрыт на время миграций, полуоткрытое соединение держит
замок проекта, тесты на общей базе мешают друг другу).

**Миграции и смешанные версии.** Обновление идёт, пока экземпляры прежней версии (в том
числе круга 22, который не знает chain) работают на той же базе. Правила для каждой
миграции: колонки — без перезаписи таблицы (без умолчания или с постоянным умолчанием,
Postgres 11+); «сужение» — не `SET NOT NULL`, а `CHECK … NOT VALID` под коротким замком и
`VALIDATE CONSTRAINT` (SHARE UPDATE EXCLUSIVE: чтение и запись идут); DDL ждёт замок не

транзакцией, держа за собой все запросы к таблице; всё идемпотентно.

Триггер `operations_chain` (BEFORE INSERT, `WHEN (NEW.chain IS NULL)` — новых экземпляров

предыдущей chain ещё нет (003 не дошла) — запись остаётся без chain, её подберёт 003 или

chain его записи. Проект, созданный прежней версией, не пишет `project_epochs` — нынешняя
эпоха проекта считается известной всегда (`knownEpoch`). База, где прежняя 004 уже
поставила NOT NULL, проходит 005/006 без проверки таблицы.

(«…— сделанное сохранено, повторный старт продолжит с 003_chain_backfill.mjs»), процесс
выходит с кодом 1, следующий старт продолжает (003 — с первой записи без chain). SIGTERM
во время миграций обрывает их соединение: база откатывает текущую пачку, выход — 0.

Замер (одна машина, 2 ядра, Postgres 16; журнал 1 000 000 записей одного проекта «круга 22»,
его писатель — транзакция раз в 5 мс, читатель — хвост раз в 20 мс):

| | прежние 002–004 | круг 25 |
|---|---|---|
| итог | 004 падает: `column "chain" contains null values` — и так при каждом старте | 15,3 с, 0 ошибок, chain у всех записей |
| замок записи (006) | ACCESS EXCLUSIVE на всю проверку (3 млн — 6 с) | 2 мс |
| запись старого экземпляра | — | p50 3 / p99 39 / max 302 мс, 0 ошибок (1392 записи) |
| чтение | — | p50 1 / p99 15 / max 20 мс |

Сквозная проверка: процесс круга 22 пишет по HTTP раз в 20 мс в проект с журналом 400 000
записей, рядом стартует круг 25: 24 с отвечает 503 `migrating` с прогрессом 003, затем 200;
у процесса круга 22 — 792 ответа 201 из 792, у журнала — ни одной записи без chain,
`head_chain` = chain головы, круг 25 пишет в тот же проект и читает записи круга 22.

**Порт во время миграций.** Порт открывается сразу; пока хранилище готовится, любой HTTP-
запрос (и `/api/health`) — `503 {error, code:'migrating', message, retryable:true,
detail:{phase:'connect'|'lock'|'migrate'|'init', migration, progress}, retry_after:5}` с
`Retry-After: 5`; upgrade сокета — тот же 503. Строка лога «слушаю http://…» — когда сервис
готов (её ждут скрипты и тесты), до неё — «порт … открыт · … 503 migrating». Обработчики
SIGTERM/SIGINT ставятся до миграций. Программно: `launch(opts)` → `{port, url, ready, close,
state}` (промис — когда открыт порт), `start(opts)` — как прежде (промис — когда готов).

**Полуоткрытое соединение.** Пул, слушатель и соединение миграций — с TCP keepalive (10 с) и
`idle_in_transaction_session_timeout` = 15 с (миграции — 60 с): сеанс, застрявший в
транзакции записи (ответ базы не дошёл, обрыв база не видит), база обрывает сама — замок
строки проекта отпускается ≤ 15 с. Соединение, на котором истёк `query_timeout` или которое
оборвалось, сразу закрывается и в пул не возвращается (`release(err)`): прежде `ROLLBACK`
вставал на нём в очередь за зависшим запросом — второе ожидание дедлайна, и соединение
возвращалось в пул сломанным. Слушатель LISTEN пингуется (`SELECT 1` раз в 10 с, ответ ≤ 5 с),
молча умерший — переподключается со сверкой голов. Проверено прокси, который глотает
ответ базы на `INSERT` и не передаёт базе обрыв: A — 503 за 2,5 с (query_timeout), B,
ждавший замок, пишет через 15 с, номер не потерян, пул A цел.

**Данные, которых база не хранит.** Ошибка Postgres класса 22 (`22P05` — `\u0000` в jsonb,
`22P02` — половинка суррогатной пары в jsonb, `22021` — NUL в text, …) — не сбой хранилища,
а `400 bad_request`, `retryable: false`, `detail: {cause:'data', sqlstate}`: клиент снимает
транзакцию с очереди (прежде — 503 навсегда и вся очередь за ней). Адаптер в памяти
отвергает то же (`pgRejects`), чтобы не быть мягче базы. Каждый 503 и 400 от хранилища —
строка лога: причина, SQLSTATE, сообщение базы не длиннее 200 символов, без переводов
строк; одинаковые — не чаще раза в секунду («и ещё N таких»).

**Выжимка `dropped`.** `preview` и поля `node` режутся по кодовым точкам: половинка
суррогатной пары на границе 120 символов делала всю запись журнала неприемлемой для jsonb
(22P02 → 503 навсегда).

**Интерфейс хранилища (для DSLTS).** `writeSnapshot(projectId, seq, doc, engine, chain,
tombstones?)` и `saveSnapshot(projectId, {seq, doc, engine, chain, tombstones})` —
надгробия объектом id → родитель (Map и массив пар тоже принимаются); `latestSnapshot` →
`{…, tombstones}` (`{}` у снимков до круга 25). `commitTx` сохраняет `tx.command_id`
(строка; нет — NULL), `Committed.command_id` — только если был.

**Тесты на общем кластере.** Каждый тестовый файл (`node --test` — процесс на файл) работает в
своей временной базе `<база>_t<pid><случайное>_x` на кластере `TEST_DATABASE_URL`: создаётся
при первой проверке доступности, удаляется после всех тестов файла (`DROP … WITH (FORCE)`),
базы умерших прогонов убираются при следующем старте; без права CREATE DATABASE — своя
схема (`search_path` в адресе) и свой канал NOTIFY. Подсчёт сеансов в тестах — с `datname =
current_database()` и `application_name`, уникальным на прогон. Три одновременных
`npm run test:server` с одной `TEST_DATABASE_URL` — все зелёные. ~~Полный `npm test`
параллельно сталкивается ещё на фиксированных портах тестов Orchestrator (8711–8716)~~ —
**закрыто в круге 26** (§9.12): тесты процессов берут `PORT=0`, три полных `npm test` на
одной `TEST_DATABASE_URL` параллельно — зелёные.

**Обновление нескольких экземпляров.** Бэкап базы → поднять ОДИН экземпляр новой версии
рядом с работающими (он берёт advisory-lock миграций, отвечает 503 `migrating`,
балансировщик его не нагружает, прежние пишут как раньше) → когда он ответил 200, менять
прежние по одному (SIGTERM, выхода ждать до 10 с). Схема после 001–006 годится и для
кругов 22–24 — откат образа назад без отката базы возможен. Экземпляры круга 22 не шлют
NOTIFY: новые узнают об их записях сверкой (5 с); присутствие между кругами до 24 не
ходит — смешанный режим держать недолго.

### 9.12 Круг 26

Дополняет §9.8–§9.11; нормативно для `server/document/` и `src/sync.js`.

**Список проектов.** `GET /api/projects?kind=design|library&limit=N&after=<курсор>` →
`{projects, more, next?}`. Порядок — `updated_at` по убыванию, при равенстве — id по
убыванию. `limit` — 200 по умолчанию, не больше 1000 (`PROJECTS_PAGE`, `PROJECTS_PAGE_MAX`).
`next` — непрозрачный курсор (ключ `(updated_at, id)` последней строки; в Postgres время с
микросекундами), есть только при `more: true`. Ключ, а не смещение: проект, созданный или
изменённый между страницами, уходит в начало списка и не сдвигает остальные страницы (он
виден при следующем чтении первой). Негодные `kind`, `limit`, `after` — `400`. Хранилище:
`listProjectsPage({kind, limit, after})`. Клиенты: агент (DUIL) просит
`kind=library&limit=MAX_LIBRARIES+1`; оболочка — первую страницу по 50 в шторке «Проекты» и
«Показать ещё» по `next`; проект из ссылки, которого нет на первой странице, — по
`GET /api/projects/:id?head=1`; имя открытого проекта — тоже по `?head=1`.

**Голова DSLTS одним черновиком.** Загрузка снимка с хвостом и догон за другим экземпляром
применяют страницу журнала `core.applyBatches` (словарь узлов копируется раз на страницу, а
не дважды на транзакцию); итог — документ, надгробия, seq, chain, байты документа — тот же,
что у поштучного `collectTombstones` + `applyOps` (тест сверяет). При догоне цепочка
страницы проверяется до применения: целый префикс ложится пачкой и уходит сокетам, на
разрыве — откат, как прежде. Замер (одна машина, 2 ядра): снимок в 20 040 узлов и хвост
50 транзакций по 1000 операций — голова DSLTS за ~0,4 с против ~1,0 с поштучно.

**Бюджет слияния внутри `rebase`.** `mergeIntoHead` передаёт `core.rebase` дедлайн
`deadline = начало + MERGE_BUDGET_MS`: исчерпан посреди слияния — остаток операций в
`dropped` с `reason:'invalid'`, `limit:'merge_budget'` (раньше бюджет проверялся только при
поиске операции, которую не принял строгий `applyOps`).

**Пределы из окружения.** `WS_INFLIGHT`, `HTTP_WRITE_CONCURRENCY`, `HTTP_WRITE_QUEUE`,
`QUEUE_PROJECT_BYTES`, `QUEUE_PROJECT_TXS`, `QUEUE_TOTAL_BYTES`, `PRESENCE_TTL_MS`,
`SNAPSHOT_EVERY`, `SNAPSHOT_KEEP`, `DB_TIMEOUT_MS` — целые, умолчания из `limits.js`;
негодное значение — строка в лог и умолчание; опция `start()` главнее; итог — `svc.config`
(`server/document/README.md`).

**Числа протокола клиента.** Кроме `LIMITS` (равенство с `CLIENT_LIMITS`), реплика
экспортирует `WIRE`: пауза присутствия (≥ 1000 / `PRESENCE_PER_SECOND`), TTL чужого
присутствия (≥ `PRESENCE_TTL_MS` сервера), страница догона (≤ `MAX_LIMIT`), вложенность
значений (= `MAX_VALUE_DEPTH`), длина `command_id` (= `MAX_COMMAND_ID`), код закрытия эпохи
(= `CLOSE.epoch` Hub); тест сверяет.

**Тесты параллельно.** Тесты процессов Orchestrator и nginx берут случайный порт (`PORT=0`,
порт — из строки «слушаю…»; nginx — порт ядра с повтором при занятом); «останов:
выполняемая команда доводится» — дедлайн с запасом и относительная проверка. Три полных
`npm test` на одной `TEST_DATABASE_URL` одновременно — зелёные.

### 10.7 Круг 26

Дополняет §10.2–§10.6; нормативно для `server/orchestrator/` и `src/agent.js`.

**`/agent/health`** — плюс `instance` (случайный id процесса, `orch_<12 hex>`) и
`started_at` (ISO). Оболочка запоминает `instance` в момент отправки команды; поток
оборвался — ответ health с другим `instance` значит «сервер агента перезапустился»: команды
больше нет, текст возвращается в строку с «Повторить». Тот же `instance` — процесс жив:
транзакцию ждут полный срок, короткий сбой связи между проверками команду не губит. Сервер
без `instance` (прежней версии) — прежняя эвристика «был недоступен — стал доступен».

**`retry_after`.** Тело ошибки (HTTP) и событие `error` потока несут `retry_after` (с),
когда срок повтора известен (`busy`, `llm_down`, `document_down`, `shutting_down`). Клиент
(`src/agent.js`) берёт срок из заголовка `Retry-After`, без него — из `retry_after` тела или
события (`AgentError.retryAfterMs`); кнопка «Повторить» считает его обратным отсчётом и для
ошибки, пришедшей в потоке.

**Текст `llm_down`** — для человека, без советов администратору: «Модель сейчас недоступна
— команда не выполнена. Повторите чуть позже.»; модель не подключена — «Модель на сервере
пока не подключена — команды оболочки работают, правки агентом — нет.» (`detail.cause:
'unconfigured'`). Совет («проверьте, что сервер модели запущен», адрес модели и причина
сбоя сети; «задайте LLM_BASE_URL») — строкой в лог Orchestrator, по причине не чаще раза в
минуту. Подробности сети (адрес, `ECONNREFUSED`) в ответ больше не попадают.

**DUIL** просит у Document service `GET /api/projects?kind=library&limit=MAX_LIBRARIES+1`
(§9.12): сервис отдаёт только библиотеки, новые первыми; сервис прежней версии фильтр и
предел не знает — DUIL фильтрует сам, как прежде.
