# Imago Studio — MVP агентного редактора макетов

AI-first редактор: человек формулирует задачу словами (текстом, а в локальной сборке — голосом),
агент строит и правит макет; ручные инструменты есть, но нужны редко. Документ построен по
архитектуре A3 из архитектурного проекта: структурный DSL — источник истины, геометрия
вычисляется решателем, ручные сдвиги хранятся как `override` отсоединённого узла.

Две оболочки, один код:
* **артефакт claude.ai** — агент через `claude.use("sample")`, команды текстом (микрофон в артефактах запрещён платформой);
* **локальная сборка** — статические файлы + `START.cmd`, агент через OpenAI‑совместимый API LM Studio
  (`http://localhost:1234/v1`), голосовой ввод через Web Speech API.

## 1. Модули и контракты

Файлы (ES‑модули, без сборки, без зависимостей кроме шрифтов):

```
index.html      каркас, разметка панелей
styles.css      токены темы, вёрстка оболочки
src/core.js     документ, операции, решатель, отрисовка, взаимодействия  ← агент A
src/brain.js    провайдеры моделей, схемы, промпты, конвейер команд      ← агент B
src/app.js      оболочка: панели, командная строка, голос, история       ← оркестратор
```

### 1.1 `core.js` экспортирует

```js
export function createDoc(seed?) -> Doc
export function applyOps(doc, ops) -> {doc, error?}        // иммутабельно, с проверкой
export function invertOps(doc, ops) -> ops                 // для отмены
export function solve(doc) -> Geometry                     // детерминированно
export function validate(doc, geo) -> Violation[]
export class Stage {                                       // отрисовка + ввод
  constructor(host: HTMLElement, opts: {onSelect, onCommit, onHover})
  render(doc, geo, state)                                  // state: {selection, preview, diff, zoom, pan}
  fitTo(ids?: string[])                                    // вписать во вьюпорт
  screenshot() -> Promise<Blob>                            // PNG активного артборда
  toSVG(artboardId) -> string
}
export const ops = { create, remove, set, move, setToken } // конструкторы операций
```

### 1.2 Модель документа

```ts
Doc = { id, version:int, root:NodeId, nodes:Record<NodeId,Node>, tokens:Tokens, meta:{name, createdAt} }
Node =
  | {type:'page',   id, name, parent:null, children:NodeId[]}
  | {type:'frame',  id, name, parent, children, layout, size, fill?, stroke?, radius, pos?, override?, clip?}
  | {type:'text',   id, name, parent, characters, style, color?, align, size, pos?, override?}
  | {type:'rect'|'ellipse', id, name, parent, size, fill?, stroke?, radius, pos?, override?}
  | {type:'image',  id, name, parent, src?, fill?, radius, size, pos?, override?}
Layout = {mode:'none'|'row'|'column', gap, padding:{t,r,b,l}, align:'start'|'center'|'end'|'stretch', justify:'start'|'center'|'end'|'between', wrap:boolean}
Size   = {w:SizeSpec, h:SizeSpec},  SizeSpec = {mode:'fixed', value} | {mode:'hug'} | {mode:'fill'}
Tokens = {colors:Record<string,'#rrggbb'>, type:Record<string,{fontSize,fontWeight,lineHeight,letterSpacing?,font?}>, spacing:number[], radii:number[]}
Override = {x,y,w,h}   // абсолютная геометрия отсоединённого узла относительно родителя
```

Артборд — фрейм, чей `parent === root`; у него обязателен `pos:{x,y}` (координаты на бесконечном холсте).

### 1.3 Операции

Пять, как в архитектурном проекте: `create{node,index?}`, `remove{id}`, `set{id,path,value?}`,
`move{id,parent,index}`, `setToken{path,value?}`. Применение иммутабельно и перепроверяет узел схемой;
защищённые пути (`id`, `type`, `parent`, `children`) менять нельзя. `remove` уносит поддерево.
Каждая пользовательская или агентная правка — **транзакция**: массив операций + инверсия для отмены.

### 1.4 Решатель

Порядок: для каждого артборда рекурсивно сверху вниз. Режимы `row`/`column` раскладывают детей в поток
с `gap`, `padding`, `align`, `justify`, `wrap`; `none` — свободное размещение по `pos`. Размеры: `fixed` —
значение; `hug` — по содержимому (текст меряется через `measureText` на offscreen‑canvas с теми же
шрифтами, что и отрисовка); `fill` — остаток по главной оси, растяжение по поперечной. Узел с `override`
позиционируется абсолютно внутри родителя и не участвует в потоке.
Решатель обязан быть чистой функцией: одинаковый документ → одинаковая геометрия (тест на равенство хэшей).

### 1.5 Отрисовка

`Stage` рисует в **SVG** (чёткий текст, простой хит‑тест, экспорт «как есть»), поверх — слой
интерфейса (рамки выделения, ручки, подсказки). Поддержать: зум колесом (к курсору), панорама
пробелом/средней кнопкой, выделение кликом, Shift+клик, рамка выделения, перетаскивание (создаёт
`override` или меняет порядок в потоке — по проекции сдвига: вдоль главной оси ≥0.7 → `move`, иначе
`override`), ресайз за 8 ручек, двойной клик по тексту — инлайн‑правка, Delete, Ctrl/Cmd+Z/Shift+Z,
Ctrl/Cmd+D дублирование, стрелки — сдвиг на 1/10 px. Анимация применения агентной транзакции:
изменённые узлы подсвечиваются и плавно переезжают (FLIP, 220 мс, уважая `prefers-reduced-motion`).

### 1.6 `brain.js` экспортирует

```js
export function makeProvider(cfg) -> {name, complete(messages, schema, opts) -> Promise<object>}
   // cfg.kind: 'claude' (claude.use('sample').json) | 'lmstudio' (OpenAI-совместимый /chat/completions)
export async function runCommand({doc, selection, utterance, provider, onStage, signal}) -> {
  ops, preview:{doc, geo}, plan:{title, summary, steps[]}, warnings[], usage
}
export async function runVariants({doc, selection, utterance, provider, n}) -> [{label, ops, preview}]
export const SCHEMAS = { plan, tree, patch }
```

Конвейер одной команды: классификация (создать / изменить / оформление / вопрос) → выбор области
(выделение, иначе активный артборд, иначе весь документ) → план (короткий JSON) → генерация
(дерево для создания либо список точечных правок для изменения) → материализация в операции → решатель
→ валидаторы → при ошибках одна попытка починки с обратной связью → результат.
Стадии транслируются в `onStage({stage, text, partial?})`, чтобы интерфейс показывал ход работы.

Схема ответа модели — компактное дерево (как в layout-agent): `{type, name?, layout?, size?, fill?, text?, style?, children?}`,
где размер — число | `"hug"` | `"fill"`, цвет — имя токена или `#rrggbb`, отступы — число | `[v,h]` | `[t,r,b,l]`.
Точечная правка — `{op:'set'|'remove'|'create'|'move', target:'<id|name|роль>', path?, value?}` с разрешением цели по имени/роли.

### 1.7 Голос (локальная сборка)

`webkitSpeechRecognition`/`SpeechRecognition`, язык `ru-RU`, непрерывный режим с промежуточными
результатами; кнопка удержания (Space вне ввода) и режим «всегда слушать» с ключевой фразой.
В артефакте API недоступен — кнопка скрыта, в подсказке сказано, где голос работает.

## 2. Что должно работать в MVP

1. Пустой холст с примером: два артборда (мобильный экран и десктопный блок), заполненные реальным содержимым.
2. Команда текстом → план → макет; видно, что делает агент; результат появляется анимацией.
3. Правка выделенного: «сделай заголовок крупнее», «замени кнопку на две», «сделай тёмную тему».
4. Три варианта по одной команде, выбор кликом.
5. Ручная правка: перетащить, изменить размер, поменять текст, удалить; агент уважает ручные сдвиги (`override`).
6. Отмена/повтор любой транзакции, включая агентные, с понятной историей.
7. Экспорт: PNG артборда, SVG, JSON документа; импорт JSON.
8. Сохранение: в артефакте — `db` (документы пользователя), локально — файл рядом с приложением.
9. Тема интерфейса светлая/тёмная, документ живёт в своих токенах независимо от темы интерфейса.

## 3. Дизайн

Тёмный «студийный» интерфейс, светлый холст. Токены:

```
--ink        #0D0E12   фон приложения
--panel      #14161C   панели
--line       #222735   разделители
--text       #E8EAF0
--muted      #8A92A6
--accent     #FF6B3D   действие пользователя (команда, выделение)
--agent      #38D6B0   активность агента (стадии, подсветка изменений)
--warn       #F0B429
```
Шрифты: интерфейс — IBM Plex Sans; числа и ярлыки — IBM Plex Mono; заголовок приложения и пустые
состояния — Instrument Serif. В светлой теме те же роли, ground `#F7F6F3`, панели `#FFFFFF`.

Композиция: слева узкий рельс со страницами и слоями (сворачивается), в центре холст во всю высоту,
справа инспектор (появляется только при выделении), снизу по центру — командная строка: она и есть
главный элемент, над ней лентой идут стадии работы агента.

## 4. Отклонения реализации от этого проекта

Проект писался до сборки; ниже — где готовое приложение сознательно разошлось с ним.
Полностью изменения и их причины описаны в `ОТЧЁТ.md`.

* **Акцент интерфейса — холодный индиго, а не `#FF6B3D`.** Оранжевый остался цветом
  ДОКУМЕНТА (кнопка внутри макета), и два оранжевых на одном экране спорили за роль
  «главное действие». Интерфейсный акцент уведён в индиго; цвет агента (`--agent`) и
  предупреждения сохранены.
* **Голос — кнопка микрофона (или клавиша V), а не удержание пробела.** Пробел занят
  панорамой холста; одновременное срабатывание включало панораму и распознавание сразу.
  Из §1.7 сделано: непрерывное распознавание с промежуточными результатами, граница команды
  по паузе 1,2 с, режим «слушать постоянно» отдельным переключателем в настройках
  (по умолчанию выключен, микрофон сам гаснет после 10 с тишины). Не сделана только
  ключевая фраза: режим включается кнопкой, а не словом.
* **Часть команд выполняет сама оболочка, не обращаясь к модели.** Отмена и повтор
  («верни как было», «отмени два раза»), просьба о вариантах, выбор варианта, переключение
  артборда, масштаб и «вписать», выделение слоя по имени, экспорт, открытие панелей.
  Так голосом управляется не только макет, но и сам редактор — в том числе когда модель
  не подключена. Артборд, который человек видит, задаёт область работы агента, поэтому
  «покажи сводку недели» — это ещё и указание агенту, где работать.
* **Кнопка микрофона в артефакте не скрыта, а выключена** с пояснением: так видно, что
  голос существует и где он работает.
* **Появилось намерение `clarify`** (переспрос) сверх четырёх из §1.6: для голоса это
  обязательный случай — недослышанная фраза не должна становиться макетом.
* **Выжимка документа описывает весь документ**, а не выбранную область: область работы
  размечается пометками внутри полной картины. Без этого агент не мог сослаться на
  соседний экран.
* **`Stage.fitTo(ids, {padding, inset, maxZoom})`** принимает поля вьюпорта: командная
  строка лежит поверх холста, и без вычета её высоты низ макета всегда срезан.

## 5. Компоненты: библиотека как словарь агента (круг 19)

Проектное решение, принятое по итогам разговора с пользователем: сначала строится
UI-библиотека, потом продукт собирается из неё. Раздел описывает, КАК это лежит в
документе. Он обязателен к соблюдению всеми тремя частями (`core`, `brain`, оболочка) —
это общий контракт, а не предложение.

### 5.1 Почему именно так

Документ и без того хранит структуру, а не геометрию, поэтому компонент здесь — это
не «связанная копия, которую надо синхронизировать», а **именованное поддерево плюс
объявленные пропсы**. Синхронизировать нечего: геометрию всё равно считает решатель.

Главное следствие — не переиспользование, а **сужение словаря агента**: модель выбирает
из компонентов продукта вместо того, чтобы сочинять кнопку с нуля. Из этого:
выжимка документа схлопывается (экземпляр — одна строка вместо поддерева),
генерация дешевеет и попадает точнее, а «агент собрал не из нашей системы»
перестаёт быть вопросом ревью и становится невозможным состоянием документа.

### 5.2 Пять операций не растут

Новых операций НЕТ. Компонент — это поле на обычном узле, поэтому `create/remove/set/
move/setToken` покрывают всё, а `applyOps` (неизменяемость), `invertOps` (отмена) и
транзакция оболочки работают без единой правки в своей механике.

### 5.3 Где живут мастера

У корня документа появляется ещё один потомок — **библиотека**: узел с `role: 'library'`,
`type: 'page'`. Не «второй» по счёту: контракт — «ребёнок корня с `role: 'library'`»,
индекс не фиксирован (в демо она идёт последней, чтобы номера досок не поехали).
Это единственное место, где странице разрешён родитель.

Библиотека НЕ доска: `isArtboard` для неё ложь, в список досок не попадает, в «все доски»
при оформлении не считается, в экспорт «всё» не идёт. Её **прямые** дети — мастера
компонентов; поле `component` на узле, лежащем не в библиотеке, мастером его не делает.
На холсте библиотека при этом РИСУЕТСЯ, рядом с досками и без подписи доски: иначе
обещание «правка мастера меняет все экземпляры» человеку нечем показать.

Такое размещение выбрано сознательно: одна карта узлов на документ, поэтому операции,
отмена, валидатор и решатель не получают особых случаев.

### 5.4 Мастер

Мастер — обычный узел (чаще `frame`), лежащий в библиотеке, с новым полем:

```js
component: {
  name: 'Кнопка',            // как его назовёт человек и модель
  props: [                    // что разрешено менять у экземпляра
    { name: 'текст', kind: 'text',   target: '<id узла внутри мастера>', path: 'characters' },
    { name: 'вид',   kind: 'enum',   target: '<id>', path: 'fill', values: ['accent', 'surface'] },
    { name: 'виден', kind: 'bool',   target: '<id>', path: 'visible' }
  ]
}
```

`kind` — один из `text | enum | color | number | bool`. `target` обязан быть узлом ВНУТРИ
этого мастера, `path` — тем же путём, что понимает `set`. Реестра компонентов в документе
нет: список компонентов — производная от детей библиотеки, считается на лету.

### 5.5 Экземпляр

Новый тип узла — `instance`:

```js
{ id, type: 'instance', parent, name?, of: '<id мастера>',
  props: { 'текст': 'Оплатить', 'вид': 'accent' },
  size?, override?, visible? }
```

Детей у экземпляра нет: его содержимое — это мастер. `props` могут содержать ТОЛЬКО
объявленные имена; неизвестное имя — негодная операция (`bad-op`), как и любое другое
нарушение схемы, а в документе, пришедшем из файла, такое имя просто не применяется
и ловится валидатором (`unknown-prop`).

Оси `size` необязательны по отдельности: незаданная берётся у мастера. Поэтому экземпляр
кнопки получает её размер сам, а тяга за одну кромку не превращает вторую ось в `fixed`.

### 5.6 Раскрытие при решении

`solve` раскрывает экземпляр на лету: раскладывает поддерево мастера, применяя пропсы,
и кладёт прямоугольники под **синтетическими** идентификаторами `"<id экземпляра>/<id
узла мастера>"`. Корень мастера — исключение: он раскрывается под id САМОГО экземпляра,
поэтому `geo.rects[<id экземпляра>]` и есть рамка экземпляра, а не вторая рамка поверх неё.

В `doc.nodes` раскрытых узлов нет и не будет — в этом и смысл: документ остаётся
коротким, а геометрия по-прежнему функция от структуры. `geo.order` тоже содержит только
узлы документа: поэтому клик попадает в экземпляр целиком, а не в его внутренность.

Требования к раскрытию: оно детерминировано (тот же документ — тот же `hashGeometry`);
глубина вложенных экземпляров ограничена (предел выбрать и назвать); компонент,
который прямо или косвенно содержит экземпляр самого себя, — нарушение, а не зависание.

### 5.7 Отсоединение

«Отсоединить» превращает экземпляр в настоящую копию поддерева (`cloneSubtree`) —
одна транзакция `remove` + `create`, отменяемая как всё остальное. Это тот же приём,
которым уже описан ручной сдвиг: исключение помечено явно, а не спрятано.

### 5.8 Новые коды валидатора

* `dead-instance` — `of` указывает на узел, которого нет, или на узел вне библиотеки;
* `unknown-prop` — в экземпляре пропс, которого мастер не объявлял;
* `component-cycle` — компонент содержит экземпляр самого себя;
* `instance-too-deep` — вложенность экземпляров глубже предела.

Первые три — блокирующие (документ нельзя показать как верный), четвёртый — `warn`.

### 5.9 Что видит модель

В выжимке библиотека идёт отдельным блоком ПЕРЕД документом — это словарь:

```
БИБЛИОТЕКА (собирать только из этого):
  Кнопка(текст, вид: accent|surface)
  Карточка товара(заголовок, цена, картинка)
```

Экземпляр в выжимке — одна строка: `Кнопка "Оплатить" вид=accent`, без внутренностей.
Создавать экземпляр модель может только ссылкой на существующий компонент; выдуманное
имя отсекается там же, где сейчас отсекаются выдуманные слои.

### 5.10 Чего этот круг НЕ делает

Зазоры, скругления и размеры остаются числами. Перевод их на ссылки в шкалу
(`spacing.4` вместо `16`) — следующий шаг, он стоит на компонентах, а не наоборот.

## 6. Шкалы как ссылки: в документе нет числа 16 (круг 20)

Второй шаг плана «библиотека, потом сборка». Сейчас `layout.gap: 16` — просто число; шкала
`tokens.spacing` нужна только для мягкого замечания «вне шкалы» и шага по умолчанию. То есть
система есть, но документ ей не подчинён: смена шкалы ничего не переверстывает, а «сделай
просторнее» — это прибавка пикселей, а не шаг по шкале. Раздел описывает, как это меняется.
Он обязателен для всех трёх частей приложения.

### 6.1 Ссылка на шаг шкалы

Значение отступа или скругления может быть **ссылкой на шаг шкалы** — строкой вида
`'spacing.<индекс>'` или `'radii.<индекс>'`, где индекс — позиция в массиве
`tokens.spacing` / `tokens.radii`:

```js
layout: { gap: 'spacing.6', padding: { t: 'spacing.8', r: 'spacing.7', b: 'spacing.8', l: 'spacing.7' } }
radius: 'radii.4'
```

Число по-прежнему допустимо — это значение «мимо шкалы», и валидатор о нём говорит как
сейчас (`off-scale`, info). Ссылка на несуществующий шаг — `dead-scale-ref` (error).

Индекс, а не имя, выбран сознательно: индексы устойчивы при самой частой правке шкалы —
изменении значений (в том числе всей лестницы разом), — и не требуют менять формат
`tokens.spacing`, который уже понимают `setToken` и мозг. Вставка шага В СЕРЕДИНУ шкалы
сдвигает ссылки; это редкая операция, и она оформляется отдельной функцией ядра, которая
переписывает ссылки вместе со вставкой. Правка шкалы «в лоб» через `setToken spacing.6`
меняет только значение шага — ровно то, ради чего всё делается.

### 6.2 Какие поля

Ссылками становятся: `layout.gap`, `layout.padding.{t,r,b,l}` → `spacing`; `radius`
(и покорнерные формы, если они есть) → `radii`. Размеры (`size.*.value`), позиции и
типографика этим кругом НЕ трогаются — у размеров нет шкалы, а у типографики уже есть
своя система (`tokens.type`).

### 6.3 Решатель и всё, что читает эти поля

Ссылка разрешается в число на входе решателя — одной функцией ядра, и той же функцией
пользуются валидатор, экспорт, инспектор и мозг. Читать `layout.gap` как число напрямую
больше нельзя нигде; это правило проверяется тестом на демо-документе, где все отступы
и скругления — ссылки.

### 6.4 «То же самое» — одно на всех

`set layout.gap = 16` при текущем `'spacing.6'` (= 16) — правка тем же значением: поле
остаётся байт в байт (`keepFieldForm`), мозг считает её пустой (`sameAsNow`). Обратное
тоже: `set layout.gap = 'spacing.6'` при текущем `16` — НЕ пустая правка: число становится
ссылкой, и это изменение смысла, хотя картинка та же. Механический тест мозга «зеркало
совпадает с настоящим `applyOps`» расширяется на эти формы.

### 6.5 Миграция

`ensureScaleRefs(doc)` — один вызов, идемпотентный: число, ТОЧНО совпадающее с шагом
шкалы, становится ссылкой на этот шаг; число мимо шкалы остаётся числом. Демо-документ
после `createDoc()` уже целиком на ссылках. Оболочка зовёт миграцию там же, где
`ensureLibrary`.

### 6.6 Что видит модель

В выжимке шкалы печатаются с индексами и значениями один раз, в шапке:
`spacing: 0=0 1=2 2=4 3=6 4=8 5=12 6=16 7=20 8=24 9=32 10=40 11=48 12=64`. У узлов отступы
печатаются как `gap spacing.6(16)` — и ссылка, и число, чтобы модель могла и рассуждать
о пикселях, и отвечать ссылкой. Правило промпта: отступы и скругления задавать ссылкой на
шаг; «плотнее/просторнее» — это шаг вниз/вверх по шкале, а не прибавка пикселей. Число
от модели, совпадающее с шагом, мозг превращает в ссылку сам. Число мимо шкалы: если его
назвал сам человек (оно есть в реплике) — остаётся числом, и об этом сказано; если число
придумала модель (16 + 8 вместо шага вверх) — берётся ближайший шаг, и об этом тоже
сказано («28 — мимо шкалы скруглений, взял ближайший шаг 24. Скажите «ровно 28», если
нужно именно это число»). Ноль — «без отступа», не обсуждается.

### 6.7 Что видит человек

Человек шкалу не обязан знать. Инспектор показывает значение в пикселях и признак «по
шкале»; выбор — из шагов шкалы с возможностью «своё число». В сообщениях: «Зазор 16 → 24
(шаг шкалы)». Редактор шкал — отдельная шторка: значения шагов, и правка любого сразу
переверстывает всё, что на него ссылается. Слово для человека — «шкала отступов» и
«шкала скруглений», без «spacing» и «radii».

## 7. Распознавание намерений оболочки: не словарь, а классификатор (решение, круг 21)

Сейчас команды оболочки — отмена, повтор, «стоп», варианты, переключение доски, «сделай из
этого компонент», «отсоедини» — узнаются словарём русских регулярок (`shellIntent`,
`recognizeAction`, `recognizeVariants`, `recognizeComponentIntent`). Это работает быстро
и без модели, но привязано к языку: человек может говорить на любом, а словарь — нет.
Решение: **словарь заменяется классификатором намерений на многоязычных эмбеддингах.**

* Намерения оболочки (двадцать-тридцать) описываются примерами на нескольких языках.
  Реплика превращается в вектор маленькой локальной моделью (миллисекунды, CPU) и
  сравнивается с примерами. Уверенное попадание — команда исполняется сразу, без большой
  модели; иначе реплика идёт планировщику, как сейчас. Язык перестаёт быть параметром.
* «Стоп» дополнительно держится точным совпадением по короткому списку на языках
  интерфейса: цена промаха у команды прерывания — продолжающаяся работа агента.
* Ответы на переспрос и выбор варианта («второй», «этот») — тот же классификатор, но с
  контекстом «сейчас задан вопрос».
* Основной конвейер (план → патч) от языка не зависит и не меняется: большая модель
  понимает любой, имена слоёв и компонентов берутся из документа.

Пока классификатора нет, словарь остаётся как есть; **расширять его новыми формами
больше не нужно** — следующие правки распознавания делаются классификатором.

## 8. Целевая архитектура системы (решение, круг 21; уточнено в круге 22)

Принято на доске вместе с пользователем. Имена ниже — канонические; код и разговоры
ведутся в них. Текущее приложение (§1–7) — всё в браузере; этот раздел описывает, во что
оно разъезжается, когда библиотека становится общей на команду и продукты, а документ
правят несколько человек и агент одновременно.

Круг 22 уточнил (после независимого ревью, `docs/07`): процессов два, а не восемь; имена
с доски — модули с чёткими границами внутри них; клиент — полная реплика с локальным
журналом; слияние транзакций не отказывает; библиотека — проект вида `library`.

### 8.1 Действующие элементы

| Имя | Где живёт | Обязанность |
|---|---|---|
| **CLIENT** | браузер | оболочка + движок `core`; **полная реплика**: локальный журнал (IndexedDB), свои правки применяет всегда и сразу, отправка и приём — отдельный процесс синхронизации (`src/sync.js`); присутствие (кто в сети, выделение) по тому же сокету, без записи |
| **NGINX** | вход | TLS, статика клиента, прокси `/api` и `/ws` → Document service, `/agent` → Orchestrator |
| **Document service** | процесс «документ» | модули **DSLR** (чтение: снимок + хвост журнала = стейт и номер головы), **DSLTS** (секвенсор и единственный писатель: перекладка, номер, запись, снимок раз в N), **Hub** (рассылка транзакций и присутствия по WebSocket). Держит голову каждого открытого проекта в памяти. Содержит движок |
| **Orchestrator** | процесс «агент» | ведёт команду по шагам; модули **JEV** (классификатор: команда оболочки и какая), **DUIL** (чтение библиотек — срез проекта вида `library`: компоненты с пропсами, шкалы, версии), **DSLV** (движок: применяет патч к копии стейта, считает раскладку, судит форму и смысл), **LLM** (клиент к модели). **К базе не прикасается**: стейт берёт у DSLR, пишет через DSLTS как любой клиент |
| **LLM** | внешняя модель | Claude / LM Studio / любой OpenAI-совместимый; получает промпт, отдаёт патч в терминах DSL |
| **База** | PostgreSQL | журнал операций каждого проекта (источник истины), снимки, проекты — в том числе вида `library`, трассы агента |

Каждое имя с доски — каталог-модуль со своим интерфейсом; вынести модуль в отдельный
процесс потом — это добавить транспорт, а не переписать.

Модель не пишет DSL никогда: она предлагает патч, DSLV превращает его в операции,
DSLTS записывает. Два места, где недоверенный ответ становится доверенным: DSLV и
слияние в DSLTS.

### 8.2 Поток одной команды (нумерация с доски)

```
0   CLIENT ↔ Document service (DSLR): открыть проект — снимок + хвост, номер головы; дальше WS
1   человек → NGINX (HTTPS)            2   NGINX → CLIENT (статика)
3   CLIENT → Orchestrator: команда (текст, выделение, активная доска, номер базы)
4/5 Orchestrator ↔ JEV: команда оболочки?  да → операции сразу в 12, ответ клиенту по 7b
4a/5a Orchestrator ↔ DSLR: стейт + номер головы
6/7 Orchestrator ↔ DUIL: словарь компонентов
8/9 Orchestrator ↔ LLM: промпт → патч
10/11 Orchestrator ↔ DSLV: стейт + патч → годные операции | нарушение → снова 8 (ретрай, один раз)
12/13 Orchestrator ↔ DSLTS: транзакция (base_seq, ops) → seq, применённые операции, отброшенные
12a DSLTS → база (журнал, раз в N — снимок);  Hub → всем подписчикам проекта, автору тоже
7b  Orchestrator → CLIENT: стадии по ходу работы и ответы команд оболочки
M   CLIENT → DSLTS: ручная правка = транзакция тем же путём, что 12; мимо очереди агента
```

Клиент после открытия документ целиком не получает: только транзакции и номера, применяет
их своим движком — картинка совпадает с той, что посчитал DSLV, потому что движок один.

### 8.3 Правила, без которых это не работает

* **Движок один.** `core` исполняется в CLIENT, в DSLTS (слияние и применение) и в DSLV
  без изменений. Переигрывание журнала — строгий `applyOps` записанных операций в порядке
  `seq`; детерминизм решателя делает картинку сервера и клиента одинаковой.
* **Журнал — источник истины, снимок — производная.** Снимок = документ целиком (`root`,
  `nodes`, `tokens`, `meta`) + версия движка. Каждая транзакция получает номер `seq` от
  DSLTS; клиент и Orchestrator шлют операции с номером базы `base_seq`.
* **Модель согласованности — CP по проекту.** Сервер — единственный арбитр порядка;
  когда он недоступен, никто не фиксирует правки — это цена единственного арбитра, её
  платят все серверно-авторитетные редакторы. Актуальность отстаёт всегда (чужие правки
  приходят с задержкой на круг до сервера), при разрыве — неограниченно. Клиент при этом
  **продолжает работать**: он реплика с локальным журналом, правки принимаются всегда,
  переживают перезагрузку вкладки и досылаются при воссоединении. Неподтверждённое видно
  как неподтверждённое — молча потерять работу нельзя.
* **Слияние не отказывает.** DSLTS перекладывает транзакцию поверх пришедших после
  `base_seq` по правилам §9.6 — операция за операцией. Транзакция целиком не отклоняется
  никогда; отдельная операция отбрасывается только по этим правилам (узел уже удалён,
  перемещение в цикл), и автору об этом сказано (`dropped`). Отказа «документ изменился»
  человек не видит никогда. В журнал ложится **применённая** форма операций.
* **Валидатор — линтер для человека, ворота для агента.** Ручные правки не проверяются
  перед записью: документ может временно содержать `dead-instance`, `overflow`,
  `dead-scale-ref` — это бейджи в слоях, а рендер такое переживает (заглушка вместо
  мёртвого экземпляра, запасное число вместо мёртвой ссылки). Агентная транзакция
  проходит DSLV до записи — чтобы ловить ошибки модели, а не чужие правки; после слияния
  агент при необходимости делает круг починки на свежем стейте.
* **Живое — это оптимистичное применение + рассылка транзакций.** Своя правка рисуется
  сразу своим движком; сервер присылает её применённую форму с номером; чужие прилетают
  транзакциями и применяются тем же движком. На клиенте: `view = replay(confirmed, pending)`.
* **Идемпотентность.** `tx_id` генерирует клиент; `UNIQUE(project_id, tx_id)` в журнале;
  повторная отправка возвращает тот же результат. Переподключение — с последнего
  известного `seq`; если он ниже хранимого хвоста, клиент получает снимок и переигрывает
  свою очередь поверх него — штатный путь.
* **Id узлов и транзакций генерирует клиент**, глобально уникальные: 12 случайных
  символов base36 (~62 бита; на проект в сто тысяч узлов столкновение ~10⁻⁹) — длиннее
  нельзя без причины, id ходят в выжимке к модели и стоят токенов на каждой команде.
  `create` с уже занятым id — повтор, не конфликт: отбрасывается как `exists`.
* **Отмена — новая транзакция, а не откат.** «Отменить» = дописать обратные операции
  своей транзакции с пометкой `undo_of`, повтор — `redo_of`; второе «отмени» отменяет
  предыдущую *свою* транзакцию, а не отмену. Инверсия считается на клиенте от его текущего
  вида **на уровне пути операции**: `set id a.b.c` ↔ `set id a.b.c <было>`; если до правки по
  голове пути лежал скаляр, а стал объект (или наоборот), возвращается голова целиком —
  иначе форму не восстановить. Пересечение с чужой правкой того же листа решает порядок
  `seq`: позже — побеждает.
* **Версия формата движка** (`core.ENGINE_VERSION`) — в каждой транзакции и снимке. Клиент
  со старой версией получает `426` и просьбу обновиться; миграция формата — системная
  транзакция, а не тихая правка снимка.
* **Ретрай ограничен** одним кругом починки; не помогло — берётся лучший вариант, и
  человеку сказано, что не удалось.
* **«Стоп»** ловится на клиенте точным совпадением до сети.
* **Команды агента — в очередь на проект.** Две одновременные команды разным людям
  выполняются по очереди: модель рассуждает над стейтом, который вторая команда уже
  меняет. Ручные правки идут мимо очереди и не ждут агента.
* **Текст меряется одинаково там, где судят раскладку.** DSLTS геометрии не считает —
  операции структурны. DSLV обязан мерить текст тем же измерителем, что клиент (по файлам
  шрифтов; крючок `solve(doc, {measureText})` есть); пока измеритель не общий,
  `overflow` у агента — предупреждение, не отказ.
* **Библиотека = проект вида `library`.** Свой журнал, как у любого проекта; версия —
  помеченный снимок (`library_versions`); продукт **импортирует** мастера: они
  материализуются в его документе под стабильными id системной транзакцией; «обновить
  до v5» = одна транзакция миграции, которую строит DUIL по разнице мастеров. Один
  механизм записи на всё.
* **Чистка журнала — по запасу, не по календарю, и не удаляет.** Раз в сутки операции
  старше последнего снимка, кроме последних N транзакций каждого автора и всего моложе
  недели, **уносятся в холодную партицию** — история «кто что менял» сохраняется, горячий
  хвост остаётся коротким. Клиент, чья база ушла за горячий хвост, получает снимок и
  переигрывает свою очередь (см. идемпотентность).
* **Авторизация и права** в этом круге не решаются: автор — самоназванное имя. Это
  открытый вопрос из ревью (№ 11), он закрывается до внешнего запуска.

### 8.4 Что из текущего кода куда

`src/core.js` — общий модуль движка: его импортируют CLIENT (как сейчас), Document
service (`rebase` + `applyOps`) и DSLV. `brain.js` → Orchestrator (конвейер, промпты,
компилятор патча) и DSLV (`patchToOps` + `validate`). `app.js` → CLIENT; из него уходят
автосохранение в `localStorage` и прямые вызовы модели (второе — при переезде
Orchestrator). Новый `src/sync.js` — реплика: локальный журнал, очередь, сокет.
Библиотека из узла документа → проект вида `library` под DUIL. Словарь регулярок → JEV (§7).

Порядок переезда: **(1) Document service + клиент-реплика** — истина переезжает на сервер,
два окна правят один документ вживую; **(2) Orchestrator** — `brain.js` на сервер, DSLV,
JEV как заглушка на нынешнем словаре, DUIL; **(3) библиотека как проект и импорты**;
**(4) поток стадий 7b по сокету**, потому что до серверного агента уведомлять не о чем.
Локальный запуск — Docker Compose (Postgres + Document service + NGINX); артефакт на
claude.ai к серверу подключиться не может (CSP) и остаётся демонстрацией без сервера.

## 9. Контракт Document service (круг 22)

По этому разделу пишутся сервер (`server/document/`) и клиент (`src/sync.js`); он
нормативен для обоих. JSON, UTF-8; все id — строки; `seq` — целое ≥ 0 (0 — только что
созданный проект); `engine` = `core.ENGINE_VERSION`. Авторизации нет: заголовок
`X-Author` (или поле `author`) — отображаемое имя.

### 9.1 Транзакция

```ts
Tx = {
  tx_id: string,            // генерирует клиент (core.uid('tx')); ключ идемпотентности
  base_seq: number,         // номер головы, которую клиент видел, когда строил ops
  ops: Op[],                // пять операций §1.3; у create узел уже с id (клиентским)
  undo_of?: string,         // tx_id отменяемой транзакции
  redo_of?: string,         // tx_id отменённой транзакции (повтор)
  author?: string,          // отображаемое имя
  author_kind?: 'human' | 'agent' | 'system',   // по умолчанию human
  client?: string,          // clientId вкладки — чтобы отличать своё в рассылке
  title?: string,           // как показать в истории
  engine: number
}
Committed = Tx & {
  seq: number,              // присвоил DSLTS
  ops: Op[],                // ПРИМЕНЁННАЯ форма (после слияния; она и лежит в журнале)
  dropped: { index: number, op: Op, reason: DropReason }[],
  notes?: { index: number, note: 'reparented' }[],   // что слияние поправило, не отбросив
  created_at: string        // ISO
}
DropReason = 'removed' | 'exists' | 'orphan' | 'cycle' | 'invalid'
```

`create` и `move` могут нести `after: NodeId | null` — намерение «после этого соседа»
(`null` — первым); сервер сначала разрешает `after` в индекс, и только без него берёт
`index` (с зажимом в границы). Клиент проставляет `after` всегда, когда знает соседа.

### 9.2 HTTP (`/api`)

| Метод и путь | Тело | Ответ |
|---|---|---|
| `GET /api/health` | — | `200 {ok, engine}` |
| `GET /api/projects` | — | `200 {projects: [{id, name, kind, head_seq, updated_at}]}` |
| `POST /api/projects` | `{name?, kind?: 'design'\|'library', doc?}` | `201 {id, name, kind, head_seq: 0}`; без `doc` — `createDoc()`; документ = снимок при `seq 0` |
| `GET /api/projects/:id` | — | `200 {id, name, kind, head_seq, snapshot: {seq, doc, engine}, tail: Committed[]}` — хвост = транзакции с `seq > snapshot.seq` |
| `PATCH /api/projects/:id` | `{name}` | `200 {id, name, kind, head_seq}` |
| `GET /api/projects/:id/ops?since=<seq>&limit=<n>` | — | `200 {head_seq, txs: Committed[]}`; `since` ниже хранимого хвоста → `410 {snapshot, head_seq}` |
| `POST /api/projects/:id/tx` | `Tx` | `201 Committed`; повтор `tx_id` → `200` с тем же `Committed`; `400` — негодная форма; `404`; `426 {engine}` — версия движка; `503` — хранилище недоступно (клиент держит очередь). `409` не бывает: конкуренция решается слиянием |

### 9.3 WebSocket (`/ws?project=<id>&since=<seq>&client=<clientId>`)

Сервер → клиент:

* `{type:'hello', project, head_seq, engine}` — затем догон: `{type:'tx', tx: Committed}`
  для каждой `seq > since` по порядку, затем живой поток.
* `{type:'tx', tx: Committed}` — каждая зафиксированная транзакция, **своя тоже** (клиент
  узнаёт её по `tx_id`; это и есть подтверждение).
* `{type:'gone', snapshot: {seq, doc, engine}, head_seq}` — `since` ниже хранимого хвоста:
  клиент берёт снимок как `confirmed` и переигрывает очередь.
* `{type:'error', tx_id?, code, message}` — негодная транзакция (форма, версия движка).
* `{type:'presence', client, author, selection: NodeId[], board?: NodeId, at}` — чужое
  присутствие; `{type:'left', client}`.

Клиент → сервер:

* `{type:'tx', tx: Tx}` — то же, что `POST …/tx`; ответ приходит рассылкой `tx` (или `error`).
* `{type:'presence', selection, board}` — эфемерно, не пишется, не чаще 10 раз в секунду.

Гарантия порядка: по одному сокету `tx` приходят с возрастающим `seq` без пропусков
(догон, потом живое). Увидев `seq > last + 1`, клиент запрашивает `GET …/ops?since=last`.

### 9.4 Секвенсор DSLTS

1. Голова проекта в памяти: снимок + хвост → документ, `head_seq`, надгробия (id
   удалённых узлов → последний родитель; восстанавливаются из `remove` в хвосте).
   Загружается лениво при первом обращении, выгружается по бездействию.
2. На транзакцию — под мьютексом проекта (очередь в процессе):
   `tx_id` известен → вернуть сохранённое. Иначе `concurrent` = транзакции с
   `seq > base_seq`; `merged = core.rebase(head, tx.ops, {tombstones})` → `{ops, dropped, notes}`;
   строгий `applyOps(head, merged.ops)` обязан пройти (это гарантирует `rebase`); если нет —
   виноватая операция отбрасывается с `reason:'invalid'`, применение повторяется.
3. В одной транзакции базы: `UPDATE projects SET head_seq = head_seq + 1 … RETURNING head_seq`
   → `seq`; если `seq ≠ память + 1`, писал другой экземпляр — хвост перечитывается, шаг 2
   повторяется (ограниченно); `INSERT INTO operations … ON CONFLICT (project_id, tx_id) DO NOTHING`
   — при конфликте вернуть существующую запись.
4. Обновить голову, отдать `Committed` в Hub (всем подпискам проекта), каждые N = 50
   транзакций — снимок (асинхронно, после ответа).

### 9.5 Клиент-реплика (`src/sync.js`)

* Состояние: `confirmed = {seq, doc}`, `pending: Tx[]` в порядке отправки,
  `view = replay(confirmed.doc, pending)` — теми же `rebase` + `applyOps`, что на сервере.
* Локальный журнал: IndexedDB `imago`, хранилище `projects`, ключ — id проекта:
  `{seq, doc, pending, clientId, updatedAt}`; пишется после каждого изменения (не чаще
  раза в 200 мс). При открытии сначала читается он → рисуется → потом сокет.
* Отправка: `pending[0]` уходит, как только сокет открыт; своя `tx` в рассылке →
  `pending.shift()`, `confirmed = apply(confirmed, tx.ops)`, `seq = tx.seq`, уходит
  следующая. Чужая `tx` → `confirmed = apply(...)`, `view = replay(...)`.
* Переподключение: `since = confirmed.seq`; `gone` → `confirmed = snapshot`; очередь
  досылается с начала (сервер вернёт сохранённое для уже зафиксированных).
* `dropped` своей транзакции показывается человеку одной строкой («2 правки не
  применились: узел уже удалён»); `view` пересчитывается по применённой форме.
* Статус в интерфейсе: «в сети · всё сохранено» / «не в сети · N правок ждут» /
  «синхронизация…»; присутствие — кто в сети, чужие выделения цветной рамкой с именем.
* Отмена/повтор — как в §8.3: инверсия от `view`, транзакция с `undo_of`/`redo_of`.

### 9.6 Правила слияния (`core.rebase(doc, ops, {tombstones})`)

Вход — документ-голова и операции, построенные относительно более старой базы; выход —
применимые операции, отброшенные с причиной и пометки. Правила по операциям:

| Операция | Условие | Результат |
|---|---|---|
| `set` | узел жив | остаётся; поздняя по `seq` побеждает (LWW на уровне листа; `keepFieldForm` как в §6.4) |
| `set` | узел удалён | `dropped: removed` — remove побеждает |
| `setToken` | всегда | остаётся |
| `create` | id занят | `dropped: exists` (повтор) |
| `create` | родитель жив | остаётся; `after` → индекс, иначе `index` с зажимом; дети, которых уже нет, вычёркиваются |
| `create` | родитель удалён | переприкрепляется к ближайшему живому предку по цепочке надгробий, `notes: reparented`; живых предков нет — `dropped: orphan` |
| `remove` | узел жив | остаётся |
| `remove` | уже удалён | `dropped: removed` (нет операции) |
| `move` | узел удалён | `dropped: removed` |
| `move` | новый родитель удалён | ближайший живой предок, иначе `dropped: orphan` |
| `move` | цель внутри поддерева узла (в том числе из-за чужого `move`) | `dropped: cycle` — отбрасывается только поздний |
| `move` | иначе | остаётся; `after` → индекс, иначе `index` с зажимом |

`rebase` детерминирован и не бросает; после него строгий `applyOps` обязан пройти.
Тест сходимости: три реплики, случайные операции над общим документом, любые порядки
доставки через один журнал → одинаковый документ у всех (сравнение по `hashDoc`).
